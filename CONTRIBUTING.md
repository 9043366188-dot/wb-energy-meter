# Contributing

Спасибо за интерес к проекту! Краткие правила.

## Как сообщить о баге

Откройте Issue с шаблоном «Bug report» (`.github/ISSUE_TEMPLATE/bug.md`).
Обязательно укажите:

- версию `wb-energy-meter` (`wb-energy-meter --version`);
- ревизию WB (`cat /etc/wb-release`);
- что делали;
- что ожидали увидеть;
- что увидели на самом деле;
- последние 100 строк лога: `journalctl -u wb-energy-meter -n 100`.

## Как предложить фичу

Откройте Issue с шаблоном «Feature request». Прежде чем писать код,
обсудите идею — это сэкономит ваше и наше время, если что-то уже есть в
дорожной карте или не подходит по архитектуре.

## Как прислать pull request

1. Форкните репозиторий и сделайте ветку от `main`:
   ```
   git checkout -b feature/short-description
   ```
2. Сделайте изменения, добавьте тесты.
3. Запустите тесты локально:
   ```
   python tests/test_step3_consumption.py
   python tests/test_step3_e2e.py        # требует запущенный mosquitto
   ```
4. Сделайте осмысленный commit message — желательно по
   [Conventional Commits](https://www.conventionalcommits.org/):
   - `feat:` — новая возможность
   - `fix:` — исправление бага
   - `docs:` — только документация
   - `refactor:` — рефакторинг без изменения поведения
   - `test:` — только тесты
   - `chore:` — рутина (зависимости, форматирование)
5. Запушьте и откройте PR. Дождитесь зелёного CI.

## Стиль кода

- Python 3.9+, форматирование по PEP 8.
- Длина строки ~88 символов (как у `black`), но без фанатизма.
- Docstring'и на русском или английском — главное, чтобы был контекст
  «зачем», а не «что» (что и так видно из кода).
- Имена переменных и логи — по-русски, если это пользовательское
  сообщение, и по-английски — если внутреннее техническое.

## Архитектурные принципы

- **Не дублировать телеметрию.** Сырые значения каналов живут в
  `wb-mqtt-db`. Наша БД хранит только реестр и (с Шага 4) производные
  агрегаты, которые легко пересчитать.
- **Не писать в чужие БД.** `wb-mqtt-db` имеет публичный контракт через
  MQTT-RPC, читать через него — да; писать в его SQLite напрямую — нет.
- **Не блокировать MQTT-колбэки.** Тяжёлая работа (например, обращение к
  БД на каждом сообщении) — в фоновые задачи (`background.py`).
- **Миграции БД — только вперёд.** Не править существующие SQL-файлы
  миграций, всегда добавлять новый `NNN_xxx.sql`.

## Тестирование

- Юнит-тесты — без сети, без MQTT, без БД (или с временной БД в
  `tmpfile`).
- E2E-тесты — с реальным `mosquitto` и фейковым «ответчиком» вместо
  настоящего `wb-mqtt-db`.
- Не используем `pytest` для упрощения зависимостей: тесты — обычные
  Python-скрипты с `assert` (так их легче запустить прямо на WB при
  отладке).

## Релизы

- Версии по [SemVer](https://semver.org/): `MAJOR.MINOR.PATCH`.
- При выпуске релиза:
  1. Обновить версию в `wb_energy_meter/__init__.py` и `pyproject.toml`.
  2. Добавить раздел в `CHANGELOG.md`.
  3. Создать тег `vX.Y.Z` и push.
  4. GitHub Actions сами соберут архив `wb-energy-meter.tar.gz` и
     приложат его к Release.
