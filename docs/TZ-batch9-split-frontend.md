## 1. Что уже подготовлено (не переделывать)

**`tests/browser/test_b04_app_surface.py` + `tests/fixtures/app_keys_baseline.json`**
(коммит `45b7e51`) — сверка живой страницы с эталоном из 564 ключей.

Это главный инструмент партии. При переносе кода самая дорогая ошибка —
молча потерять метод: Alpine не ругается на несуществующий метод в
разметке, кнопка просто перестаёт работать, а консоль, `node --check`,
баланс тегов и все 39 юнит-тестов остаются зелёными. Именно так
получаются белые экраны, которые в этом проекте уже были дважды.

**Эталон при переносе не трогать.** Перенос кода не меняет поверхность
компонента. Покраснел `b04` — значит потерялся метод или появился
дубликат имени; это не повод править эталон, это тот самый баг.

## 2. Проверенные факты об окружении

Проверено 26.09.2026 на обоих наборах версий, пользоваться можно:

- **Новые файлы под `wb_energy_meter/static/js/` отдаются без нового
  маршрута.** `Flask("wb_energy_meter")` даёт штатный `/static/<path>`;
  `GET /static/js/<файл>.js` вернул 200 и на свежем Flask, и на
  `flask==1.1.2`/`werkzeug==1.0.1`. Маршрут `/static/vendor/<file>`
  писать по образцу **не нужно** — и, значит, ловушка с
  `werkzeug.safe_join` не повторяется.
- **`/api/selfcheck` уже прикрывает новые файлы.** `build_selfcheck_result`
  (`api.py`, ≈стр. 248–310) вытаскивает из `index.html` все
  `src="/static/…"`/`href="/static/…"` и проверяет каждый на диске:
  существует, читается, непустой. Пропавшая или пустая часть будет
  видна в `/api/selfcheck` до того, как пользователь увидит белый
  экран. Ветка для не-`vendor` путей там уже есть.
- **Никаких `?v=…` в `src`.** Резолвер selfcheck не отрезает
  query-строку: `/static/js/core.js?v=0.19.0` превратится в поиск файла
  с таким именем и даст ложный «файл не найден». Ревалидация кэша и так
  идёт по ETag/Last-Modified, которые Flask отдаёт на статику. Если
  когда-нибудь query всё же понадобится — сначала научить `resolve()`
  его отбрасывать, отдельной задачей.

### 3.2 Механика сборки

Каждый файл регистрирует свою часть:

```js
// wb_energy_meter/static/js/plan-v3.js
(function () {
  window.WBEM = window.WBEM || { parts: [], conflicts: [] };
  window.WBEM.parts.push(function planV3() {
    return {
      planV3Current: null,
      openPlanV3Tab() { /* ... */ },
      // ...
    };
  });
})();
```

`app()` остаётся в `index.html` и только собирает:

```js
function app() {
  const out = {};
  const reg = window.WBEM || { parts: [], conflicts: [] };
  for (const part of reg.parts) {
    const frag = part();
    for (const k of Object.keys(frag)) {
      if (k in out) reg.conflicts.push(k + ' (повтор в «' + part.name + '»)');
      out[k] = frag[k];
    }
  }
  return out;
}
```

Требования к механике:

- **Конфликт имён не молчит и не роняет страницу.** Дубликат
  записывается в `window.WBEM.conflicts` (его читает `b04`) и
  показывается пользователю через уже существующую загрузочную
  заглушку — ту же, что проверяет `tests/test_step12_selfcheck.py`.
  `throw` использовать нельзя: он даст ровно тот белый экран, от
  которого мы уходим.
- **`this` не трогать.** Методы объявляются в объектных литералах, как
  сейчас; при слиянии `this` по-прежнему указывает на компонент Alpine.
  Стрелочные функции вместо методов не подставлять.
- **Модульные переменные** (`_planV3Map`, слои Leaflet и подобные)
  остаются переменными уровня файла внутри своей IIFE, вне Alpine — как
  сейчас. Если значение нужно двум частям, это `window.WBEM.shared`, а
  не глобальная переменная.
- **Порядок подключения** в `index.html`: vendor-скрипты → все части
  (обычные `<script src>`, без `defer`, без `type="module"`) →
  `alpine.min.js` c `defer`. Alpine обязан стартовать после того, как
  все части зарегистрированы.
- Загрузочная заглушка и защита от белого экрана остаются в
  `index.html` и в первом инлайн-блоке — их не выносить.

### 3.3 Порядок работы и откат

- **По одному файлу за коммит.** После каждого файла: `node --check` по
  нему, `test_step6_webui.py`, `test_step12_selfcheck.py`,
  `tests/browser/run.py` (все четыре сценария, включая `b04`). Только
  потом следующий.
- Начинать с самого изолированного экрана, а не с `core.js`. Разумный
  порядок: `plan-v3` → `reports-v2` → `overview-v2` → `plan-v1` →
  `zones` → `consumption` → `dashboard` → `settings` → `structure` →
  `plan-v2` → и в конце `core.js` из того, что осталось.
- **Половинчатый результат допустим и является нормальным исходом.**
  Если после N файлов стало ясно, что дальше не идёт, — остановись на
  последнем зелёном коммите, опиши в отчёте, что вынесено и что
  осталось. Хуже монолита это не делает: несколько вынесенных экранов
  плюс остаток в `index.html` — рабочее состояние.
- Откатывать целиком нужно только если зелёного состояния не осталось.
