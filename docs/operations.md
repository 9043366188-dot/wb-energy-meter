# Эксплуатация wb-energy-meter

Что делать с работающей службой на контроллере: где что лежит, как устроены установка,
обновление и откат, как восстановиться из резервной копии, как проверить миграцию и нагрузку,
что делать при типичных неисправностях. Документ описывает версию 0.25.0 и сверен с
`scripts/install.sh`, `scripts/self-update.sh`, `scripts/check-generation.sh`,
`scripts/clean-start-once.sh` и `scripts/loadtest/`. Все команды — для контроллера Wiren Board
от `root`; адрес в примерах `127.0.0.1:8080` (порт — `http.port` в `/etc/wb-energy-meter.conf`).

Описание HTTP API — в [`docs/api-v2.md`](api-v2.md); границы текущего состояния проекта —
в [`docs/status.md`](status.md).

## 1. Где что лежит

| Что | Где |
|---|---|
| Код службы | `/opt/wb-energy-meter/wb_energy_meter/` |
| Скрипты (установка, самообновление, страж поколений) | `/opt/wb-energy-meter/scripts/` |
| Версия и коммит установки | `/opt/wb-energy-meter/VERSION.json` |
| Конфиг | `/etc/wb-energy-meter.conf` (создаётся один раз; установка его не перезаписывает) |
| База данных | `/mnt/data/var/lib/wb-energy-meter/state.db` (рядом `-wal`, `-shm` пока служба работает) |
| Изображения планов | `/mnt/data/var/lib/wb-energy-meter/plans/` |
| Статус последнего обновления | `/mnt/data/var/lib/wb-energy-meter/update-status.json` |
| Резервные копии БД установки | `/mnt/data/var/lib/wb-energy-meter/state.db.backup-ГГГГММДД-ЧЧММСС` (хранятся 5 последних) |
| Отложенные тестовые данные («чистый старт») | `/mnt/data/var/lib/wb-energy-meter/test-data-<дата-время>/` |
| Каталог отката самообновления | `/opt/wb-energy-meter.rollback/` (есть только после неудачного или оборванного обновления) |
| Лог службы | `/var/log/wb-energy-meter/wb-energy-meter.log` и `journalctl -u wb-energy-meter` |
| Лог обновления | `/var/log/wb-energy-meter/update.log` |
| Юнит systemd | `/etc/systemd/system/wb-energy-meter.service` |
| Запуск службы и CLI | `/usr/bin/wb-energy-meter`, `/usr/bin/wb-energy-meter-cli` |

`scripts/uninstall.sh` убирает юнит, лаунчеры и `/opt/wb-energy-meter`; конфиг, логи, данные и
`/opt/wb-energy-meter.rollback` оставляет — их удаляют вручную.

## 2. Установка и обновление

Первая установка — `install-from-github.sh` (README, «Установка»); обновление — кнопка «Обновить
сейчас» в «Настройках» либо повторная установка. Обе дороги идут через `scripts/install.sh`, который
по шагам делает:

1. проверяет `root`, Python и зависимости (`python3-paho-mqtt`, `python3-yaml`, `python3-flask`);
   `apt` трогает только если пакетов нет (код выхода **5**, если поставить не удалось);
2. **останавливает службу**;
3. снимает **резервную копию БД** `state.db.backup-<дата>` через SQLite Online Backup API (с
   учётом `-wal`), оставляет 5 последних; не удалось — установка останавливается, ничего не
   тронув (код **3**);
4. один раз выполняет «чистый старт» R12 (раздел 2.1; код **6**, если перенос не удался);
5. копирует код и `scripts/`, пишет `VERSION.json`, лаунчеры и юнит; без `check-generation.sh`
   установка останавливается (код **4**), без миграций — код **2**; без `root` — код **1**;
6. `systemctl restart wb-energy-meter`. Миграции схемы применяются при старте службы.

Самообновление (`scripts/self-update.sh`) вокруг этого делает ещё и свои шаги: скачать архив ветки
`main` (**не теги** — что в `main`, то и приедет), проверить архив и синтаксис нового кода, снять
копию рабочего каталога и данных, поставить, проверить и при неудаче откатить (раздел 4). Автоматических
проверок обновлений нет: служба ходит в сеть только по нажатию «Проверить обновления».

Состояние обновления — `GET /api/update/status` (`state`: `idle`, `starting`, `downloading`, `installing`,
`verifying`, `rolling_back`, `success`, `rolled_back`, `failed`; при ошибке `error` и `log_tail`).

### 2.1. Чистый старт R12 (разовый)

Решение R12: всё, что заведено до пилота, — тестовые данные. При обновлении `scripts/clean-start-once.sh`
**один раз** переносит `state.db` (с `-wal`, `-shm`) и `plans/` в `test-data-<дата-время>/` (ничего не
удаляется) — служба стартует с пустой базой. После переноса пишется метка
`/mnt/data/var/lib/wb-energy-meter/.clean-start-r12-done`; базу, созданную после неё, скрипт не трогает.
Отключить на контроллере с настоящими данными — до обновления записать `0` в метку:

```bash
echo 0 | tee /mnt/data/var/lib/wb-energy-meter/.clean-start-r12-done
```

## 3. Резервные копии и восстановление

Три независимые копии БД, ни одна не заменяет другую:

| Копия | Кто снимает | Что хранит | Срок |
|---|---|---|---|
| `state.db.backup-<дата>` | `install.sh`, при каждой установке и обновлении, после остановки службы | только БД | 5 последних |
| `/opt/wb-energy-meter.rollback/` | `self-update.sh`, перед установкой | весь каталог установки, `_data_backup/state.db`, `_data_backup/plans/` | до успеха обновления (при успехе удаляется) |
| `state.db.pre-rollback-<время>` | `self-update.sh`, в момент отката | БД такой, какой она была после неудачной установки | пока не удалите |

**Ручная копия без остановки службы** (Online Backup API; простое `cp` при работающей службе даёт
рваный файл, потому что часть данных лежит в `-wal`):

```bash
python3 -c 'import sqlite3,sys; s=sqlite3.connect(sys.argv[1]); d=sqlite3.connect(sys.argv[2]); s.backup(d); d.close(); s.close()' \
  /mnt/data/var/lib/wb-energy-meter/state.db \
  /mnt/data/var/lib/wb-energy-meter/state.db.manual-$(date +%Y%m%d-%H%M%S)
```

Изображения планов `plans/` копируются отдельно (`cp -a`) — в файлах БД их нет.

**Восстановить БД из копии** (сначала сохраните текущую — она может пригодиться):

```bash
systemctl stop wb-energy-meter
cd /mnt/data/var/lib/wb-energy-meter
cp -a state.db state.db.before-restore-$(date +%Y%m%d-%H%M%S)
cp -a state.db.backup-ГГГГММДД-ЧЧММСС state.db        # нужная копия
rm -f state.db-wal state.db-shm                          # хвосты от прежней базы — удалить
systemctl start wb-energy-meter
curl -s http://127.0.0.1:8080/api/v2/migration/status | python3 -m json.tool
```

Служба стартует, только если установленный код умеет читать эту БД (раздел 5). Если восстановленная
база старше кода — миграции применятся при старте. Если она новее кода (после отката на старую
версию), старт заблокирует страж поколений.

## 4. Откат обновления

`self-update.sh` откатывает установку, если после неё не прошла проверка: служба не поднялась за 90 с
(`systemctl is-active` и `/health`), версия схемы БД уменьшилась, не прошла самопроверка интерфейса
(`/api/selfcheck`) или контрольный расчёт `/api/v2/metrics/query` по первой точке. Что происходит на
каждом этапе:

| Где сорвалось | Что с системой | Статус |
|---|---|---|
| скачивание, распаковка, проверка архива, `compileall` нового кода | рабочий каталог **не тронут** | `failed` |
| резервная копия | рабочий каталог **не тронут** | `failed` |
| установка или проверка после неё | **откат** (ниже) | `rolled_back` или `failed` |
| после «успеха» | статус успеха не затирается | `success` |

**Откат** выполняется в таком порядке: (1) проверка поколений — откатываемый код должен уметь читать БД
из снимка; (2) остановка службы; (3) код, `VERSION.json` и `scripts/` из `/opt/wb-energy-meter.rollback/`;
(4) БД из снимка `_data_backup/state.db` через Online Backup API, перед этим текущая сохраняется как
`state.db.pre-rollback-<время>`, хвосты `-wal`/`-shm` удаляются; (5) каталог `plans/` из снимка;
(6) `daemon-reload`, запуск и ожидание `/health` (до 90 с). Код, БД и изображения возвращаются
**парой из одного снимка** — не «код старый, база новее».

| Положение | Откат |
|---|---|
| БД **до** первой записи через `/api/v2` (`minimum_reader_generation` нет или 1) | разрешён на любую версию; БД возвращается к снимку |
| БД **после** первой записи через `/api/v2` (`minimum_reader_generation = 2`), откатываемый код поколения **2 и выше** | разрешён; БД возвращается к снимку с поколением домена 2 |
| то же, откатываемый код поколения **ниже 2** (версии до перехода на модель v2) | **заблокирован**: статус `failed` («Откат заблокирован…»), служба остаётся на новой версии, БД и изображения не тронуты; нужен вход по SSH |
| откат выполнен, но `/health` не отвечает | `failed` («Откат не помог»): `journalctl -u wb-energy-meter -n 100` |

Поколение установленного кода — константа `__code_generation__` в `wb_energy_meter/__init__.py`;
в версии 0.25.0 она равна 3. Поведение откатов покрыто тестами `tests/test_step47_generation_guard.py` и
`tests/test_step76_rollback_triple.py` (откат до и после первой записи v2 в песочнице с настоящим
`self-update.sh`).

После отката: `GET /api/update/status` — `error` и `log_tail`; полный ход — в
`/var/log/wb-energy-meter/update.log`. Каталог `/opt/wb-energy-meter.rollback/` остаётся до следующего
обновления (он пересоздаётся).

## 5. Страж поколений и отчёт о миграции

`ExecStartPre` юнита запускает `scripts/check-generation.sh <БД> <__init__.py>` **при каждом старте** службы
(в том числе после ручного отката). Код выхода:

| Положение | Выход | Что видно |
|---|---|---|
| БД ещё нет, нет таблицы `kv`, нет ключа поколения, или поколение кода не ниже требуемого | 0 | служба стартует |
| код старше, чем требует БД (`minimum_reader_generation`) | 1 | в `journalctl -u wb-energy-meter`: «ЗАБЛОКИРОВАН ЗАПУСК: БД … требует поколение домена не ниже N» — поставьте версию, понимающую N |
| БД повреждена и поколение определить нельзя | 1 | «ЗАБЛОКИРОВАН ЗАПУСК: БД … повреждена» — восстановите из `state.db.backup-*` |

Проверка вручную:

```bash
/opt/wb-energy-meter/scripts/check-generation.sh \
  /mnt/data/var/lib/wb-energy-meter/state.db /opt/wb-energy-meter/wb_energy_meter/__init__.py; echo "код выхода: $?"
```

**Отчёт о миграции** — `GET /api/v2/migration/status`:

```bash
curl -s http://127.0.0.1:8080/api/v2/migration/status | python3 -m json.tool
```

Поля: `schema_version` (версия схемы БД), `code_generation`, `domain_model_generation` и
`minimum_reader_generation` (2 — база уже ведётся в модели v2, старая запись в реестр закрыта),
`model_v2_first_write_revision` (метка первой записи v2), `legacy_meters` (`total`, `migrated`,
`not_migrated`), `legacy_links` (`total`, `confirmed`, `unconfirmed`). На чистой базе пилота все счётчики
старых строк — 0. Перенос старых строк и связей — раздел «Перенос легаси-данных» в «Настройках» классического набора вкладок
(в наборе v2 его нет: пилот идёт с чистой базы, решения R9, R12); ход и итог видны в этом же ответе
(`not_migrated`, `unconfirmed` → 0).

## 6. Проверка нагрузки

Нагрузочный прогон **никогда** не запускают на рабочей `state.db`: он создаёт собственную базу и поднимает
отдельный экземпляр службы на другом порту (по умолчанию 18080). Методика и результаты —
[`docs/load-test-2026-09.md`](load-test-2026-09.md); цели: p95 ответа не больше 500 мс, память
процесса меньше 200 МиБ, ответ не больше 1 МБ.

```bash
cd /opt/wb-energy-meter
python3 scripts/loadtest/seed_load_db.py --db-path /tmp/loadtest.db        # 100 точек, год почасовых данных
python3 scripts/loadtest/measure.py --db /tmp/loadtest.db --minutes 10 --out /tmp/loadtest.json
rm -f /tmp/loadtest.db /tmp/loadtest.json                                    # места на eMMC мало
```

Проверить расчёт на **копии** настоящей базы: снять ручную копию (раздел 3), запустить
`measure.py --db <копия>` и удалить копию. Само измерение на работающей службе — только запросы чтения
(`GET` и расчётные `POST`, которые ничего не пишут), вне часов, когда учёт важен.

## 7. Типичные неисправности

| Симптом | Причина | Что делать |
|---|---|---|
| Служба не стартует, в журнале «ЗАБЛОКИРОВАН ЗАПУСК» | код старше БД или БД повреждена (раздел 5) | поставить свежую версию либо восстановить БД из `state.db.backup-*` (раздел 3) |
| Страница белая, «не загрузились файлы» | интерфейс не отдаёт часть файлов | `curl -s http://127.0.0.1:8080/api/selfcheck` назовёт файлы; переустановить |
| Плашка «Служба обновлена до X — перезагрузите страницу» | вкладка открыта на старой версии | нажать «Перезагрузить» в плашке либо Ctrl+F5 |
| Все приборы «нет связи» | MQTT-брокер недоступен или нет сообщений дольше `status.no_connection_timeout_s` | `systemctl status mosquitto`; `curl -s http://127.0.0.1:8080/api/status` — смотреть `mqtt.connected` |
| Отчёты пустые, нет почасовых данных | `wb-mqtt-db` не пишет историю нужных каналов | «Настройки» → «Эмулятор» → «Проверить историю»; проверить `wb-mqtt-db` |
| Прибор виден в MQTT, но не в учёте | у него нет точки учёта | «Структура» → «Приборы без точки учёта» → «+ Счётчик → куда?» |
| Обновление ушло в `rolled_back` | новая версия не прошла проверку | `GET /api/update/status` (`error`, `log_tail`), `update.log`; повторно не нажимать, пока причина не ясна |
| Обновление в `failed`, «Откат заблокирован» | БД уже ведётся в модели v2, откатываемый код её не читает | вход по SSH; разбор причины по `journalctl`; БД не трогать |
| Запись через старый маршрут: `409 moved_to_v2` | база на модели v2, `/api/registry/*` для записи закрыт | пользоваться интерфейсом v2 (`docs/api-v2.md`, раздел 3) |
| `wb-energy-meter-cli …` завершился кодом 3 | то же для командной строки | то же; диагностические команды (`meter list`, `consumption`, …) работают |
| «Обзор» или отчёт отвечает 400 «Неизвестный часовой пояс», поле `timezone` | период задан строкой-датой, а на контроллере нет базы часовых поясов (`/usr/share/zoneinfo`) либо браузер прислал имя, которого в ней нет (строка-дата читается в поясе запроса, `docs/api-v2.md`, раздел 1.4) | `ls /usr/share/zoneinfo/Europe/Moscow`; если файла нет — `apt install tzdata`; скрипту достаточно прислать `from`/`to` в unix-секундах — пояс тогда не нужен |
| Нет места при обновлении | мало места на `/mnt/data` или `/opt` | `df -h /mnt/data /opt`; убрать `test-data-*`, старые `state.db.pre-rollback-*`, `state.db.manual-*` |
| В «Обзоре» баннер «Включён эмулятор» | включён эмулятор счётчиков, цифры с ним не настоящие | «Настройки» → «Эмулятор счётчиков» → выключить; архивировать его точки |

## 8. Известные ограничения

* **Нет аутентификации.** Любой, кто достучится до порта, может читать данные, менять конфигурацию и
  нажать «Обновить сейчас». Все JSON-ответы API отдают `Access-Control-Allow-Origin: *`, заголовок
  `Origin` не проверяется (решение R1). Меры — `http.host: 127.0.0.1` и доступ через SSH-туннель либо
  `update.allow_from_ui: false` (README, «Обновление»).
* **История топологии** (журнал изменений, режим `as_was`) ведётся с 0.22.0; раньше — только текущее
  состояние, расчёты за такой период помечаются `assumed_legacy` (решение R7).
* **Классический интерфейс и «План» v1/v2** пока доступны переключателем набора вкладок; их прячут в
  1.0.0 после пилота (решения R4, R19), код удаляют отдельной чисткой после месяца работы на контроллере
  (решения R2, R5).
  Старые маршруты чтения `GET /api/registry/*` остаются до той же чистки; запись в них закрыта.
* **Обновление — из ветки `main`**, не из тегов; тег и GitHub Release появятся только у 1.0.0.
* **Нагрузка** проверена в песочнице на 100 точках (`docs/load-test-2026-09.md`); измерение на самом
  контроллере проводится отдельно и фиксируется в отчёте партии.
