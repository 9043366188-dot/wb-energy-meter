# Проектная заметка: эмулятор счётчиков (П12, выпуск 0.23.1)

Решение Кира — R17: на контроллере без нагрузки нечем проверять учёт, поэтому
сервис получает виртуальные WB-MAP3E в том же брокере. Заметка написана **до
кода** (как `docs/design-phase-aggregates.md`) и фиксирует выбор: модель
счётчика, хранение состояния, что и когда стирается. Код следует ей;
расхождения — только с правкой этого файла в том же PR.

## 1. Границы

Эмулятор — часть сервиса (`wb_energy_meter/emulator.py`), **по умолчанию
выключен**. Он публикует топики так, как публикует драйвер `wb-mqtt-serial`, и
больше ничего: учёт, агрегатор, отчёты и интерфейс видят обычные приборы и не
знают, что они виртуальные, кроме меток «эмулятор» (§8). Историю пишет
настоящий `wb-mqtt-db` (CODING_STANDARDS: сырую телеметрию не дублируем).
Новых миграций нет (R7).

## 2. Модель счётчика: «якорь + чистая функция»

Накопитель — не переменная, обновляемая каждые 5 с, а **функция времени**:

`E_фаза(t) = anchor_kwh[фаза] + ∫ P_фаза(τ) dτ / 3600` по `τ ∈ [anchor_ts, t]`.

`P_фаза` — кусочно-постоянная по минутам: `kw[фаза] × профиль(минута суток) ×
(1 + шум)`, шум — детерминированный хеш `(прибор, фаза, номер минуты)`, без
`random`. Профиль `flat` даёт 1; `daily` — ночью ≈ 0,3, днём до 1 (день >
ночь). Следствия: (а) **перезапуск не сбрасывает счётчик** — после старта
значение считается из сохранённого якоря и совпадает с тем, что было бы без
остановки (счётчик «работал», пока сервис стоял; в истории `wb-mqtt-db`
остаётся дыра, как у настоящего прибора при пропавшей связи); (б) на диск
пишется не каждый тик, а только якорь — при создании, при правке/неисправности
и раз в час (экономия флеш-памяти контроллера); (в) тесты считают ожидаемое
значение независимо от публикации. Любая правка настроек сначала **фиксирует
якоря всех приборов на «сейчас» по старым настройкам**, потом применяет
правку — прошлое не переписывается.

**Ввод.** Прибор с ролью «ввод» имеет список `sources` (номера эмуляторов) и
`pct`: `P_ввод,фаза = (1 + pct/100) × Σ P_источника,фаза` — сумма выбранных
плюс процент потерь/неучтённого. Нет собственных `kw`; у ввода тот же якорь и
те же неисправности.

## 3. Что публикуется

Устройство `emu-map3e-N`, название «Эмулятор N» (пользователь может
переименовать; слово «эмулятор» из названия не пропадает, §8), `Serial` =
`EMU-<N>-<поколение>`, в `meta` `driver = wb-energy-meter-emulator`. Каналы
как у WB-MAP3E: `Urms/Irms/P/AP energy L1–L3`, `Total P`, `Total AP energy`,
`Frequency`, `Serial`, `Uptime`, метаданные каналов (`type`, `readonly`,
`order`). Публикация retained, QoS 1, как у драйвера, тик 5 с; топик
пропускается, если округлённое значение не изменилось (как драйвер — на
изменение); `Uptime` меняется каждый тик, поэтому прибор «живой». Свой
paho-клиент (`loop_start`, отдельный от `MqttService`), публикатор, часы, kv и
проба истории подменяются в тестах.

## 4. Сценарии

| Сценарий | Как задаётся | Что происходит |
|---|---|---|
| Суточный профиль | `profile = daily` | день > ночи, шум, мощность у каждого прибора своя |
| Разные фазы | `kw = [L1, L2, L3]` | каждая фаза со своей мощностью — для режима «по фазам» |
| Перекос щита | роль «ввод» + `sources` + `pct` | ввод = сумма выбранных + % |
| Сброс | кнопка «сброс» | якорь `anchor_kwh = 0`, серийный тот же |
| Замена | кнопка «замена» | якорь 0, новое поколение `Serial`, `Uptime` с нуля |
| Потеря связи N мин | кнопка | значения не публикуются, на каналах `meta/error = r` (статус «ошибка прибора»); по окончании ошибка снимается; счётчик «считал» всё время |
| Редкие показания N ч | кнопка | числовые каналы раз в 30–60 мин (детерминированно), `Uptime` как обычно |

Каждое действие пишется в журнал со временем (`kv`, последние 200 записей).

## 5. Состояние: kv, не таблица

`kv` `emulator.state` (JSON: `enabled`, `enabled_at`, `next_n`, приборы с
настройками, якорем и активными неисправностями, состояние пробы истории) и
`emulator.journal`. Таблица не нужна: приборов единицы, выборок по полям нет,
состояние переписывается целиком, а новая миграция запрещена (R7). Номера
приборов не переиспользуются (`next_n` растёт) — устройство `emu-map3e-N`
никогда не меняет смысл.

## 6. Вход в сервис

`MqttService` принимает префикс `emu-` вдобавок к `device_prefix` (иначе
фильтр отбросит виртуальные приборы). Реестр получает `MeterRegistry.forget()`.
Метка «эмулятор» вычисляется по префиксу `emu-` (`is_emulator_device`), хранить
её не нужно.

## 7. Выключение и удаление

Выключение: публикация прекращается; **retained-топики стираются** (пустой
retained по каждому топику прибора, дожидаемся доставки); в реестре
забываются приборы без привязки (`meters` не знает их — иначе остались бы в
списках «+ Счётчик»). **Точки, привязанные к эмулятору, остаются** — выключенный
прибор уходит в «нет связи» штатно. Кнопка «Архивировать точки эмулятора»
(с подтверждением) архивирует точки, привязанные к `emu-…`, обычным путём
архивации точки. Удаление одного прибора стирает его топики так же. Включение
повторно продолжает счётчики с якоря.

## 8. Метки «эмулятор»

API отдаёт `is_emulator` рядом с устройством: реестр и «неподключённые»,
занятость приборов в структуре, снимок точки, строки «Обзора» и отчёта.
Интерфейс показывает значок «эмулятор» в пикерах прибора, карточках узла и
точки, «Структуре», «Обзоре» и отчётах; CSV отчёта получает колонку
«Эмулятор» и строку-предупреждение. Баннер в «Обзоре» — «Включён эмулятор: N
виртуальных приборов — цифры с ними не настоящие» — пока сервис включён.

## 9. Проба истории `wb-mqtt-db`

Через 12 минут после включения (и далее раз в 10 минут, пока ответа нет)
сервис по RPC `get_values` (`ver=1`) спрашивает у `wb-mqtt-db` историю одного
канала эмулятора. Есть точки — состояние `ok`, проба больше не повторяется.
Точек нет — `missing` и предупреждение «wb-mqtt-db не пишет историю эмулятора
— отчёты будут пустыми; проверьте настройки wb-mqtt-db (группы каналов)».
Ошибка самого RPC — `error` («не удалось спросить wb-mqtt-db»), не
`missing`: «пусто» и «не спросили» не смешиваются. Запрос — в фоновом потоке
эмулятора, не в MQTT-колбэке.

## 10. API (`/api/v2/emulator…`, ошибки через `_err`)

`GET` состояние (живые значения, журнал, история); `POST …/enabled`;
`POST …/devices`, `PATCH`/`DELETE …/devices/<n>`; `POST …/devices/preset`
(типовой набор: ввод и три нагрузки); `POST …/devices/<n>/fault`;
`POST …/archive-points` (`confirm: true`); `POST …/probe-history`. `PATCH`
без изменяемых полей — `400`. Правки приборов обновляют и kv, и работающий
сервис (CODING_STANDARDS: обе копии).

## 11. Проверка

Тесты: модуль (чистая функция, перезапуск, сценарии, стирание топиков, проба),
API, браузер (включить → приборы с меткой в «+ Счётчик» → схема Ввод→Щит→
нагрузки → «по фазам» → баланс щита = заданный % → «сброс» → флаг в отчёте →
выключить → топики стёрты), репетиция пилота на новом модуле. На контроллере
(R17) после выпуска: включить эмулятор, собрать свою схему на плане
«Эмулятор — проверки агента» **только** из `emu-…`, не выключать без причины —
неделя данных нужна для замера A40.
