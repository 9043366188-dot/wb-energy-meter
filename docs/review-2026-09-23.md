## 1. КРИТИЧНО: небаланс на «Обзоре» считается не по той модели

`api_v2.py::v2_overview_summary` (≈стр. 1860–1920):

```
object_total  = sum_points(первичные точки линий из узлов kind=source)   # по схеме — верно
branches      = корневые учётные группы (group_repo.list_children(None))
imbalance     = object_total − Σ branches                                  # по группам — неверно
```

Итог объекта берётся из электрической схемы, а «выходы» баланса из учётных
групп. По ТЗ §3 и §5.2 это разные оси: группы отвечают за отнесение
расхода, а баланс считается по электрической границе («поиск
останавливается на первом измерении в каждой ветви», неизмеренные ветви
выдаются через `unmetered_branch_ids`/`boundary_coverage`).

Воспроизведение (`review-repro/repro_imbalance.py`): ввод 100 → ЩР-1 →
две отходящие линии со счётчиками 60 и 30:

| Сценарий | Показывает «Обзор» | Верно по ТЗ |
|---|---|---|
| Схема собрана в «Плане v3», групп нет | **небаланс 100 кВт·ч (100 %)** | 10 (10 %) |
| Есть группа «Цех» = {60, 30} | 10 (10 %) | 10 (10 %) |
| + группа «Арендатор А» = {60} (ТЗ §4.4 это разрешает) | **−50 (−50 %)** | 10 (10 %) |

Обязательный e2e `test_step39` этого не ловит: он сам создаёт группу
«Нагрузка цеха» со всеми потребителями, то есть проверяет только тот
случай, где числа совпадают случайно.

**Что сделать:**
- Выводить баланс из топологии. Для узла с измеренной входящей линией:
  вход минус первые измерения вниз по каждой отходящей ветви.
  Неизмеренные ветви перечислять отдельно, признак покрытия отдавать в
  ответе. Небаланс объекта = тот же расчёт от вводов.
- Группы показывать отдельным блоком «Распределение по группам»,
  без вычитания из итога (строки групп могут пересекаться).
- Тесты: «групп нет», «группы пересекаются», «ветвь без счётчика»,
  «счётчик глубже первого уровня» (не вычитать дважды).
- Бонус, почти бесплатный на готовой топологии: **баланс каждого щита в
  карточке узла «Плана v3»**: «вход 100, отходящие 90, не измерено:
  Розетки, небаланс 10 (10 %)». Для энергетика это главная функция
  продукта. Отдельная сущность `balance_scopes` для этого не нужна.

## 2. КРИТИЧНО: «План v3» на чистой базе. Первый узел не ставится

Воспроизведено в Chromium (`review-repro/planv3_browser_smoke.py`):

1. После «Создать план» карта открывается с `zoom = −4` (minZoom), и холст
   2000×1200 выглядит точкой в центре. Клик по карте с «+ Узел» даёт тост
   «Точка вне границ плана», узел не создаётся. Причина: `fitBounds` в
   `_planV3RenderBase` вызывается, пока контейнер ещё скрыт (`x-show`,
   размер 0). Это та самая грабля Leaflet, которая уже описана в AGENTS.md.
   После перезагрузки страницы картина та же.
2. Каждое действие (узел, линия, перетаскивание, отходящая линия)
   вызывает `selectPlanV3()` → `planV3CancelTool()` + `closeInspector()` +
   `_planV3RenderBase()` → `fitBounds`. Масштаб и положение сбрасываются
   после каждого клика: пользователь приблизил участок, поставил узел, и
   карту отбросило. В Плане v2 ровно это уже решали разделением
   `_planV2RenderBase`/`_planV2RenderItems`.
3. У маркеров узлов нет подписей (`bindTooltip`/label), на карте только
   цветные кружки. Чтобы понять, где какой щит, приходится кликать.

Лечится разделением «база только при смене плана / элементы при каждом
изменении», `invalidateSize()` + `fitBounds` после показа контейнера и
постоянными подписями.

## 4. ВАЖНО: две несовместимые модели питания живут одновременно

- Простой режим (0.16.0) — «Это ввод»/«Питается от» на карточке точки
  в «Структуре». Он заводит служебные узлы `sm-pt-<id>`/`sm-src-<id>`, а
  выпадающий список молча заменяет входящую линию.
- «План v3» (0.17.0) — узлы на карте и счётчик на линии; второй источник
  питания он отклоняет.

ТЗ партии 6 объявило простой режим отменённым, но реализованный код
остался в UI («Подробная схема: выкл» по умолчанию показывает именно его).
`simple_mode_service.describe_power_supply` ищет питание только через свои
`sm-*` узлы. Поэтому точка, поставленная на линию в «Плане v3», в
«Структуре» выглядит «без питания», а колонка «Чего не хватает» врёт.

**Что сделать:** сейчас скрыть UI простого режима. Потом удалить его и
перевести существующие `sm-*` узлы в обычные узлы (если такие есть на
контроллере). Правило надзора на будущее: если задание отменяют посреди
партии, в новом задании явно писать, что делать с уже сделанной частью.

## 5. Процесс и надзор

1. **Браузер в DoD.** С 0.11 каждая партия заканчивается фразой «в
   браузере не открывалось», баги находит Кир и они уходят в следующую
   партию. Нужен Playwright-сценарий в песочнице агента: чистая БД →
   сценарий чеклиста → скриншоты обеих тем → 0 ошибок консоли. Чеклист
   `docs/browser-checklist-plan-v3.md` (35 шагов) постепенно переводить в
   автотест. Для реального контроллера `192.168.10.212` у надзорной
   сессии есть Claude in Chrome.
2. **Приёмка по доказательствам.** Каждый пункт «Критериев приёмки»
   закрывать ссылкой на файл:строку, имя теста или скриншот, а не
   галочкой агента. Пункты 1–3 этого ревью прошли бы такую приёмку только
   как «не выполнено».
3. **Партия 4 отложена дважды** (журнал изменений, «как было», нагрузка
   100 точек/10 планов/3 клиента). Нагрузочную часть нужно сделать до
   пилота на реальном WB 8 (лимит 256 МБ): `index.html` весит 458 КБ без
   gzip и кеш-заголовков, а под нагрузкой ничего не мерили. В песочнице
   RSS в простое 55 МБ.
4. **Проверки, которые агент может делать сам:** Python 3.9 (`uv venv -p
   3.9`) и mosquitto (`apt-get install mosquitto`). Оговорки «не
   проверено на 3.9» и «3 теста требуют mosquitto» больше не нужны.
5. **Меньше партий «плюс экран».** За 6 дней добавились «Обзор»,
   «Отчёты v2», «Структура», «План v2», «План v3», простой режим,
   «Подробная схема», переключатель наборов. Не убрано ничего.

## 6. Техдолг (по убыванию пользы)

1. **`index.html` — 458 КБ, ≈7000 строк JS в одном `app()`** (≈310 полей,
   ≈360 методов), три версии плана с тремя копиями конвертации координат и
   рисования Geoman. Повторяющиеся классы багов (два корня у `x-if`,
   `fitBounds` в скрытом контейнере, незакрытый `<template>`) — следствие
   этого. Без сборщика и без нарушения §9.1 ТЗ JS можно разнести в
   `static/js/<экран>.js` (Alpine.data или миксины, объединяемые в
   `app()`) и общий `leaflet-helpers.js`. `/api/selfcheck` уже умеет
   проверять файлы, подключённые из `index.html`.
2. **`api_v2.py` — 2636 строк**, расчёт обзора/отчётов прямо в
   обработчиках (`v2_overview_summary` 177 строк, `v2_reports_query` 230).
   Вынести в `overview_service.py`/`reports_service.py`. Тогда расчёт
   тестируется без HTTP, и «один расчёт на все экраны» (A43) держится
   структурно. Пункт 1 правится как раз там.
3. **Безопасность** (для стенда допустимо, для объекта нет):
   аутентификации нет, `0.0.0.0:8080`, в примере конфига
   `update.allow_from_ui: true`. Все JSON-ответы идут с
   `Access-Control-Allow-Origin: *` (`api.py::json_response`), поэтому
   любая страница, открытая у оператора в той же сети, может читать весь
   API. Multipart-маршруты загрузки планов принимают кросс-сайтовые POST
   без preflight. Минимум: убрать `ACAO: *`, в `before_request` для
   мутирующих методов проверять Origin/Host, пароль или токен на
   изменения конфигурации.
4. **Старые хвосты:** `scripts/install.sh` делает `cp -a` БД до остановки
   сервиса (WAL; известно с 16.09); `ExecStartPre`-гард поколений (§11.2)
   не сделан; причина `no_data` у `wb-map3e_49` не найдена (проверить,
   актуально ли).
5. **CI:** 79 строк `python tests/...` вручную в двух job, «забыли
   зарегистрировать тест» уже случалось. Нужен один `tests/run_all.py`
   (обход `test_step*.py`) и одна строка в CI.
6. **Документация для агентов:** AGENTS.md 64 КБ (из них раздел «Что в
   работе» — 220 строк повествования), CHANGELOG 97 КБ. Каждая сессия
   тратит десятки тысяч токенов только на вход. AGENTS.md стоит оставить
   под правила и грабли, текущий статус вынести в `docs/status.md`
   таблицей, историю держать в CHANGELOG.
7. **Мелочи UX:** пустой «Обзор» советует «создайте точки на вкладке
   „Настройки“» (устарело). «Требует внимания: 0», когда обнаружены 3
   прибора без точек учёта. Первого запуска по шагам (§8.5) нет.
   `viewport=1100`.

## 7. Концепция

- **Направление верное.** «План v3» — это §4.3 ТЗ (радиальная сеть,
  счётчик на линии), вынесенный прямо на карту. Энергетик думает именно
  так: щиты, линии, счётчики на линиях. Предлагаю официально сделать схему
  ядром: из неё выводятся итог объекта и балансы щитов, группы остаются
  наложением «кому отнести расход» (арендаторы, цеха), места — текстовым
  атрибутом узла.
- **Большое ТЗ тяжёлое для 100 точек на контроллере:** версионирование
  всего, ревизии конфигурации, `as_was`/`current`, поколения, отдельная
  сущность границ баланса. Построенное и покрытое тестами оставить, но UI
  под тяжёлые функции пока не строить. `balance_scopes` как ручная
  сущность становится лишней, если балансы щитов выводятся из топологии.
- **Целевой набор экранов:** Обзор / Схема (План v3) / Отчёты / Настройки,
  плюс «Структура» как список и поиск. План v2 убрать после прохождения
  чеклиста v3, простой режим убрать сейчас, классический интерфейс —
  после паритета отчётов (это совпадает с «Точкой №1» Кира).
- **Веха «пилот» вместо новых партий-функций:** реальный контроллер, ≥3
  счётчика, один щит. Перенос → схема в «Плане v3» → «Обзор» и баланс щита
  совпадают с ручным расчётом → неделя реальных данных → CSV. До прохождения
  вехи новые функции не брать.
