# План миграции и отката на модель v2

Черновик этапа A (`docs/TZ-metering-architecture-dashboard.md`, §11 «Миграция
и откат»). Переводит требования ТЗ в конкретные шаги для *этого* дерева:
`db.py`, `scripts/self-update.sh`, `repo.py::KvRepo`, реальный путь БД
`Database.DEFAULT_DB_PATH = /mnt/data/var/lib/wb-energy-meter/state.db`.
Не является реализацией — реализуется в этапах B (схема/данные) и F
(self-update/генерации).

## 0. Что уже сегодня не соответствует требованиям ТЗ (проверено кодом)

- **Миграции не атомарны.** `Database._apply_migrations()` (`db.py:106-126`)
  вызывает `self.conn().executescript(sql)` на соединении, открытом с
  `isolation_level=None` (`db.py:44`, автокоммит) — без явного
  `BEGIN`/`COMMIT`/`ROLLBACK`. При падении посередине файла часть DDL уже
  закоммичена, а строка в `schema_migrations` не появляется: повторный
  запуск падает на «table already exists». Воспроизведено тестом
  `tests/test_step13_legacy_scenarios.py::test_migration_apply_is_not_atomic`.
- **`self-update.sh` не бэкапит БД.** `backup_current()`
  (`scripts/self-update.sh:261`) копирует только `$INSTALL_DIR` (код);
  `state.db` лежит отдельно (`/mnt/data/var/lib/...`) и в откат не входит.
  Откат кода после неудачного релиза с новой схемой БД сегодня физически
  не восстановит совместимую пару «код + БД».
- **Нет протокола версии домена.** `kv`-таблица уже есть и используется
  (`repo.py::KvRepo`, пример — `PENDING_RESTART_KEY` в `api.py:1050-1069`),
  но нет `domain_model_generation`/`minimum_reader_generation`/
  `model_v2_first_write_revision` — заводится в этапе B.

## 1. Инвентаризация и контрольные результаты (до любых изменений схемы)

На тестовом контроллере/копии `192.168.10.212`:

1. `Database.stats()` (`db.py`, уже существует) + прямые запросы: полный
   список `meters` (включая `enabled=0`), `meter_groups` (с `parent_id`,
   пусть и неиспользуемым), `period_aggregates` по всем счётчикам,
   `site_plans`/`plan_zones`/`plan_links`.
2. `PRAGMA integrity_check; PRAGMA foreign_key_check;` — зафиксировать
   результат (ожидается пусто/`ok`).
3. Снять контрольные результаты текущих отчётов (`/api/reports/balance`,
   `/api/reports/consumption` и т. п.) на копии БД — до миграции и сразу
   после (см. §4) числа не по всем полям обязаны совпасть (семантика
   меняется, ТЗ §2), но список счётчиков/сумм должен быть объясним построчно.

## 2. Резервная копия

- SQLite: **Online Backup API** (`sqlite3.Connection.backup(...)` в Python —
  согласованный снимок даже при открытых WAL-писателях; не копировать
  файл `state.db`+`-wal`+`-shm` напрямую).
- Каталог изображений плана (`wb_energy_meter/plan_repo.py`, файлы на
  диске) — отдельная копия с manifest: список файлов + размер + sha256.
- Обе копии кладутся рядом с существующим `$ROLLBACK_DIR` конвенции
  `self-update.sh`, но **отдельно от кода** — код-бэкап уже есть
  (`backup_current()`), БД/изображения — новый шаг, добавляемый в этап F.

## 3. Прогон на копии, затем — на рабочей БД

1. Применить новую миграцию (см. §4) к копии `state.db` из §2.
2. Прогнать `PRAGMA integrity_check`/`foreign_key_check` и весь набор
   `tests/test_step*.py` против копии.
3. Только после зелёного прогона на копии — реальная миграция, при
   остановленных фоновых записях (`background.py::BackgroundTasks`,
   MQTT-подписчик) и закрытом редактировании UI (feature-flag «только
   чтение» до этапа F, см. §7).

## 4. Атомарный протокол миграции (закрывает дефект §0)

Новый метод заменяет прямой `executescript` для файлов версии ≥5:

```python
def _apply_migration_atomic(self, version, name, sql, path):
    conn = self.conn()
    conn.execute("BEGIN IMMEDIATE")
    try:
        conn.executescript(sql)  # DDL/DML миграции 005+
        conn.execute(
            "INSERT INTO schema_migrations (version, name, applied_at) "
            "VALUES (?, ?, strftime('%s','now'))", (version, name))
        conn.execute("COMMIT")
    except sqlite3.Error:
        conn.execute("ROLLBACK")
        raise
```

Замечания:

- `executescript()` сам по себе коммитит неявные транзакции внутри
  скрипта на некоторых версиях SQLite/Python — миграции 005+ не должны
  содержать `BEGIN`/`COMMIT` внутри своего `.sql`; транзакцию держит
  вызывающий код.
- Существующие миграции 001-004 **не переписываются** — они уже применены
  на объекте, менять историю задним числом опаснее, чем оставить как есть.
  Новый метод используется только начиная с версии 5.
- INSERT в `schema_migrations` — в той же транзакции, что и DDL: либо оба,
  либо ни одного. Это и есть «половина структуры уже новая» из ТЗ §11.1,
  закрытая буквально.
- При падении: файл БД остаётся в состоянии ДО этой миграции (ROLLBACK),
  следующий запуск видит тот же `current_schema_version()` и просто
  повторяет попытку — идемпотентно, без ручного вмешательства.
- Для фонового файла (изображения плана, §11.1.10 ТЗ): сначала временный
  файл → fsync → атомарный `rename()` в неизменяемое имя версии → и
  только после этого commit строки БД, ссылающейся на готовый файл
  (симметрично протоколу выше, но на уровне файловой системы).

## 5. Перенос данных (в рамках миграции 005+, этап B/C)

Порядок из ТЗ §11.1, привязанный к текущим сущностям:

1. Каждый `meters.id` → один новый `metering_point` + `point_binding`
   на канал `Total AP energy`, с сохранением `enabled`, `display_name`→`name`,
   `notes`→`installation_note`, `role`→подсказка мастеру границ (не
   топология).
2. `meter_groups`+`meters.group_id` → новая `group`/`group_membership`
   через `migration_map`; `parent_id` в `meter_groups` сегодня всегда
   `NULL` (не используется приложением) — переносить как есть, не
   выдумывать историю иерархии.
3. `plan_zones` (ссылаются на `meter_groups`) → представления групп на
   новых `plan_items`; `plan_links` → `legacy_annotation/needs_review` с
   исходными `from_zone_id/to_zone_id/source_meter_id`, БЕЗ автоматического
   превышения в питающую связь (ТЗ §2, строка про §31.5).
4. `period_aggregates` не переносятся построчно в новый формат — остаются
   легаси-данными существующего канала; новый формат агрегатов (§6.2 ТЗ,
   ключ с `measurement_epoch_id`) пишется только для новых измерений.

Каждый шаг — свой `migration_map` (старый ID → новый ID, версия миграции),
таблица заводится в той же миграции 005.

## 6. Идемпотентность и повторный запуск

- Проверка перед стартом: `SELECT MAX(version) FROM schema_migrations`;
  версии ≤ current пропускаются (уже работает, `db.py:118`).
- Для миграций 005+ дополнительно: перед вставкой в `migration_map`
  проверять `INSERT OR IGNORE`/уникальный индекс `(legacy_table, legacy_id)`,
  чтобы повторный прогон после сбоя на шаге 5 не создавал дублей —
  атомарность §4 гарантирует, что до `COMMIT` миграция не считается
  применённой, но перенос данных (DML) внутри одной миграции должен сам
  быть устойчив к повтору, если разбит на несколько файлов.

## 7. Переключение и откат (закрывает дефект §0 про self-update.sh)

1. До первой публикации новой топологии — старый UI/API работают как
   сейчас; новые таблицы существуют, но не являются источником отчётов.
2. `kv`-ключи (через существующий `KvRepo`, `repo.py:358`), заводятся в
   этапе B:
   - `domain_model_generation` (int) — по умолчанию `1` для БД без ключа
     (легаси-manifest без объявления generation);
   - `minimum_reader_generation` (int) — какой код умеет читать эту БД;
   - `model_v2_first_write_revision` — пишется **в той же транзакции**,
     что первая предметная/геометрическая запись через `/api/v2`; после
     этого момента откат к дореформенному коду для этой БД запрещён.
3. `scripts/self-update.sh` расширяется шагом проверки матрицы
   **до** `attempt_rollback()` (`scripts/self-update.sh:386`):
   старая схема → только совместимый (дореформенный) код; новая схема без
   `model_v2_first_write_revision` → откат на сохранённый backup
   разрешён; новая схема с `model_v2_first_write_revision` → откат
   блокируется, код первого поколения не запускается на этой БД.
   Проверка матрицы дублируется отдельным startup guard вне
   Python-пакета (`ExecStartPre`), чтобы отказ уже после установки не
   допустил старый код к новым связям — как и написано в ТЗ §11.2.
4. `backup_current()` (`scripts/self-update.sh:261`) расширяется
   резервным копированием `state.db` (через Online Backup API, не `cp`,
   т.к. WAL) и каталога изображений плана — сегодня бэкапится только код.
5. `verify_after_install()` (`scripts/self-update.sh:367`) дополняется
   проверкой версии схемы и контрольным расчётом на одной существующей
   точке (не только `/api/selfcheck.ok`, как сейчас).
