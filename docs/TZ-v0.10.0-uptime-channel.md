# ТЗ v0.10.0 — контроль канала Uptime и правка конфига wb-mqtt-serial

**Проект:** `wb-energy-meter` (Wiren Board 8.x + WB-MAP3E)
**Базовая версия:** 0.9.0
**Целевая версия:** 0.10.0
**Рабочий каталог:** `C:\wb-energy-meter-repo\wb-energy-meter`
**Дата составления:** 09.09.2026

---

## 1. Задача и её предыстория

WB-MAP3E fw2 работает в event-driven режиме: пока нагрузка не меняется,
счётчик молчит часами. Отличить «нет связи» от «нет нагрузки» нельзя.
Лечится включением канала **Uptime** — он растёт каждые 2 секунды и служит
пульсом. Включается галочкой в Device Manager: HW Info → Uptime →
«in queue order».

Проблема не в том, что галочку трудно поставить. Проблема в том, что про
неё забывают, а потом полдня выясняют, почему исправный счётчик показывает
«нет связи». Поэтому основная ценность здесь — **диагностика**, а
автоматическая правка конфига — приятное дополнение, которое по умолчанию
выключено.

Решения заказчика:

- **Диагностика — всегда**, правка конфига — **за флагом**, по умолчанию
  выключенным.
- **Изменения накапливаются**, драйвер перезапускается **один раз по
  отдельной кнопке**, а не после каждого счётчика.

## 2. Как это устроено в Wiren Board (проверено по README драйвера)

Источник: [wb-mqtt-serial/README.md](https://github.com/wirenboard/wb-mqtt-serial/blob/master/README.md).

- Галочка «in queue order» — это свойство канала **`"enabled": true`**.
  Цитата из README: «Включает канал в цикл опроса, по умолчанию - true».
- Конфиг устройства и его шаблон **сливаются по имени канала**, причём
  «значения свойств из определения устройства (в файле конфигурации) имеют
  преимущество». Значит достаточно дописать устройству в массив `channels`
  запись `{"name": "Uptime", "enabled": true}` — остальные свойства канала
  подтянутся из шаблона.
- Идентификатор устройства в MQTT — поле `"id"`; если не задано, берётся
  «из шаблона с добавлением slave_id: `deviceID + "_" + slave_id`».
  Наш `wb-map3e_21` — это ровно такой вычисленный id.
- **RPC на изменение конфигурации у драйвера нет.** Есть RPC на чтение
  портов (`ports/List`), сканирование и опрос регистров — на запись
  конфигурации ничего. Единственный путь: править
  `/etc/wb-mqtt-serial.conf` и делать `systemctl restart wb-mqtt-serial`.
- **`conf.d` не спасает**: `/etc/wb-mqtt-serial.conf.d/templates` — только
  для пользовательских шаблонов, класть туда куски конфигурации устройств
  нельзя.

### Чем это опасно

`/etc/wb-mqtt-serial.conf` — не наш файл. В нём описаны **все** устройства
контроллера: реле, датчики, приводы. Давая сервису учёта право записи в
него, мы даём ему возможность уронить весь ввод-вывод объекта, а не только
учёт электроэнергии. Отсюда все требования §5.

Плюс перезапуск драйвера прерывает опрос **всех** устройств на несколько
секунд. И тот же файл редактирует веб-интерфейс WB — возможна гонка.

## 3. Слой 1 — диагностика (включена всегда, ничего не пишет)

### 3.1. Два независимых источника правды

Оба нужны, потому что по отдельности каждый врёт.

**А. Чтение конфига — только на чтение.** Открыть
`/etc/wb-mqtt-serial.conf`, найти устройство, посмотреть, есть ли у него в
`channels` запись `Uptime` и не выставлено ли ей `"enabled": false`.
Это отвечает на вопрос «стоит ли галочка».

**Б. Наблюдение по MQTT.** В `MeterState.controls` уже есть всё нужное:
`update_count`, `last_update_ts`, `first_seen_ts`. Это отвечает на вопрос
«идут ли данные на самом деле».

### 3.2. Итоговый вердикт

| Состояние | Условие | Что показать |
|---|---|---|
| `ok` | канал обновлялся ≥ 2 раз и `last_update_ts` свежее 60 с | Всё в порядке |
| `disabled` | в конфиге у канала `"enabled": false` | Галочка не стоит — вот инструкция и кнопка |
| `not_in_config` | устройство в конфиге найдено, канала `Uptime` в нём нет (значит берётся из шаблона) и данные не идут | То же, что `disabled` |
| `stale` | в конфиге включён, но данных нет дольше 60 с | Галочка стоит, но данные не приходят — это уже связь с устройством, а не конфиг |
| `device_not_found` | устройство в конфиге не нашлось | Счётчик опрашивается не через этот конфиг либо id не совпал; правку не предлагать |
| `unknown` | конфиг не прочитался (нет файла, нет прав, не JSON) | Сказать честно, что проверить не удалось, и почему |

**Важно:** `unknown` — это не ошибка интерфейса. Файл может быть недоступен
на машине разработчика, в тестах, в контейнере. Никаких 500, спокойный
статус.

### 3.3. Сопоставление счётчика с устройством в конфиге

Порядок попыток, строго:

1. Устройство с явным `"id" == device_id` — точное совпадение.
2. Иначе вычислить id по правилу `<deviceID шаблона>_<slave_id>`. Префикс
   брать из шаблонов: прочитать `/usr/share/wb-mqtt-serial/templates/` и
   `/etc/wb-mqtt-serial.conf.d/templates/`, построить карту
   `device_type → префикс id`. Сравнить с `device_id`.
3. Если не нашлось или **нашлось больше одного** — вернуть
   `device_not_found` и **не гадать**. Лучше попросить человека, чем
   отредактировать чужое устройство.

Необязательный, но полезный перекрёстный контроль: RPC
`/rpc/v1/wb-mqtt-serial/ports/List/<client_id>` (драйвер от 2.271.0)
возвращает конфигурацию, с которой реально запущен опрос, — это
авторитетная связка «MQTT id ↔ устройство». Если вызов удался, сверяться с
ним; если нет (старый драйвер, таймаут) — тихо работать по файлу.
Переиспользуйте `WbDbClient._call` как образец MQTT-RPC, но **не** правьте
сам `WbDbClient` — он про историю, а не про драйвер. Заведите отдельный
тонкий клиент.

### 3.4. Новый модуль `wb_energy_meter/wb_serial_config.py`

Только стандартная библиотека. Функции:

- `load_config(path)` → `(data: dict, sha256: str)`; поднимает
  `WbSerialConfigError` с внятным русским текстом при отсутствии файла,
  отказе в правах и невалидном JSON.
- `build_template_id_map(dirs)` → `{device_type: id_prefix}`.
- `find_device(data, device_id, id_map)` → `(port_idx, dev_idx, device)`
  либо `None`; при неоднозначности — `None`.
- `uptime_channel_state(device)` → `"enabled" | "disabled" | "absent"`.
- `set_uptime_enabled(data, port_idx, dev_idx)` → правит **только** массив
  `channels` нужного устройства, возвращает новый `data`.
- `save_config(path, data, expected_sha, backup_dir)` → см. §5.

### 3.5. API

- `GET /api/meters/<device_id>/uptime-channel` — вердикт по одному счётчику
  из таблицы §3.2 плюс поля: `config_state`, `mqtt_state`, `can_enable`
  (`true`, только если `allow_edit` включён **и** устройство найдено **и**
  состояние `disabled`/`not_in_config`), `detail` — человеческий текст.
- `GET /api/uptime-channel/summary` — то же по всем счётчикам реестра
  одним запросом, для таблицы настроек. Конфиг читать **один раз** на весь
  ответ, а не по разу на счётчик.

## 4. Слой 2 — правка конфига (за флагом, по умолчанию выключено)

### 4.1. Конфиг сервиса

```yaml
wb_serial:
  config_path: /etc/wb-mqtt-serial.conf
  templates_dirs:
    - /usr/share/wb-mqtt-serial/templates
    - /etc/wb-mqtt-serial.conf.d/templates
  allow_edit: false        # ПО УМОЛЧАНИЮ ВЫКЛЮЧЕНО — осознанное решение
  backup_dir: /mnt/data/var/lib/wb-energy-meter/wb-serial-backups
  service_name: wb-mqtt-serial
```

Значения по умолчанию задать в коде: старые конфиги без секции
`wb_serial:` обязаны продолжать работать. Проверить отдельным тестом.

### 4.2. API

- `POST /api/wb-config/enable-uptime`, тело `{"device_id": "...", "sha256": "..."}`
  - `allow_edit: false` → **403** с текстом, что правка запрещена в конфиге
    и как её включить.
  - Устройство не найдено / неоднозначно → **409**.
  - `sha256` не совпал с текущим файлом → **409** «конфиг изменился,
    обновите страницу» (см. §5.3).
  - Успех → **200**, в ответе новый `sha256` и признак, что теперь есть
    неприменённые изменения.
- `GET /api/wb-config/pending` → `{"pending": ["wb-map3e_21", ...],
  "needs_restart": true}`. Список хранить в таблице `kv`
  (`KvRepo`, ключ `wb_serial_pending_restart`) — он должен пережить
  перезапуск нашего сервиса.
- `POST /api/wb-config/restart-driver`
  - `allow_edit: false` → 403.
  - Выполняет `systemctl restart <service_name>`, ждёт до 30 с
    `systemctl is-active`.
  - Успех → очистить `pending`, вернуть 200.
  - Драйвер не поднялся → **восстановить конфиг из последнего бэкапа**,
    перезапустить снова, вернуть 500 с честным описанием и путём к бэкапу.

### 4.3. UI

**В таблице реестра счётчиков** — колонка «Uptime» с бейджем:
зелёный «опрашивается», жёлтый «не включён», серый «не проверено».
Бейдж кликабелен — раскрывает пояснение из `detail`.

**Отдельный блок в «Настройках»**, ниже реестра: «Опрос канала Uptime».
- Короткое объяснение, зачем это нужно (2–3 строки, без лекции).
- Список счётчиков, у которых канал не включён, с кнопкой «Включить» у
  каждой строки. Кнопка видна, только если `can_edit`.
- Если `allow_edit: false` — вместо кнопок текст: «Автоматическая правка
  выключена в конфиге сервиса (`wb_serial.allow_edit`). Включите канал
  вручную: Device Manager → устройство → HW Info → Uptime → in queue
  order».
- Инструкция для ручного включения должна быть видна **всегда**, даже
  когда кнопка есть. Кнопка может не сработать, человек должен знать
  запасной путь.

**Плашка о неприменённых изменениях** — заметная, жёлтая, в самом верху
вкладки «Настройки», пока `pending` не пуст:

> Конфиг опроса изменён для N счётчиков, но драйвер не перезапущен.
> Изменения вступят в силу после перезапуска.
> **[Перезапустить опрос]**

Кнопка открывает диалог подтверждения (стиль `confirm-overlay` уже есть)
с прямым текстом:

> Будет перезапущен драйвер `wb-mqtt-serial`. На несколько секунд
> прервётся опрос **всех** устройств контроллера — не только счётчиков.
> Продолжить?

## 5. Требования к безопасности правки. Это главное в задаче

Мы пишем в файл, от которого зависит весь ввод-вывод объекта. Каждый пункт
ниже обязателен.

**5.1. Не JSON — не трогаем.** Прочитать файл, `json.loads`. Если не
разобрался (комментарии `//`, JSON5, битый файл) — вернуть 409 с текстом
«конфиг не является чистым JSON, отредактируйте канал вручную».
**Никогда** не пытаться «починить» или очистить файл от комментариев.

**5.2. Бэкап до записи.** Копия в `backup_dir` с меткой времени, хранить
последние 10. Бэкап делать **только** когда дело реально дошло до записи —
при `allow_edit: false` файл не открывается на запись вообще.

**5.3. Оптимистическая блокировка.** При чтении отдавать в UI `sha256`
файла. Перед записью перечитать файл и сверить хеш. Не совпал — 409, не
писать. Это защита от гонки с веб-интерфейсом WB.

**5.4. Точечность.** Менять **только** массив `channels` у найденного
устройства: если запись `Uptime` есть — выставить `enabled: true`, иначе
добавить `{"name": "Uptime", "enabled": true}`. Ничего больше в документе
не трогать. Порядок ключей сохранится сам (`json` в Python 3.7+ держит
порядок вставки).

**5.5. Атомарная запись.** Временный файл в том же каталоге, `fsync`,
затем `os.replace`. Права и владельца исходного файла сохранить
(`os.stat` до, `os.chmod`/`os.chown` после).

**5.6. Проверка после записи.** Перечитать файл, убедиться, что он
разбирается и что наше изменение на месте. Если нет — немедленно
восстановить из бэкапа и вернуть ошибку.

**5.7. Откат при неподнявшемся драйвере** — см. §4.2.

**5.8. Форматирование.** Писать `indent=4`, `ensure_ascii=False` (иначе
русские имена устройств превратятся в `\uXXXX` и человек не узнает свой
файл). В UI честно предупредить, что отступы в файле будут
нормализованы.

## 6. Тесты

Новый `tests/test_step10_wbserial.py` — самостоятельный скрипт (не pytest),
без root и без systemd, на временных файлах.

1. `find_device`: по явному `id`; по вычисленному `<prefix>_<slave_id>`;
   не найдено; **найдено дважды → отказ**.
2. `uptime_channel_state`: `enabled: true`, `enabled: false`, канала нет.
3. `set_uptime_enabled`: добавление новой записи; обновление
   существующей; **соседние устройства и порты остались байт в байт теми
   же** (сравнить сериализацию до и после по остальным ветвям документа).
4. Конфиг с комментариями `//` → `WbSerialConfigError`, файл не изменён.
5. Несовпадение `sha256` → отказ, файл не изменён.
6. Бэкап создаётся, старые сверх 10 удаляются.
7. Атомарность: после записи в каталоге нет `.tmp`-хвостов.
8. Права файла сохраняются (проверить `os.stat().st_mode`).
9. API: 403 при `allow_edit: false` (и убедиться, что файл **не открывался
   на запись** — например, по неизменности mtime); 409 при конфликте
   хеша; `pending` появляется после успешной правки и переживает
   пересоздание приложения (лежит в `kv`).
10. Старый конфиг сервиса без секции `wb_serial:` не ломает запуск.
11. Диагностика: все шесть состояний из таблицы §3.2 воспроизводятся на
    синтетических данных.

**Отдельно и обязательно:** тест, что при **любом** сценарии отказа
(не JSON, хеш не совпал, устройство не найдено, `allow_edit: false`)
файл конфига остаётся **байт в байт** прежним. Сравнивать sha256 до и
после.

## 9. Чего делать нельзя

- Не добавлять зависимостей — только стандартная библиотека.
- Не подставлять в пути, URL и shell-команды ничего из HTTP-запроса.
  `device_id` использовать только для поиска по разобранному JSON.
- Не трогать `wb_db_client.py` — он про историю значений, а не про драйвер.
- Не писать в `/etc/wb-mqtt-serial.conf` ничего, кроме `enabled` у канала
  `Uptime` у одного конкретного устройства.
- Не перезапускать `wb-mqtt-serial` нигде, кроме явного нажатия кнопки
  «Перезапустить опрос».
- Не удалять и не переписывать пользовательские комментарии и структуру —
  при малейшем сомнении отказ, а не «умная» правка.
- Не ломать поддержку Python 3.9 (CI гоняет 3.9–3.12).
- Не менять формат существующих ответов API — только добавлять.
