# История изменений и топология «как было» — проектная заметка

Партия 12 (0.22.0), решение R7: историю топологии восстанавливаем **из
журнала изменений, без новой миграции**. Таблица `change_log` есть с
миграции 005, но до 0.22.0 в неё не писал никто. Честное следствие: история
топологии существует только с момента выхода 0.22.0; раньше этого момента
расчёт опирается на текущую структуру и подписан `assumed_legacy` (A23).

## 1. Журнал

**Где пишется.** Не в каждом репозитории вручную, а на уровне записывающего
соединения БД (`db.py` + новый `change_journal.py`). При `open()` — после
миграций — на соединении-писателе создаются **временные** (`TEMP`) триггеры
`AFTER INSERT/UPDATE/DELETE` на перечисленных ниже таблицах; они складывают
старую и новую строку во временные теневые таблицы. Внешний `transaction()`
перед `COMMIT` переносит накопленное в `change_log` — **в той же транзакции**:
откат правки откатывает и журнал, а временные таблицы откатываются вместе с
транзакцией. Выбор обоснован так:

- ни один путь записи не обходит журнал (мастер, `migrate-legacy`, старые
  маршруты, CLI идут через то же соединение) — это исчерпывающе по построению,
  а не по списку, который надо поддерживать;
- не нужна миграция (триггеры временные, в файле БД их нет) и не нужны
  JSON1/пользовательские функции SQLite — только обычные триггеры, работают на
  Python 3.9 / SQLite контроллера (проверено на 3.9 и 3.11);
- ревизия берётся из того же потока: вставка в `configuration_revisions`
  тоже попадает в теневую таблицу, поэтому все строки журнала транзакции
  получают её `revision_id` (правка без ревизии — `NULL`).

**Что журналируется** (таблица → `entity_type`): `metering_points` →
`metering_point`, `point_bindings` → `point_binding`, `meter_sources` →
`meter_source`, `point_state_versions` → `point_state`, `point_locations` /
`point_served_locations` → `point_location` / `point_served_location`,
`locations` → `location`, `location_parent_bindings` → `location_parent`,
`meter_groups` → `group`, `group_parent_bindings` → `group_parent`,
`group_memberships` → `group_member`, `electrical_nodes` → `electrical_node`,
`electrical_edges` → `electrical_edge`, `balance_scopes` / `balance_members` →
`balance_scope` / `balance_member`, `site_plans` → `plan`. Раскладка плана
(`plan_items`, `plan_edge_views`) покоординатно не журналируется: одна запись
`plan_layout` на сохранение (счётчики добавленных/изменённых/удалённых). Не
журналируются телеметрия и агрегаты, `kv`, `migration_map`, легаси-`meters`.

**Формат строки.** `entity_id` — `id` строки таблицы. `action`: `create`,
`update`, `archive`/`restore` (смена `archived_at`), `close` (закрыт интервал
`valid_to`), `publish` (черновик связи стал опубликованным), `delete`.
Несколько изменений одной строки в одной транзакции схлопываются в одну
запись; изменение одного `updated_at` не записывается. `old_value` /
`new_value` — JSON: для `create` полная новая строка, для `delete` полная
старая, для `update` изменённые поля **плюс ключевые поля топологии** в обоих
значениях (связь: `primary_point_id`, `from_node_id`, `to_node_id`, `state`,
`valid_from`, `valid_to`; узел: `kind`) — по ним восстанавливается структура.
`effective_from` — момент вступления в силу (`valid_from` / `valid_to` строки),
иначе время записи.

**«Кто».** Аутентификации нет, пользователя не выдумываем. Колонка `reason`
несёт JSON `{"op", "origin", "client"}`: операция (`POST /api/v2/topology/connect`),
происхождение (`web`, `wizard`, `migration`, `cli`, `system`) и адрес клиента.
Отдельного поля «пользователь» нет, и это названо ограничением (в
`docs/operations.md` — в партии 15).

**Чтение.** `GET /api/v2/change-log`: `entity_type`, `entity_id`, `action`,
`from`, `to`, `limit` (≤ 500), курсор `before_id`; флаг `related=1` добавляет
записи подчинённых сущностей (для точки — её привязки, места, членство в
группах, линии, которые она измеряет). Только чтение.

## 2. Структура «как было на момент T»

1. **Граница.** Метка `kv.change_log_started_at` ставится один раз при первом
   открытии БД кодом 0.22.0. Если `T` раньше метки, структура берётся на
   момент метки, а результат несёт `assumed_legacy` (A23). Новых таблиц нет.
2. **Существование связи** задают её `state`, `valid_from`, `valid_to`
   (интервальная историчность уже есть: публикация вытесняет старую связь,
   `retire` закрывает): связь действует в `T`, если опубликована и
   `valid_from <= T < valid_to`.
3. **Поля, меняющиеся «на месте»** — `primary_point_id` связи и `kind` узла —
   восстанавливаются откатом журнала: записи с `recorded_at > T` проходим от
   новых к старым и возвращаем `old_value` ключевых полей.
4. **Точка-измеритель выбывает** (A39-сеть): архивная на `T` или выключенная
   (`enabled=0` по `point_state_versions`) точка не считается измерителем —
   линия «без счётчика». Это действует и в режиме `current` (на сегодня).
5. **Период пересекает изменение.** Границы интервалов — моменты изменений
   связей, узлов, точек и составов групп внутри периода, округлённые **вверх
   до часа** (час принадлежит структуре, действовавшей в его начале; границу
   часа не делим, как при замене прибора, A19). Каждый интервал считается
   существующими функциями на структуре начала интервала, интервалы
   суммируются: значение — сумма, неполное — `value=null` и `known_value`
   (инвариант §5.3), процент пересчитывается по сумме.
6. **Режимы.** `structure_mode="current"` (по умолчанию, не меняется) — как
   раньше, плюс правило п. 4; `"as_was"` — пп. 1–5. Режим и `assumed_legacy`
   возвращаются в ответе. Смена умолчания — отдельное решение Кира.

## 3. Опись путей записи мимо протокола ревизий (H12-I)

Журнал пишет слой БД, поэтому он полон независимо от того, прошла ли запись
через `with_revision_check`. Но ревизия в строках журнала есть только у
операций, которые её создают. Опись по `api.py` / `api_v2.py` / `cli.py`
(не «ошибка», а граница: что журнал знает и с какой ревизией).

| Путь | Что пишет | Ревизия в журнале |
|---|---|---|
| `/api/v2/points`, `/locations`, `/groups`, `/topology/*`, `/balance-scopes`, `/migration/legacy-links/confirm` | предметные сущности | есть (`with_revision_check` или прямой `create_revision` — баланс, мастер) |
| `/api/v2/plans` (создание, правка, удаление) | `site_plans` | нет (`NULL`): план не входит в конфигурацию, защита — `canvas_revision` |
| `/api/v2/plans/<id>/layout`, `/items`, `/edges` | раскладка плана | нет; пишется `plan_layout` с счётчиками |
| `/api/v2/admin/migrate-legacy` | точки, привязки, группы из старых `meters` | нет; происхождение `migration` |
| `/api/registry/groups` (POST/PATCH/DELETE, старый интерфейс) | `meter_groups` | нет (`NULL`), происхождение `legacy-api` |
| `/api/registry/meters*`, `/api/plans*` (старые зоны/связи) | `meters`, `plan_zones`, `plan_links` | не журналируются (легаси-таблицы, не входят в модель v2) |
| приём MQTT, агрегатор | телеметрия, часовые агрегаты | не журналируются |

Вывод: структура, от которой зависят отчёты (точки, привязки, группы, узлы,
связи, границы баланса), журналируется целиком; правки без ревизии видны в
журнале с `revision_id = NULL` и по полю `operation`.
