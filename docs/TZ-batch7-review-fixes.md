## 0. Зачем эта партия

Ревью нашло ошибки, которые юнит-тесты и самоотчёты агентов не ловили:

1. **Небаланс на «Обзоре» считается неверно.** Итог объекта берётся по
   электрической схеме, а вычитается сумма корневых **учётных групп**. Если
   схема собрана без групп, «Обзор» показывает небаланс 100 %. Если точка
   входит в две группы, небаланс уходит в минус из-за двойного счёта.
2. **«План v3» на чистой базе не даёт поставить первый узел.** Карта
   открывается в масштабе −4, и клик даёт «Точка вне границ плана». Кроме
   того, после каждого действия масштаб и положение карты сбрасываются.
3. **Экран «План v3» доделан наполовину** (§2 задания партии 6): нет
   карточек линии и зоны, нет чисел, нет списков, счётчик нельзя завести
   с экрана.
4. **Две несовместимые модели питания.** Отменённый простой режим живёт
   рядом с «Планом v3», и «Структура» показывает «не указано питание» даже
   у ввода объекта.
5. **Интерфейс ни разу не проверялся в браузере**, хотя в песочнице есть
   Chromium и Playwright.
6. **Техдолг:** `index.html` весит 458 КБ; `api_v2.py` — 2636 строк; 79
   строк тестов вручную прописаны в CI; бэкап БД в `install.sh` делается
   через `cp`; нет `ExecStartPre`-гарда; `AGENTS.md` весит 64 КБ.

Скрипты-воспроизведения из ревью: `docs/review-repro/repro_imbalance.py`,
`docs/review-repro/planv3_browser_smoke.py`. На 0.17.0 оба показывают
ошибки. После партии оба обязаны проходить.

## 2. Как работать: Sonnet ведёт, Haiku исполняет

### 2.1 Роли

**Ты (Sonnet) — ведущий инженер.**
- Читаешь задание и нужные места кода.
- Проектируешь решения и пишешь рискованный код (список в §2.2).
- Каждую задачу для Haiku формулируешь брифом (§2.3).
- **Построчно** проверяешь результат Haiku (§2.4), гоняешь проверки,
  коммитишь.
- За корректность отвечаешь ты, а не субагент.

**Субагенты Haiku** (Agent tool, `model: "haiku"`; для чистого поиска
подходит тип `Explore`) получают узкие задачи с полным брифом:
- инвентаризация и поиск по коду: где используется X, какие строки
  затронуты;
- механические правки по точной спецификации: удалить блок, переименовать,
  перенести код без изменения логики;
- тесты по заданной тобой таблице сценариев с готовыми ожидаемыми числами;
- шаги Playwright-сценариев по готовому харнессу;
- черновики документации (CHANGELOG, `docs/status.md`, чеклист).

Haiku **не коммитит**, не меняет задание и не принимает архитектурных
решений. Если бриф неясен, он останавливается и возвращает вопрос.

### 2.2 Что НЕЛЬЗЯ отдавать Haiku

Эти задачи пишешь сам. Haiku можно поручить только поиск по ним или тесты
к ним:

- алгоритм баланса по схеме и новый `overview_service.py` (этап 2);
- удаление простого режима на бэкенде и вычисление питания из топологии
  (этап 4, C2);
- жизненный цикл карты Leaflet в «Плане v3»: `fitBounds`, перерисовка,
  видимость контейнера (этап 3, B1–B2);
- атомарная ручка «новая точка из прибора на линию» (этап 3, B8);
- `install.sh`, `self-update.sh`, `ExecStartPre`-гард (этап 6);
- схема разнесения `index.html` по файлам и механизм сборки `app()` из
  частей (этап 6, F5). Переносить готовые куски по твоей схеме Haiku может.

### Этап 2 — баланс по электрической схеме (главное)

Реализуешь сам. Haiku пишет тесты по таблице Э2.7 (бриф H3). Подразделы
этапа 2 нумеруются «Э2.x», чтобы не путать их с §2 «Как работать».

#### Э2.1 Определения

- **Действующая топология** — `edge_repo.list_active_published()`, как
  сейчас. Режим структуры — текущий; в ответе явно
  `structure_mode: "current"`. Историческая топология «как было» вне
  объёма.
- `incoming(N)` — единственная действующая линия с `to_node_id = N`
  (валидатор радиальности гарантирует не больше одной).
  `outgoing(N)` — линии с `from_node_id = N`.
- Линия **измеряемая**, если `primary_point_id` не пустой.
- **`first_measurements(N)`** (выходы границы, большое ТЗ §5.2 «поиск
  останавливается на первом измерении в каждой ветви»). Для каждой
  `e ∈ outgoing(N)`:
  - если `e` измеряемая, её точка — выход, дальше по этой ветви не идти;
  - иначе рекурсивно `first_measurements(e.to_node)`;
  - если во всём поддереве под `e`, включая саму `e`, нет ни одной
    измеряемой линии, `e` — **неизмеренная ветвь**. Записывается самая
    верхняя такая линия, её поддерево дальше не разворачивается;
  - защита от циклов: множество посещённых узлов и предел глубины 32
    (защитный предел обхода из большого ТЗ §4.2).

  Выходы по построению не пересекаются электрически, поэтому
  `sum_points` по ним не должен давать `AccountingConflict`. Если всё же
  дал — это ошибка алгоритма, а не данных; лови её тестом.

#### Э2.2 Общее ядро баланса

Вынести из `accounting_service.balance()` ядро
`balance_from_point_sets(input_ids, output_ids, …) -> MetricResult`.
Семантика **строго та же**, что сейчас:

- `R = ΣE_in − ΣE_out` со знаком;
- `value = null`, если неизвестна любая обязательная часть; `known_value`
  отдельно;
- `availability`, `missing_ids`, `quality_flags`, `structure_quality`;
- процент через `resolve_percentage(R, E_in)`.

`balance()` для `balance_scopes` переписать поверх ядра; `test_step17` и
`test_step28` должны пройти без изменений. Новые расчёты ниже идут только
через это ядро: никаких сумм «вручную» в обработчиках и на фронте.

#### Э2.3 Баланс узла (щита)

`balance_node(N, ts_from, ts_to, timezone)` в новом
`wb_energy_meter/overview_service.py`:

| Ситуация | Результат |
|---|---|
| `incoming(N)` нет (узел-источник или висячий) | `value=null`, `unavailable_reason="no_incoming_line"` |
| `incoming(N)` без счётчика | `value=null`, `unavailable_reason="input_unmetered"`; выходы и неизмеренные ветви **всё равно** в ответе |
| Нет выходов и нет неизмеренных ветвей (лист) | `value=null`, `unavailable_reason="no_outgoing_lines"` |
| Иначе | ядро с `input_ids=[incoming.primary_point_id]`, `output_ids=first_measurements(N)` |

`boundary_coverage`: `"verified"`, если неизмеренных ветвей нет, иначе
`"has_unmetered_branches"`. Небаланс при неизмеренных ветвях показывается
как есть, со знаком. Подпись в UI: «нераспределённый расход, включая
неизмеренные ветви: …». Потерями его не называть (большое ТЗ §5.2).

#### Э2.4 Итог и небаланс объекта (`/api/v2/overview/summary`)

- **Вводы** — все действующие линии из узлов `kind='source'`.
  - Нет ни одной такой линии: `object_total=null`,
    `object_total_unavailable_reason="no_input_assigned"` (как сейчас,
    UI-кнопка «Настроить границу объекта» остаётся).
  - Есть линии от источника без счётчика: `object_total.value=null`,
    `known_value` = сумма измеряемых вводов (null, если таких нет),
    `availability` partial/missing, причина `"unmetered_input"`, новое
    поле `unmetered_inputs: [{edge_id, from_node_name, to_node_name}]`.
    **Сейчас такие линии молча пропускаются, и итог занижается — это
    тоже ошибка.**
  - Все вводы измеряемые: как сейчас, через `sum_points`.
- **Выходы уровня 1** — объединение `first_measurements(e_in.to_node)` по
  всем измеряемым вводам (без повторов).
- **Небаланс объекта** — ядро Э2.2 по вводам и выходам уровня 1. Если итог
  объекта неполный: `imbalance_value=null`,
  `imbalance_percent_reason="object_total_incomplete"`.
- Поля ответа `imbalance_value`, `imbalance_percent`,
  `imbalance_percent_reason` **сохраняют имена**, меняется только смысл —
  это исправление ошибки. Новые поля, только добавление:
  - `imbalance` — полный MetricResult;
  - `boundary_coverage`;
  - `network_branches: [{edge_id, point_id, name, result,
    percentage_of_object}]` — выходы уровня 1. `name` — имя линии, иначе
    имя узла-получателя;
  - `unmetered_branches: [{edge_id, name}]`;
  - `unmetered_inputs`;
  - `structure_mode`.
- Поля `object_input_point_ids`, `object_total`,
  `object_total_unavailable_reason`, `ungrouped_point_ids` остаются как
  есть (на них завязаны `test_step27`/`test_step39` и UI).
- Поле `branches` (корневые учётные группы) **остаётся** для совместимости,
  но в небалансе больше не участвует. Добавить поле
  `groups_note: "распределение по учётным группам; группы могут
  пересекаться, в небалансе не участвуют"`.
- Весь расчёт — в `overview_service.py`. Обработчик в `api_v2.py` только
  разбирает тело, фиксирует ревизию (A43: один `db.read()`, как сейчас) и
  переводит исключения в HTTP.

## 5. Ограничения проекта (как в прошлых партиях)

- Рантайм: только стандартная библиотека + `flask`, `paho-mqtt`,
  `pyyaml`. Playwright — только тесты.
- Контроллер: Python 3.9, Flask 1.1.2, Werkzeug 1.0.1. Job
  `legacy-deps` обязан быть зелёным.
- Никаких CDN и сборщиков; React и сборка запрещены большим ТЗ §9.1.
- Любая предметная запись — через протокол ревизий; при 409 понятный
  текст, чужая работа не затирается.
- Форматы ответов API не менять. Исключения — только перечисленные в
  этом задании (смысл `imbalance_*`, `dimension=branch`, удалённые поля
  PATCH), каждое описано в CHANGELOG.
- Хранение дерева — только `electrical_edges`. Никакого
  `parent_meter_id`.
- Не трогать: расчёт `measured_point`/`sum_points`, контракт
  `MetricResult`, валидатор радиальности, протокол ревизий, миграции
  001–005 (новая миграция этой партии не нужна; если кажется, что нужна
  — остановись и спроси).
- Сверять форму ответа ручки с тем, как её разбирает фронт (прошлый баг
  `.find is not a function`).
- К каждой проверке «отказ» — парная «легитимный запрос работает».

## 6. Вне объёма

- Безопасность API (решение Кира).
- Журнал изменений и структура «как было» (задачи 1–2 партии 4).
- Адаптивная вёрстка, `viewport`, доступность, однолинейная схема вторым
  холстом, пошаговый мастер первого запуска (большое ТЗ §8.5).
- Удаление «Плана v2», «Структуры», классического интерфейса.
- Причина `no_data` у `wb-map3e_49`: нужен доступ к контроллеру.
- `Install-WbEnergyMeter.cmd/.ps1`: не выдумывать.

## 7. Когда останавливаться и спрашивать Кира

- Существующий тест, не перечисленный в этом задании как изменяемый,
  противоречит новому смыслу баланса.
- На реальных данных (если будут) у одного узла две действующие входящие
  линии или найден цикл.
- Нагрузочный замер показывает RSS ≥ 256 МиБ или p95 > 2 с, и
  конкретное узкое место не находится.
- Для задачи кажется нужной новая миграция или новая сущность.

Во всех остальных случаях решай сам, отмечай решение в CHANGELOG и
отчёте.
