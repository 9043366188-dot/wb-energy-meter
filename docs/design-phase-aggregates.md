# Проектная заметка: пофазные часовые итоги (П9, выпуск 0.22.3)

Решение Кира — R13 (18.10.2026): «нужно вернуть возможность прописать каждой
фазе своего потребителя» — один WB-MAP3E, у которого L1, L2 и L3 питают разные
нагрузки. Заметка написана **до кода** (как `docs/design-history.md` в партии
12) и фиксирует выбор: схему хранения, миграцию, откат, нагрузку на
`wb-mqtt-db`. Код партии следует ей; расхождения — только с правкой этого файла
в том же PR.

## 1. Что было в 0.22.2 и почему «молча неверно»

| Место | Как устроено | Следствие для точки на фазе |
|---|---|---|
| `period_aggregates` (миграция 001) | ключ `(meter_id, period_type, period_start)` — **один час на прибор**, канала в ключе нет | фазе негде хранить свой итог |
| `aggregator.py` | RPC только по `Total AP energy` (и `Total P` для мощности) | пофазных итогов никто не считает |
| `accounting_service.measured_point` | `aggregates_repo.list_range(src.meter_id, …)`; профиль привязки (`Segment.channel_profile`) вычисляется, но не используется | точка на `phase_l1` получает весь трёхфазный расход прибора, три фазы одного прибора — утроенный |
| `api_v2` снимок точки | `power_w = Total P`, `energy_total_kwh = Total AP energy` | то же для живых значений |
| `POST /api/v2/topology/nodes/<id>/meters` | принимает `channel_profile=phase_l1` | сохраняет привязку, а считает неверно |

Правила *занятости* прибора уже правильные (`binding_service.profiles_overlap`:
`total_3p` пересекается с любой фазой, фазы между собой независимы;
`_find_conflicts` работает по `meter_source_id`). Чинить нужно хранение,
агрегатор, расчёт, список выбора прибора и форму «+ Счётчик».

## 2. Хранение: отдельная таблица `phase_aggregates`

Два варианта из текста П9: «новая таблица» или «канал в ключе итогов».

**Выбрано: новая таблица `phase_aggregates`**, `period_aggregates` не меняется.

```
phase_aggregates(
  meter_id INTEGER NOT NULL REFERENCES meters(id) ON DELETE CASCADE,
  phase    TEXT    NOT NULL CHECK (phase IN ('L1','L2','L3')),
  period_start, period_end INTEGER NOT NULL,
  ap_energy_start, ap_energy_end, ap_energy_delta REAL,
  p_avg, p_max REAL, samples_count INTEGER,
  quality_flag TEXT NOT NULL DEFAULT 'ok', computed_at INTEGER NOT NULL,
  PRIMARY KEY (meter_id, phase, period_start))
```

Колонки те же, что в `period_aggregates`: одна запись о часе — один и тот же
`HourlyAggregate`, тот же `compute_hourly_aggregate`, те же флаги (`ok`,
`edge_approx`, `no_data`, A13 `reset`, A14 `sparse`).

**Почему не «канал в ключе `period_aggregates`».** SQLite не меняет первичный
ключ на месте — пришлось бы пересоздавать таблицу с копированием всех
накопленных часов (дольше и рискованнее на контроллере) и, главное, **сломать
откат**: код 0.22.2 пишет `INSERT … ON CONFLICT(meter_id, period_type,
period_start) DO UPDATE`; при другом ключе SQLite отвечает «ON CONFLICT clause
does not match any PRIMARY KEY or UNIQUE constraint», и агрегатор прежней версии
перестал бы записывать часы. Отдельная таблица прежнему коду не видна и ему не
мешает. Существующие итоги `Total AP energy` не трогаются.

Доступ — тот же `AggregateRepo`, параметризованный источником:
`AggregateRepo(db)` — как раньше; `repo.for_profile("phase_l2")` — тот же
интерфейс (`get`, `list_range`, `upsert_many`, `missing_hours`,
`last_known_value_before` …) над `phase_aggregates` и фазой `L2`;
`for_profile("total_3p")` возвращает сам `repo`. Расчёт и агрегатор пишут
код один раз, источник выбирают по профилю.

## 3. Миграция 006

`006_phase_aggregates.sql` — только `CREATE TABLE` и `CREATE INDEX`
(`idx_phase_aggr_period_start`), применяется атомарно протоколом версий ≥ 5
(`Database._apply_migration_atomic`). Данных не копирует и не меняет, поэтому
на БД любого размера занимает миллисекунды. Миграции 001–005 не тронуты.
Это единственная новая миграция выпуска; пункт «новых миграций нет» (R7)
относится к истории топологии, а П9 прямо требует миграции схемы.

## 4. Откат на 0.22.2

Два уровня, оба проверяются тестами (`tests/test_step62_phase_migration_rollback.py`).

**Уровень схемы.** Код 0.22.2 при старте применяет только файлы 001–005 и
пропускает всё, что `<= MAX(schema_migrations.version)`; версия 6 ему не мешает
(`current_schema_version() == 6`, ничего не применяется и не падает). Он не
знает про `phase_aggregates` и не трогает её; `period_aggregates` и все прочие
данные остаются целыми, его `AggregateRepo` пишет и читает как раньше. Таблица
со ссылкой `ON DELETE CASCADE` на `meters` удаление счётчика старым кодом не
ломает. Тест: БД создаётся кодом 0.22.3, наполняется, затем открывается «кодом
0.22.2» — копия пакета без файла `006…` (то, что 0.22.2 и видит в своей папке
миграций; можно подставить настоящее дерево 0.22.2 через
`WBEM_OLD_CODE_DIR`): сервис поднимается, данные целы, запись часа по-старому
проходит.

**Уровень смысла (поколение домена).** Схема-то откат переживает, а *смысл* —
нет: пока в БД есть пофазная привязка, 0.22.2 отдал бы такой точке весь
расход прибора — ровно ту молчаливую ошибку, которую П9 устраняет. В проекте для
такого случая есть протокол поколений (`docs/migration-plan-v2.md` §7,
`domain_generation.py`, `scripts/check-generation.sh`, `self-update.sh`):
старый код блокируется, как только он начал бы показывать данные неполно или
неверно. Поэтому:

- `__code_generation__ = 3` — 0.22.3 понимает пофазные привязки;
  `domain_generation.CODE_GENERATION = 3`. `CURRENT_GENERATION` (2) остаётся
  тем, что пишет **первая v2-запись** — откат до первой пофазной привязки
  по-прежнему разрешён, как и раньше.
- **Первая пофазная привязка** (`channel_profile != total_3p`, любой путь:
  «+ Счётчик», открытие привязки, замена прибора) в той же транзакции
  поднимает `domain_model_generation` и `minimum_reader_generation` до 3
  (`domain_generation.mark_phase_binding`). Идемпотентно, не убывает.
- После этого `check-generation.sh` (ExecStartPre) и `self-update.sh`
  (`check_rollback_generation`) не дают запустить код поколения 2 на этой БД и
  говорят почему. Откат на 0.22.2 с пофазными привязками **запрещён**; до
  первой пофазной привязки — разрешён (тест на оба состояния).

Цена: пока пилот не начал вести фазы, ничего не меняется; когда начал — «вернуть
0.22.2» перестаёт быть вариантом (оно и не умеет фазы), движение только вперёд.

## 5. Агрегатор

**Какие приборы и фазы считаются.** Только те пары *(прибор, фаза)*, у которых
есть открытая привязка с профилем `phase_l1`…`phase_l3`
(`binding_service.open_phase_targets(db)` → `{meter_id: {"L1", "L3"}}`). Не «все
MAP3E».

Обоснование нагрузкой на `wb-mqtt-db`: почасовой расчёт — 2 RPC на прибор в час
(`Total AP energy` + `Total P`), для сотни приборов — 200 RPC/час. «Все MAP3E ×
3 фазы» добавило бы ещё 600 RPC/час ради итогов, которые никто не читает (на
практике почти все приборы стоят `total_3p`). По привязкам: +2 RPC/час на
каждую фазу-линию; пилот с пятью фазами — +10 RPC/час.

**Расчёт.** Те же три воркера (`aggr-hourly`, `aggr-catchup`, `aggr-patcher`):
после итогов прибора — его фазы. Каналы: энергия `AP energy L1…L3`, мощность
`P L1…L3` (`AggregatorConfig.phase_energy_channel` / `phase_power_channel`,
шаблоны с `{p}`). `compute_hourly_aggregate` не меняется — A13 (`reset`) и A14
(`sparse`) действуют на фазы автоматически, как на итог; перенос вперёд
(`last_known_value_before`) берёт якорь из таблицы той же фазы; пометка
предыдущих часов интервала редких показаний (`_mark_earlier_sparse_hours`) — тоже.

**Прошлые часы фаз.**
- `aggregates recompute <device> --phase L1|L2|L3|all` (CLI; без `--phase` —
  как раньше, только итог прибора); `aggregates show --phase`; `aggregates
  status` показывает строки `phase_aggregates` отдельно.
- Автоматически при создании пофазной привязки: четвёртый лёгкий поток
  `aggr-phases` раз в 30 с сравнивает `open_phase_targets` с уже известными
  парами и для новой догоняет дыры за `catchup_days` (`missing_hours` — только
  отсутствующие часы, суточными пачками, один RPC на сутки). Привязка
  создана любым путём (форма, API, мастер) — поток увидит её без связи
  `api_v2` с агрегатором. При старте демона известные пары запоминаются
  сразу: их догоняет обычный catch-up (он теперь включает фазы).

Нагрузка разового догоняния: до `catchup_days` (90) суточных RPC на фазу, без
запроса мощности; бюджет и пауза между приборами — прежние
(`max_catchup_duration_s`, `inter_meter_pause_s`).

## 6. Расчёт по профилю привязки

`accounting_service.measured_point`: для каждого сегмента привязки источник
итогов выбирается `aggregates_repo.for_profile(seg.channel_profile)` —
`total_3p` → итоги прибора, `phase_lN` → итоги фазы. `_SparseRuns` получает
тот же репозиторий сегмента. Контракт `MetricResult`, сегментация по истории
привязок, A13/A14/A18/A19 и `sum_points` не меняются. Снимок «Обзора», баланс
щита, отчёты и CSV зовут `measured_point` и получают пофазное автоматически.

Живые значения точки (`api_v2`, снимок): `total_3p` — `Total P`, `Total AP
energy`, напряжения/токи всех фаз (как раньше); `phase_lN` — `P LN`,
`AP energy LN`, напряжение и ток **только своей фазы** (чужие фазы
принадлежат другим точкам).

Инвариант проверки: сумма трёх фаз одного прибора за период ≈ итог прибора
(допуск — округление `REAL`, 1e-6 кВт·ч на час) — тест на поддельном RPC, где
`Total AP energy` = L1+L2+L3. Итог объекта без тройного счёта: три фазы — три
разные линии разных ветвей, `sum_points` считает их по топологии, а не по
прибору.

## 7. Занятость по фазам

`GET /api/v2/structure/points` → `occupied_devices` (формат только
расширяется): к прежним полям добавляются `profiles` (занятые профили),
`busy_phases` (`{"L1": {point_id, point_name, archived}, …}`),
`free_phases` и `fully_busy`. Прибор с занятой L1 свободен для L2 и L3;
`total_3p` занимает все три; три занятые фазы — тоже «занят полностью».
В списках выбора: «wb-map3e_16 — свободны L2, L3» (серым — только полностью
занятые, с именем держателя, как в П4). Правила конфликтов на сервере не
менялись — `profiles_overlap` уже верен; 409 `double_counting` и текст
`_binding_conflict_text` называют фазу («Фаза L1 прибора … уже занята …»).

## 8. «+ Счётчик»: режим «по фазам»

Тело `POST /api/v2/topology/nodes/<id>/meters` расширяется (прежний вариант
без `phases` работает как раньше):

```
{ device_id, measures: "outgoing", mode: "phases",
  phases: [ {phase: "L1", line_id | to_node_id | new_load_name, name?},
            {phase: "L2", …}, {phase: "L3", skip: true} ],
  expected_revision }
```

Одна серверная операция в одном `with_revision_check`, одной ревизией: для
каждой используемой фазы — недостающая линия/нагрузка (`resolve_meter_line`
с `phase_count=1`; существующая линия фазы тоже получает `phase_count = 1`),
точка учёта, привязка с профилем `phase_lN`, «измеряет линию». Любой отказ —
ничего не создано. Ответ 201 содержит `phases: [{phase, point, edge, node,
created_edge, created_node}]` (верхние `point/edge/node` — `null`).

Отказы 400: «по фазам» только для отходящих линий; ни одной используемой фазы;
одна линия назначена двум фазам; у прибора **нет пофазных счётчиков в MQTT**
(`AP energy L1…L3` в `registry`) или прибор ещё не появлялся в MQTT — текст
«у прибора нет пофазных счётчиков энергии — подключить по фазам нельзя»;
то же для одиночного `channel_profile=phase_lN`. Занятая фаза — 409
`double_counting`.

Интерфейс: «Как подключён прибор: ● все три фазы — одна линия ○ по фазам — каждая
фаза своя линия» (виден при «Отходящую линию»); по фазам — три строки L1/L2/L3,
в каждой цель (существующая линия / узел / «+ новая нагрузка…» / «не
используется»); недоступно с пояснением, если пофазных счётчиков нет. Карточка
узла: «wb-map3e_16 · L1 — линия к «Освещение»» (`describe_node_lines` отдаёт
`meter_device_id` и `channel_profile` точки).

## 9. Ограничения и что проверяется на объекте

- Пофазные итоги есть, только если `wb-mqtt-db` пишет историю каналов `AP energy
  L1…L3`. Приложение этого не настраивает. Нет истории — часы фазы помечаются
  `no_data` и видны как «нет данных» (не нулём). Проверка при пилоте —
  `docs/pilot-checklist.md`, раздел 3 (шаг «по фазам»): история по каналу есть.
- Старый поток `/api/meters/*`, `consumption.py` и итоги `Total AP energy`
  не меняются.
- Цифры по фазам до `catchup_days` назад появляются через ≤ минуту после
  создания привязки (поток `aggr-phases` + суточные RPC); пока их нет — «нет
  данных».
- Откат на 0.22.2 после первой пофазной привязки запрещён (§4).
