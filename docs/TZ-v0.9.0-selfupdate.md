# ТЗ v0.9.0 — самообновление из GitHub по кнопке

**Проект:** `wb-energy-meter` (Wiren Board 8.x + WB-MAP3E)
**Базовая версия:** 0.8.0
**Целевая версия:** 0.9.0
**Рабочий каталог:** `C:\wb-energy-meter-repo\wb-energy-meter`
**Дата составления:** 08.09.2026

---

## 1. Что нужно сделать

В настройках веб-интерфейса появляется блок «Обновление»: показывает текущую
версию, по кнопке проверяет GitHub, и если там свежее — по второй кнопке
скачивает и устанавливает обновление, перезапускает сервис. Если после
обновления сервис не поднялся — автоматически откатывается на предыдущую версию.

Решения, принятые заказчиком:

- **Источник — ветка `main`.** Не теги. Что в `main`, то и приедет на контроллер.
- **Автооткат обязателен.** Если сервис не ответил после обновления — вернуть как было.
- **Автопроверки нет.** Сервис не ходит в интернет, пока пользователь не нажал кнопку.

---

## 2. Что уже есть и на что опираться

- `scripts/install-from-github.sh` — качает tarball ветки/тега с GitHub,
  распаковывает, запускает `scripts/install.sh`. Логика скачивания уже написана,
  переиспользуйте подход (URL, поиск распакованной папки, проверки).
- `scripts/install.sh` — останавливает сервис, делает **резервную копию БД**
  (хранит 5 последних), копирует код в `/opt/wb-energy-meter`, пишет
  systemd-юнит и launcher'ы, `systemctl restart`.
- Сервис работает под `User=root` — прав на самообновление хватает.
- Веб-интерфейс — один файл `wb_energy_meter/static/index.html`, Alpine.js с CDN.

## 3. Три грабли, на которых это ломается. Прочитать до начала

### 3.1. Нельзя запускать апдейтер как дочерний процесс сервиса

В юните `KillMode=mixed` и `MemoryMax=256M`. Если апдейтер стартовать обычным
`subprocess.Popen` из процесса сервиса, он попадёт в cgroup
`wb-energy-meter.service`, и произойдёт вот что:

- `install.sh` вызовет `systemctl stop wb-energy-meter` → systemd прибьёт
  **всю** cgroup, включая сам апдейтер. Обновление оборвётся на середине,
  в `/opt` останется полускопированное дерево. Сервис не поднимется.
- Даже если бы не прибило — `MemoryMax=256M` применяется ко всей cgroup,
  и распаковка с `apt-get` могут упереться в лимит.

**Правильно** — запускать апдейтер отдельным transient-юнитом:

```bash
systemd-run --unit=wb-energy-meter-update --collect \
    --description="Обновление wb-energy-meter" \
    /bin/bash /opt/wb-energy-meter/scripts/self-update.sh
```

`--collect` убирает юнит после завершения. Такой процесс живёт вне cgroup
сервиса, переживает его остановку и не ограничен `MemoryMax`.

Фолбэк, если `systemd-run` почему-то недоступен:
`subprocess.Popen(["setsid", "nohup", "bash", script], start_new_session=True,
stdin/stdout/stderr=DEVNULL)`. Но `systemd-run` — основной путь, фолбэк
логировать предупреждением.

### 3.2. Скриптов нет в установленном дереве

`install.sh` копирует только `wb_energy_meter/`. Каталога `scripts/` в
`/opt/wb-energy-meter` нет, а `self-update.sh` должен быть именно там —
запускать его из распакованного во временный каталог архива нельзя,
временный каталог удаляется.

**Добавить в `install.sh`** копирование `scripts/` в
`/opt/wb-energy-meter/scripts/` с `chmod 0755` на `.sh`.

### 3.3. У сервиса нет никакой аутентификации

`http.host: 0.0.0.0` по умолчанию — API доступен всем в локальной сети.
Кнопка «Обновить» означает, что **любой в сети объекта может инициировать
перезапуск сервиса учёта электроэнергии**. Обязательные меры:

- В конфиге секция `update:` с флагом `allow_from_ui` (по умолчанию `true`,
  но задокументировать, как выключить).
- `POST /api/update/start` при `allow_from_ui: false` → **403** с внятным
  текстом, кнопка в UI скрыта.
- В `README.md` — явное предупреждение: если контроллер в недоверенной сети,
  ставьте `http.host: 127.0.0.1` и ходите через SSH-туннель, либо
  `allow_from_ui: false`.

Не изобретайте свою авторизацию (пароли, токены в конфиге) — это отдельная
задача, и сделанная наспех она хуже, чем честно описанное ограничение.

## 4. Компоненты

### 4.1. `scripts/self-update.sh` — новый скрипт

Делает всю работу. Запускается от root, без аргументов (параметры — через
переменные окружения, значения по умолчанию из конфига передаёт Python).

Переменные: `REPO_OWNER`, `REPO_NAME`, `REF` (по умолчанию `main`),
`EXPECTED_SHA` (sha, который проверили при `check` — чтобы установить именно
то, что показали пользователю), `STATUS_FILE`, `INSTALL_DIR`, `HTTP_PORT`.

Порядок действий:

1. **Захватить блокировку.** `flock` на `/run/lock/wb-energy-meter-update.lock`
   (каталог создать, если нет). Если занята — выйти с ошибкой «обновление уже идёт».
2. **Статус → `downloading`.** Скачать
   `https://github.com/<owner>/<repo>/archive/refs/heads/<ref>.tar.gz`
   через `curl -fsSL --max-time 120`. Только HTTPS, owner/repo из окружения,
   **никаких значений из HTTP-запроса пользователя**.
3. **Распаковать** во временный каталог, найти папку с исходниками.
4. **Проверить целостность архива** — должны существовать:
   `wb_energy_meter/main.py`, `wb_energy_meter/__init__.py`,
   `wb_energy_meter/migrations/001_initial_schema.sql`,
   `wb_energy_meter/static/index.html`, `scripts/install.sh`.
   Нет чего-то — отказ **до** подмены рабочего кода.
5. **Синтаксическая проверка нового кода:**
   `python3 -m compileall -q <src>/wb_energy_meter`. Не компилируется — отказ,
   рабочая версия не тронута. Это дёшево и ловит большую часть «кирпичей».
6. **Резервная копия:** `rm -rf /opt/wb-energy-meter.rollback` и
   `cp -a /opt/wb-energy-meter /opt/wb-energy-meter.rollback`.
   БД бэкапит сам `install.sh`, дублировать не надо.
7. **Статус → `installing`.** Запустить `bash scripts/install.sh` из
   распакованного дерева, весь вывод — в `/var/log/wb-energy-meter/update.log`
   (с ротацией: хранить последние 5 файлов или обрезать по 1 МБ).
   Передать `SKIP_APT=1` (см. §4.2).
8. **Статус → `verifying`.** Ждать до **90 секунд**, опрашивая раз в 3 с:
   - `systemctl is-active --quiet wb-energy-meter.service`
   - и `curl -fsS --max-time 3 http://127.0.0.1:<port>/health`
   Обе проверки прошли — успех. Только `is-active` недостаточно: процесс может
   стартовать и падать в цикле по `Restart=on-failure`.
9. **Успех:** статус → `success` с новой версией и sha, удалить
   `/opt/wb-energy-meter.rollback`, почистить временные файлы, снять блокировку.
10. **Неудача → откат.** Статус → `rolling_back`:
    - `systemctl stop wb-energy-meter.service`
    - `rm -rf /opt/wb-energy-meter/wb_energy_meter` и вернуть из
      `/opt/wb-energy-meter.rollback` (каталог целиком)
    - `systemctl start wb-energy-meter.service`
    - подождать те же 90 с и проверить `/health`
    - статус → `rolled_back` (откат удался) либо `failed` (не поднялось даже
      старое — тут уже только SSH, и это надо честно написать в статусе).

`set -euo pipefail`, но с `trap` на выходе: **при любом падении скрипта статус
обязан быть записан**, иначе UI навсегда останется в «идёт обновление».
Через `trap 'on_error' ERR` и `trap 'cleanup' EXIT`.

### 4.2. Правки `scripts/install.sh`

- Копировать `scripts/` в `$INSTALL_DIR/scripts/`, `chmod 0755` на `*.sh`.
- Поддержать `SKIP_APT=1` — пропускать `apt-get update` / `apt-get install`.
  Зависимости при обновлении уже стоят, а `apt-get update` на объекте без
  интернета через прокси может висеть минутами. При `SKIP_APT=1` проверить,
  что `python3 -c "import paho.mqtt, yaml, flask"` отрабатывает; если нет —
  выполнить установку пакетов несмотря на флаг.
- Писать `$INSTALL_DIR/VERSION.json`:

  ```json
  {"version": "0.9.0", "commit": "abc1234...", "ref": "main",
   "installed_at": 1788900000}
  ```

  `commit` брать из переменной окружения `SOURCE_SHA` (её передаёт
  `self-update.sh`); при ручной установке её нет — писать `null`.

### 4.3. `wb_energy_meter/updater.py` — новый модуль

Только стандартная библиотека — `urllib.request`, `json`, `subprocess`,
`os`, `re`. **Никаких новых зависимостей**: на контроллере ставится
`python3-paho-mqtt`, `python3-yaml`, `python3-flask` и всё.

Функции:

- `get_installed_info(install_dir)` → читает `VERSION.json`; если его нет —
  `{"version": __version__, "commit": None}`.
- `check_remote(owner, repo, ref, timeout=10)` →
  запрашивает `https://api.github.com/repos/{owner}/{repo}/commits/{ref}`,
  берёт `sha`, `commit.message` (только первая строка), `commit.author.date`.
  Отдельно тянет
  `https://raw.githubusercontent.com/{owner}/{repo}/{ref}/wb_energy_meter/__init__.py`
  и вытаскивает `__version__` регуляркой `__version__\s*=\s*["']([^"']+)["']`.
  Заголовок `User-Agent: wb-energy-meter/<version>` — без него GitHub API
  отвечает 403. Ошибки сети и таймауты — своё исключение `UpdateCheckError`
  с текстом по-русски.
- `is_update_available(installed, remote)` → `True`, если
  `installed["commit"]` пуст **или** отличается от `remote["sha"]`.
  Версию сравнивать не нужно: источник — ветка, а не теги.
- `read_status(path)` / `write_status(path, **fields)` — атомарная запись
  JSON: во временный файл рядом, затем `os.replace`. Иначе UI прочитает
  обрезанный файл.
- `start_update(...)` → проверяет, что обновление не идёт, пишет статус
  `starting` и запускает `systemd-run` (см. §3.1). Возвращает управление
  немедленно, **ничего не ждёт**.

Файл статуса: `<каталог БД>/update-status.json` — рядом с `state.db`, на
разделе `/mnt/data`, который переживает перезапуск и обновление. В `/run`
класть нельзя: после перезагрузки статус пропадёт, а он нужен, чтобы UI
показал результат обновления, случившегося до перезапуска.

Формат статуса:

```json
{
  "state": "idle|starting|downloading|installing|verifying|success|rolling_back|rolled_back|failed",
  "step_label": "Скачивание архива с GitHub…",
  "started_at": 1788900000,
  "finished_at": null,
  "from_version": "0.8.0", "from_commit": "abc1234",
  "to_version": "0.9.0",   "to_commit": "def5678",
  "error": null,
  "log_tail": ["...последние 20 строк update.log..."]
}
```

```yaml
  allow_from_ui: true      # кнопка в веб-интерфейсе (см. §3.3)
  repo_owner: 9043366188-dot
  repo_name: wb-energy-meter
  ref: main
  check_timeout_s: 10
```

Значения по умолчанию задать в коде, чтобы старые конфиги без этой секции
продолжали работать. **Проверьте это отдельно** — на контроллере конфиг
`install.sh` не перезаписывает.

### 4.5. API

- `GET /api/update/check` — сходить на GitHub, вернуть:

  ```json
  {"current": {"version": "0.8.0", "commit": "abc1234", "installed_at": ...},
   "remote":  {"version": "0.9.0", "commit": "def5678",
               "message": "feat: ...", "date": "2026-09-08T10:00:00Z"},
   "update_available": true, "allow_from_ui": true}
  ```

  При `update.enabled: false` → 503. При ошибке сети → 502 с русским текстом.
- `GET /api/update/status` — содержимое файла статуса. Никогда не 500:
  файла нет — вернуть `{"state": "idle"}`.
- `POST /api/update/start` — тело `{"commit": "<sha из check>"}`.
  - `update.enabled: false` → 503; `allow_from_ui: false` → 403.
  - Обновление уже идёт → **409**.
  - `commit` не совпадает с текущим удалённым sha → 409 «версия на GitHub
    изменилась, проверьте ещё раз». Это защищает от установки не того,
    что видел пользователь.
  - Успешный запуск → 202 с текущим статусом.

Все три ручки — в общем стиле `api.py` (`json_response`, русские тексты ошибок).

### 4.6. UI — блок «Обновление» в Настройках

Разместить **первым блоком** на вкладке «Настройки», выше «Зон».

Состояния:

1. **Покой.** «Текущая версия: 0.8.0 · коммит abc1234 · установлена 08.09.2026»
   и кнопка «Проверить обновления».
2. **Проверка идёт** — спиннер `.spin` на кнопке.
3. **Обновлений нет** — «У вас последняя версия» с датой проверки.
4. **Есть обновление** — карточка: новая версия, короткий sha, дата и первая
   строка сообщения коммита, кнопка «Обновить сейчас».
5. **Подтверждение** — диалог в существующем стиле (`confirm-overlay` /
   `confirm-box`): «Сервис будет остановлен и перезапущен. Сбор данных
   прервётся примерно на минуту. База данных будет сохранена, при неудаче
   произойдёт автоматический откат.» Кнопки «Отмена» / «Обновить».
6. **Идёт обновление** — прогресс: текущий шаг из `step_label`, опрос
   `/api/update/status` раз в 2 секунды.

   **Обязательно:** во время перезапуска сервиса запросы будут падать
   (`fetch` бросит исключение или вернёт 502). Это **нормальная часть
   процесса**, а не ошибка. UI должен молча продолжать опрашивать и
   показывать «Сервис перезапускается…». Сдаваться только после **120 секунд**
   подряд неудачных попыток — тогда показать «Не удалось связаться с сервисом.
   Обновите страницу через минуту или проверьте по SSH:
   `journalctl -u wb-energy-meter -n 50`».
7. **Успех** — «Обновлено до 0.9.0» и кнопка «Перезагрузить страницу»
   (`location.reload()`), потому что сам `index.html` тоже обновился.
8. **Откат** — жёлтая плашка: «Обновление не встало, вернулись на 0.8.0»
   плюс раскрывающийся `log_tail`.
9. **Провал** — красная плашка с ошибкой и хвостом лога.

Опрос статуса запускать и при **открытии вкладки** «Настройки»: если
обновление шло, когда пользователь закрыл вкладку, он должен увидеть
результат. Состояния `success` / `rolled_back` / `failed` показывать до тех
пор, пока пользователь не нажмёт «Скрыть» (тогда `POST` не нужен — просто
локальный флаг в Alpine).

существующих (не pytest), без сети. Проверить:

## 8. Чего делать нельзя

- Не добавлять зависимостей (`requests`, `GitPython` и подобное) — только stdlib.
- Не подставлять в URL, пути или shell-команды ничего, что пришло из HTTP-запроса.
  Owner, repo и ref — только из конфига.
- Не выполнять `git` на контроллере: там разворачивается tarball, а не клон.
- Не трогать БД: её резервное копирование уже делает `install.sh`.
  Миграции применяются сами при старте.
- Не ломать поддержку Python 3.9 (CI гоняет 3.9–3.12).
- Не менять формат существующих ответов API — только добавлять.
- Не строить свою систему аутентификации в рамках этой задачи.
