## 2. Что входит в партию

Три задачи, строго в этом порядке.

### Задача 1. Протокол ревизий (делать первой)

Сейчас в `api_v2.py` честно записано: `expected_revision` и проверка
конфликта версий **не реализованы**, данные читаются и пишутся без сверки.
Таблица `configuration_revisions` создана, но не используется.

Последствие: двое, правящих топологию или план одновременно, молча затрут
работу друг друга — последний победил. Чинить это дешевле сейчас, пока
редактирующих экранов мало, чем ретрофитить потом в каждый.

Делать по §6.1 (ревизия на каждую предметную транзакцию), §9.2 (единый
envelope записи `expected_revision` / `effective_from` / `reason` / `data`)
и §11.

Минимально обязательное:

- каждая предметная транзакция создаёт одну глобальную ревизию;
- запись без `expected_revision` либо с устаревшим — **409** с телом по
  §9.2 (`code`, русское `message`, `fields`, затронутые ID, путь конфликта);
- запрос расчёта фиксирует ревизию в начале и работает с одним снимком
  (A43), даже если внутри несколько обращений к репозиториям;
- необязательный `configuration_revision_id` в `metrics/query` позволяет
  повторить расчёт по той же структуре.

**Не держать транзакцию SQLite открытой на время сетевого ожидания** —
это прямо запрещено §6.1 и на контроллере с SD-картой обернётся
блокировками.

Покрыть тестами A35 (две сессии правят один план — 409, чужое не
перезаписано) и A43 (конфигурация меняется во время запроса — внутри
запроса один снимок).

### Задача 2. Обзор (§8.2)

Экран отвечает на четыре вопроса: сколько потребляет объект, какие ветви
дают расход, где проблема, каких данных нет.

Обратить внимание на то, что легко сделать неправильно:

- **Итог — не сумма всех счётчиков.** Основа итога — назначенный ввод.
  Если ввод не назначен, показывать не ложный итог, а действие
  «Настроить границу объекта».
- У каждого итога — «Из чего рассчитано»: точки, каналы, формула,
  исключённые дубликаты, период, качество.
- Небаланс — отдельной строкой, знак сохраняется; отрицательный остаток
  не рисовать отрицательным сектором.
- Никаких pie/donut из пересекающихся групп. Sankey в эту версию не входит.
- Различать «нет прибора», «нет данных», «нет связи», «архив» — это
  четыре разных состояния, а не одно (A10).
- Проценты не считать при нулевой или отсутствующей базе — `null` с
  причиной, без фиктивных 100% (A11).

Показатели — компактной строкой, а не рядом одинаковых декоративных
карточек. Первые 5–8 ветвей, остальное — сворачиваемое «Остальные» с
точным составом.

### Задача 3. Отчёты и экспорт (§8.4)

Существующие отчёты **сохранить** и перевести на расчёт v2, добавив новые
измерения: точка, ветвь, группа, граница баланса. Отчёт всегда несёт
выбранный состав, период, часовой пояс, режим исторической структуры,
источник и качество.

CSV — отдельно внимательно, тут четыре типовые ошибки:

- `null` экспортируется **пустым полем**, а не нулём (A10);
- отдельные колонки качества, известной суммы, единиц, границ периода и
  основания расчёта;
- значения, начинающиеся с `=`, `+`, `-`, `@`, экспортировать безопасно
  как текст — иначе это внедрение формул в Excel (A45); при этом
  **числовой отрицательный небаланс обязан остаться числом**;
- CSV и экран используют один расчёт и совпадают до заявленного
  округления (A43).

В сравнении периодов раскрывать различие состава и замен (A21, A22).

## 3. Чего в эту партию НЕ входит

- Инспектор объекта и однолинейная схема вторым холстом — остаток этапа D,
  следующая партия.
- Мастер переноса старых связей в электросеть — следующая партия.
- Провижининг нового прибора в `replace-meter`, `validation`,
  `metrics/jobs`, `migration/status` — следующая партия.
- **Адаптивность и смена viewport (§8.5) — сознательно отложены.**
  Сейчас `<meta name="viewport" content="width=1100">`; замена на
  `device-width` меняет вёрстку **всех** вкладок, включая классический
  набор, который сегодня является рабочим интерфейсом объекта. Проверить
  вёрстку без браузера невозможно, а вслепую ломать продакшен-интерфейс
  нельзя. Делать вместе с живым прогоном в браузере, отдельной партией.
- Тарифы, начисления, распределение затрат, Sankey, АВР/ДГУ, кольцевые
  сети — отложено большим ТЗ, §12.

## 4. Ограничения проекта

Это не общие слова — каждый пункт уже стоил рабочего контроллера.

- **Только стандартная библиотека Python** плюс уже используемые flask,
  paho-mqtt, pyyaml. Никаких новых зависимостей, в том числе в тестах
  (Pillow пришлось выкорчёвывать отдельной задачей).
- **На контроллере Debian bullseye:** Python 3.9, Flask 1.1.2,
  Werkzeug 1.0.1. Прежде чем взять что-то из Flask/Werkzeug — проверить,
  есть ли оно в этих версиях. Есть job `legacy-deps` в CI, он для этого.

- Вкладка «План» — единственная на `x-show` (из-за Leaflet), остальные на
  `<template x-if>`. Не переводить прочие вкладки заодно.
- Не менять формат существующих ответов API — только добавлять.
- Не трогать миграцию 005 и существующие данные.
- Подробности по всем граблям — в `AGENTS.md`, прочитать до начала.

## 5. Переключение интерфейса по умолчанию

В `index.html` есть константа `DEFAULT_UI_SET = 'classic'`. Сейчас по
умолчанию открывается классический набор, потому что в новом не было
отчётов и пользователя нельзя было отправлять на пустую витрину.

**Флип на `'v2'` — последним шагом партии и только если** обзор и отчёты
из задач 2 и 3 работают на реальных данных, а классический набор остаётся
доступен через переключатель в углу шапки. Если хоть один из отчётов не
переведён — оставить `'classic'` и явно написать об этом в отчёте.

Классический набор в этой партии **не удалять**: он остаётся запасным
путём, пока новый не отработает на объекте.

## 6. Проверка

Тесты гонять на **двух** наборах версий — именно несовместимость со
старыми библиотеками дважды роняла контроллер:

```bash
pip install "paho-mqtt>=1.6,<3" "pyyaml>=5.4" "flask>=1.1" --break-system-packages

python3 -m venv /tmp/venv_old
/tmp/venv_old/bin/pip install "flask==1.1.2" "werkzeug==1.0.1" \
    "jinja2<3" "itsdangerous<2" "markupsafe<2" "paho-mqtt>=1.6,<3" "pyyaml>=5.4"
```

Тесты — самостоятельные скрипты, запускать по одному
(`python3 tests/<файл>.py`), не pytest. `test_step3_daemon`,
`test_step3_e2e`, `test_step4_daemon` требуют mosquitto и в песочнице
падают — ожидаемо.

Новые тесты **добавить в оба job'а** `ci.yml`. Имя шага, содержащее
`": "`, обязательно в кавычках — иначе YAML невалиден и GitHub Actions
молча не запускает workflow целиком.

Кроме тестов: `compileall`, `bash -n` по `scripts/*.sh`, баланс тегов
`index.html` **скриптом** (комментарии вырезать ДО скриптов и стилей —
слово `<script>` внутри комментария сбивает наивный разбор),
`node --check` по каждому инлайн-блоку JS, `yaml.safe_load` по `ci.yml`.

**Численные критерии — независимыми числами.** Большое ТЗ, §13: допуск
0,000001 кВт·ч, и нельзя доказывать расчёт сравнением двух экранов,
использующих одну и ту же функцию. Обязательно закрыть: A03, A04, A08,
A10, A11, A21, A22, A35, A43, A45.
