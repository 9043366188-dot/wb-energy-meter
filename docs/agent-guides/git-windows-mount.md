# Git в Linux на Windows-mounted checkout

Читайте эту инструкцию только если Git запускается из Linux на checkout,
смонтированном с диска Windows, или Git сообщает Operation not permitted
при удалении файла либо .git/*.lock: File exists.

На таком монтировании Git может не удалить lock-файл после завершившейся
операции. Раньше это проявлялось ошибкой создания следующего lock-файла.
Предупреждение unable to unlink для временного объекта само по себе не
означает, что нужно перемещать файлы.

## Проверка перед перемещением lock-файла

1. Остановите другие Git-операции для этого checkout и проверьте процессы
   Git в Linux:

   ~~~bash
   ps -eo pid=,args= | grep -E '[g]it([[:space:]]|$)|[g]it-remote-'
   ~~~

2. Проверьте, что на Windows-хосте не выполняется другая Git-операция.
   Найдите git.exe; если GitHub Desktop или другой клиент открыт и его
   состояние неясно, закройте клиент до восстановления lock-файла:

   ~~~powershell
   Get-Process -Name git -ErrorAction SilentlyContinue
   ~~~

3. Перемещайте lock-файл только после проверки, что ни один Git-процесс
   не активен ни в Linux, ни на Windows-хосте. Если проверить обе стороны
   невозможно или процесс ещё работает, не трогайте lock-файл: дождитесь
   завершения операции либо штатно остановите её.
4. Перемещайте только путь lock-файла, названный в ошибке, и только после
   проверки, что он остался после завершения процесса. Сохраните его в
   .git/_trash/ на том же диске:

   ~~~bash
   mkdir -p .git/_trash
   lock=.git/index.lock
   if [ -e "$lock" ]; then
     mv -- "$lock" ".git/_trash/$(basename "$lock").$(date +%s%N)"
   fi
   ~~~

   Замените lock точным путём из ошибки, например .git/HEAD.lock или
   .git/objects/maintenance.lock.
5. Повторите только ту Git-команду, которая завершилась с ошибкой. Не
   проверяйте и не перемещайте lock-файлы перед каждой командой или после
   успешной операции. Если ошибка повторяется, остановитесь и выясните,
   какой процесс или другой сбой удерживает файл.

## Ограничения репозитория

- Не редактируйте файлы в .git/refs/ вручную и не запускайте git gc,
  git prune или git repack в этом checkout.
- Не используйте --force. По умолчанию оставляйте публикацию ветки
  пользователю через GitHub Desktop; явный запрос пользователя на PR или
  push разрешает нужную для этого публикацию.
- Перед передачей результата проверьте git status --short и укажите
  оставшиеся изменения. Не удаляйте файлы из .git/_trash/ как часть
  восстановления lock-файла.
