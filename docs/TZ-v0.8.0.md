## 2. Реестр дефектов

### 2.1. Группы/зоны — критично

**A1. Назначенная группа не доезжает до дашборда и отчётов.**

Корневая причина. `/api/status` и `/api/meters` строят ответ из
in-memory `MeterRegistry`, а `MeterState.group` заполняется единственным
вызовом `registry.apply_registry_config(...)` в `main.py:80` — **только при
старте демона**. `PATCH /api/registry/meters/<id>` пишет группу в SQLite, но
in-memory реестр не трогает. `_build_status()` (`api.py:45-60`) подтягивает из
БД только `notes` и `role`, `group` — нет.

Следствие: пользователь назначает зону в «Настройках», ответ 200 OK, в таблице
реестра зона видна, а на дашборде счётчик остаётся в «— Без зоны —» до
перезапуска сервиса. Ровно это описано как «не распределяет в итоге счётчик
в группу».

Подтверждение (прогон через `test_client`):

```
PATCH /api/registry/meters/wb-map3e_21  {"group":"Цех1"}  -> 200 {"group":"Цех1"}
GET   /api/registry/meters  -> group_name = "Цех1"        (БД в порядке)
GET   /api/status           -> meters[0].group = None     (дашборд слепой)
```

Затронуто: `groupedMeters` на дашборде, «Ведомость расхода»
(`/api/summary/consumption` → `m.group`, `api.py:269,275`), «Сравнение
периодов», `/api/meters/<id>/consumption` (`api.py:204`), модалка деталей.

**A2. Снять группу через UI/API невозможно.**

`api.py:399`: `kwargs["group"] = (body["group"] or "").strip() or None` —
пустая строка превращается в `None`. `MeterRepo.update` (`repo.py:228`):
`if group is not None:` — `None` пропускается. Итог: PATCH `{"group":""}`
возвращает 200 и **ничего не меняет**.

Подтверждено: после `PATCH {"group":""}` счётчик остался в «Цех1».

**A3. Переименование зоны меняет её id и теряет историю.**

`api_registry_group_rename` (`api.py:606-638`) не делает
`UPDATE meter_groups SET name = ?`, а вызывает `get_or_create(new_name)`,
перепривязывает счётчики и удаляет старую строку. В `GroupRepo` метода
переименования просто нет. Следствия: id зоны меняется, `created_at`
теряется, цвет зоны (детерминирован от имени в `zoneColor()`) меняется.

**A4. `COLLATE NOCASE` не работает для кириллицы.**

SQLite `NOCASE` сворачивает только ASCII A–Z. Уникальность
`meter_groups.name COLLATE NOCASE` для русских имён не работает: «Цех1» и
«ЦЕХ1» — две разные зоны.

Подтверждено: переименование «Цех2» → «ЦЕХ2» **создало новую зону id=3**
вместо переименования; в списке зон появились обе.

**A5. Тихое слияние зон.** Переименование в имя существующей зоны молча
сливает счётчики. Подтверждено: «ЗонаB» → «Цех1» дало «Цех1» с 2 счётчиками
без единого предупреждения.

**A6. Кривая вёрстка строки редактирования — «само меню кривое».**

`static/index.html:484-546`. Заголовки таблицы:
`Имя | Группа | Комментарий | Роль | device_id | Serial | Действия`.
А `<td>` в режиме редактирования идут в порядке:
`Имя | Комментарий | Роль | Группа | device_id | Serial | Действия` —
поле «Группа» отрисовано **после** роли (строки 533-544), а колонка «Группа»
в этот момент занята комментарием. Все поля съезжают на чужие колонки.

**A7.** `colspan="5"` в пустой строке реестра (`index.html:568`) при
7 колонках в `<thead>`.

**A8. Группа задаётся свободным текстом.** `<input list="groups-list">`
вместо выбора из списка: опечатка молча создаёт зону-дубль, нет пункта
«Без зоны». Плюс `<datalist id="groups-list">` отрисовывается **внутри
`x-for` по счётчикам** — дублирующиеся id в DOM, невалидный HTML.
То же со вторым списком `groups-list2` (`index.html:626-630`).

**A9.** Нет массового назначения: чтобы разложить 20 счётчиков, нужно
20 раз открыть/сохранить строку.

**A10.** Цвет зоны выводится из имени хешем, в БД не хранится, при
переименовании меняется.

## 3. Задача 1 — починить группы (приоритет P0)

### 3.1. Синхронизация группы БД → in-memory реестр

Это ядро проблемы. Требование: **после любого изменения группы в БД
`/api/status` немедленно отдаёт новое значение, без перезапуска сервиса.**

Реализация — два уровня, сделать оба:

1. **Push при записи.** В `api.py` после каждой успешной операции, меняющей
   привязку счётчика к зоне, обновлять `MeterRegistry`. Добавить в
   `MeterRegistry` (`model.py`) метод:

   ```python
   def set_group(self, device_id: str, group: Optional[str]) -> None:
       with self._lock:
           m = self._meters.get(device_id)
           if m is not None:
               m.group = group
   ```

   и вызывать его из:
   - `api_registry_meter_update` (PATCH счётчика),
   - `api_registry_meter_add` (POST счётчика),
   - `api_registry_group_rename` (для всех перепривязанных счётчиков),
   - `api_registry_group_delete` (сброс в `None`).

   Лучше — одна приватная функция `_sync_registry_groups(state)`, которая
   перечитывает `meters_repo.list_all()` и раскладывает `group_name`
   по реестру; вызывать её в конце каждого из четырёх обработчиков.
   Так надёжнее, чем точечные апдейты.

2. **Периодическая пересинхронизация.** В `BackgroundTasks._run`
   (`background.py`) рядом с `_sync_serials()` добавить `_sync_groups()`:
   раз в интервал перечитывать реестр из БД и обновлять `group` и
   `display_name` в памяти. Это страховка от рассинхрона по любой причине.

   Важно: `apply_registry_config` **создаёт** отсутствующие `MeterState`.
   Для периодической синхронизации это допустимо и даже полезно (счётчик
   в БД есть, в MQTT ещё не появился), но убедитесь, что статус такого
   счётчика остаётся `UNKNOWN`/`NO_CONNECTION`, а не «ок».

### 3.2. Снятие группы

- `api.py:398-399`: различать «ключ не передан» и «передана пустая строка».

  ```python
  if "group" in body:
      raw = body["group"]
      kwargs["group"] = "" if raw in (None, "") else str(raw).strip()
  ```

- `repo.py MeterRepo.update`: сохранить текущую семантику (`group=""` → NULL,
  `group=None` → не трогать) — она уже правильная, ломается только на уровне API.
- Проверить, что `PATCH {"group": ""}` и `PATCH {"group": null}` оба снимают
  зону и `/api/status` сразу отдаёт `group: null`.

### 3.3. Честное переименование зоны

- Добавить `GroupRepo.rename(gid, new_name)` → `UPDATE meter_groups SET name = ?
  WHERE id = ?`. Id и `created_at` сохраняются.

  - если существует **другая** зона с таким именем (сравнение

## 4. Задача 2 — история значений по параметру (приоритет P0)

Требование пользователя: **клик по любому параметру счётчика открывает график
истории его значений.**

### 4.1. Новый API-эндпоинт

```
GET /api/meters/<device_id>/channel-history?control=<name>&period=<preset>
GET /api/meters/<device_id>/channel-history?control=<name>&from=...&to=...
```

Реализация в `api.py`:

- Разбор периода — существующий `_parse_period_from_request()` + `build_period()`
  (поддержит и пресеты, и произвольный диапазон).
- Данные — `state.wb_db_client.get_values(device_id, control, ts_from, ts_to,
  limit=..., min_interval_ms=...)`.
- `control` обязателен; без него — 400.
- Если `wb_db_client is None` — 503, как в соседних ручках.
- `RpcError` → 502 (как в `api_meter_consumption`).
- **Прореживание.** Точек может быть десятки тысяч. Передавать в RPC
  `min_interval_ms`, рассчитанный от длины периода так, чтобы вернулось
  не больше ~1500 точек:
  `min_interval_ms = max(1000, int((ts_to - ts_from) * 1000 / 1500))`.
  Плюс жёсткий `limit=5000` как страховка.
- Ответ:

  ```json
  {
    "device_id": "wb-map3e_21",
    "control": "Urms L1",
    "label": "Напряжение L1",
    "units": "В",
    "period": { ... },
    "points_count": 1440,
    "min": 221.4, "max": 236.8, "avg": 229.1, "last": 230.2,
    "items": [{"t": 1757000000, "v": 230.1}, ...]
  }
  ```

  `min/max/avg` считать на сервере — фронту это нужно для осей и сводки.
  Пустая история — не ошибка: `items: []`, `points_count: 0`.

### 4.2. Кэш RPC-соединения (D3)

`WbDbClient._call` поднимает новое MQTT-соединение на каждый вызов. С графиками
это станет узким местом. Сделать переиспользуемое соединение: один долгоживущий
клиент с `loop_start()`, подписка на общий wildcard-топик ответов,
`request_id` → `threading.Event` в словаре под локом; при обрыве — переподключение
и фолбэк на текущее поведение «соединение на вызов».

**Грабли (из AGENTS.md):** с paho-mqtt 2.x при QoS=1 `wait_for_publish()`
виснет навсегда без `loop_start()`. Убедитесь, что `loop_start()` вызывается
сразу после `connect()`.

Если рефакторинг окажется рискованным — допустимо ограничиться троттлингом на
фронте (не чаще одного запроса истории в 300 мс) и оставить `_call` как есть,
но тогда явно записать это в CHANGELOG как известное ограничение.

### 4.3. UI графика

В модалке деталей счётчика: клик по плитке параметра открывает область графика
**внутри той же модалки** (не вложенная модалка — со вложенными оверлеями будет
каша). Поведение:

- Заголовок: русское название + единицы + `device_id`.
- Кнопки периода: `Час`, `Сутки`, `Неделя`, `Месяц` + поля произвольного
  диапазона (переиспользовать разметку из вкладки «Отчёты»).
- Линейный SVG-график по образцу `renderProfileSvg()` — тот же стиль,
  сетка, подписи осей, `var(--accent)` / `var(--line)` / `var(--txt3)`.
  Не подключать внешние библиотеки: сборки нет, Alpine.js с CDN, SVG строится
  строкой — так уже сделано в двух местах, придерживайтесь этого.
- Сводка над графиком: мин / макс / среднее / последнее.
- Состояния: загрузка (`.spin`), «нет данных за период», ошибка RPC
  («История недоступна: wb-mqtt-db не отвечает»).

## 5. Задача 3 — русификация и категоризация параметров (приоритет P0)

Требование: перевести параметры на русский, разбить по категориям, основные —
наверх, остальные — в раскрывающихся группах, при наведении — краткая подсказка
по-русски.

### 5.1. Где хранить словарь

Создать **`wb_energy_meter/channels.py`** — единый источник правды:

```python
CHANNEL_INFO = {
    "Urms L1": {
        "label": "Напряжение L1",
        "units": "В",
        "hint": "Действующее (среднеквадратичное) напряжение фазы L1 "
                "относительно нейтрали. Норма 198–253 В.",
        "category": "voltage",
        "main": True,
    },
    ...
}
CATEGORIES = [
    {"id": "main",    "label": "Основные",          "open": True},
    {"id": "voltage", "label": "Напряжение",        "open": False},
    ...
]
```

Отдавать словарь на фронт новым эндпоинтом `GET /api/channels/dictionary`
(кэшируемый, `Cache-Control: public, max-age=3600`) и дополнительно
подмешивать `label`/`units`/`hint`/`category` прямо в `_meter_detail`
(`api.py:81-109`) — чтобы модалка работала одним запросом.

**Не хардкодить словарь в HTML** — он понадобится и для CSV, и для
графиков, и для будущих отчётов.

### 5.2. Правила сопоставления

- Точное совпадение по имени канала.
- Если точного нет — сопоставление по шаблону с номером фазы:
  `"Urms L%d"`, `"Irms L%d"`, `"P L%d"` и т. д. (L1/L2/L3), чтобы не
  дублировать по три записи руками.
- Если ничего не подошло — `label = имя канала как есть`,
  `category = "other"`, `hint = None`. **Незнакомый канал обязан
  отображаться**, а не пропадать. Это ключевое требование: прошивки WB-MAP3E
  различаются, набор каналов плавает.
- Единицы брать из словаря; если в `meta` устройства пришли свои (`meta.units`) —
  приоритет у `meta`. Для этого добавить `units` в ответ `_meter_detail`
  (сейчас его там нет — см. C3).

### 5.3. Категории и состав

| id | Название | Что входит | Раскрыто по умолчанию |
|----|----------|-----------|----------------------|
| `main` | Основные | `Total P`, `Total AP energy`, `Urms L1/L2/L3`, `Irms L1/L2/L3`, `Frequency` | да |
| `voltage` | Напряжение | `Urms L*`, `Upeak L*`, линейные напряжения, углы напряжения | нет |
| `current` | Ток | `Irms L*`, `Ipeak L*` | нет |
| `power` | Мощность | `P L*`, `Q L*`, `S L*`, `Total P/Q/S`, `PF*` (коэфф. мощности), углы фаз | нет |
| `energy` | Энергия | `AP energy*`, `AN energy*`, `RP energy*`, `RN energy*`, `Total * energy` | нет |
| `quality` | Качество сети | `Frequency`, гармоники, перекос фаз | нет |
| `service` | Служебные | `Serial`, `Uptime`, `MCU Temperature`, `MCU Voltage`, `Supply voltage` | нет |
| `other` | Прочее | всё, что не опознано | нет |

Блок «Основные» — плоская сетка наверху, без сворачивания. Остальные —
`<details>`/`<summary>` или собственный аккордеон на Alpine
(`x-data="{open:false}"`), в заголовке — название категории и число
параметров: `Напряжение · 9`. Пустые категории не рендерить.

Состояние раскрытых категорий запоминать в `localStorage`
(ключ `wbem.detailCats`), обернув чтение и запись в `try/catch` —
как это уже сделано для темы (`index.html:1332-1333`).

### 5.4. Словарь-заготовка

Ниже — базовый набор. Дополнить по фактическому списку каналов с боевого
контроллера `192.168.10.212` (`GET /api/meters/<id>` вернёт все `controls`).
Формулировки подсказок — короткие, одно-два предложения, для инженера-энергетика,
**без воды**.

| Канал | Название | Ед. | Подсказка |
|-------|----------|-----|-----------|
| `Urms L1/L2/L3` | Напряжение L1/L2/L3 | В | Действующее напряжение фазы относительно нейтрали. Норма 198–253 В. |
| `Upeak L1/L2/L3` | Пиковое напряжение L1/L2/L3 | В | Максимальное мгновенное значение напряжения за период измерения. |
| `Irms L1/L2/L3` | Ток L1/L2/L3 | А | Действующий ток фазы. Считается с учётом коэффициента трансформации. |
| `Ipeak L1/L2/L3` | Пиковый ток L1/L2/L3 | А | Максимальное мгновенное значение тока — показывает пусковые броски. |
| `P L1/L2/L3` | Активная мощность L1/L2/L3 | кВт | Мощность, которая реально совершает работу. |
| `Total P` | Активная мощность, сумма | кВт | Суммарная активная мощность по трём фазам. Основной показатель нагрузки. |
| `Q L1/L2/L3` | Реактивная мощность L1/L2/L3 | квар | Мощность обмена с индуктивной и ёмкостной нагрузкой, работы не совершает. |
| `Total Q` | Реактивная мощность, сумма | квар | Суммарная реактивная мощность. Высокие значения — повод для компенсации. |
| `S L1/L2/L3` | Полная мощность L1/L2/L3 | кВА | Геометрическая сумма активной и реактивной мощности. |
| `Total S` | Полная мощность, сумма | кВА | По ней выбирают сечение кабеля и номинал трансформатора. |
| `PF L1/L2/L3` | Коэффициент мощности L1/L2/L3 | — | cos φ: отношение активной мощности к полной. Ниже 0,9 — плохо. |
| `Total PF` | Коэффициент мощности, сумма | — | Общий cos φ по объекту. |
| `Frequency` | Частота сети | Гц | Норма 50 ± 0,2 Гц. Отклонения — признак проблем в питающей сети. |
| `Total AP energy` | Активная энергия, потреблено | кВт·ч | Нарастающий счётчик потреблённой активной энергии. Основа для расчёта расхода. |
| `Total AN energy` | Активная энергия, отдано | кВт·ч | Нарастающий счётчик отданной в сеть энергии (генерация, рекуперация). |
| `Total RP energy` | Реактивная энергия, потреблено | квар·ч | Нарастающий счётчик потреблённой реактивной энергии. |
| `Total RN energy` | Реактивная энергия, отдано | квар·ч | Нарастающий счётчик отданной реактивной энергии. |
| `AP energy L1/L2/L3` | Активная энергия L1/L2/L3 | кВт·ч | Пофазный нарастающий счётчик активной энергии. |
| `Phase angle L1/L2/L3` | Угол фазы L1/L2/L3 | ° | Сдвиг между током и напряжением фазы. |
| `Voltage angle L1/L2/L3` | Угол напряжения L1/L2/L3 | ° | Взаимный сдвиг фазных напряжений, в норме около 120°. |
| `Serial` | Серийный номер | — | Заводской номер счётчика, используется для сверки с актом установки. |
| `Uptime` | Время работы | с | Сколько счётчик работает без перезагрузки. |
| `MCU Temperature` | Температура контроллера | °C | Температура процессора счётчика. |
| `MCU Voltage` | Напряжение питания МК | В | Внутреннее напряжение питания счётчика. |
