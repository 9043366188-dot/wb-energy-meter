# Находки пилота

Файл для агента следующей партии (`docs/TZ-finish-plan.md`, §12, шаг 4).
Находки разбираются **первыми**, раньше плановых этапов партии. Каждая —
с тестом и строкой в отчёте сдачи. Закрытую находку не удалять, а
пометить «закрыто в партии NN, PR #…».

Находки с пометкой **«блокирует пилот»** делаются отдельной партией
находок (§12, шаг 2): только они, выпуск — патч-версия, номер следующей
партии не сдвигается. Такие были П1–П7 — все закрыты партией
13-findings (PR #11, выпуск 0.22.2). П8–П11 (решение Кира от 18.10.2026 —
R13; П11 — нестабильный CI) закрыты партией находок 13-findings-0.22.3
(выпуск 0.22.3, PR — в строке «Закрыто» у каждой). П12 (эмулятор
счётчиков, решение Кира R17 от 21.10.2026) закрыта партией находок
13-findings-0.23.1 (выпуск 0.23.1, PR #22); следующая сессия — партия 14.
Пилот на контроллере ещё не проводился.

Контекст: все данные на контроллере тестовые (решение R9). Полностью
стереть их — чистым стартом (`docs/pilot-checklist.md`, раздел 2), а не
кнопками интерфейса. Находки ниже — о том, чего не хватает для
нормальной работы с данными, которые заводятся заново.

## П1. В интерфейсе нельзя удалить точку, узел, линию и убрать узел с плана

**Блокирует пилот.**

**Закрыто в партии 13-findings, PR #11** (выпуск 0.22.2; таблица сдачи — в описании PR).

**Сообщил Кир, 11.10.2026:** созданные точки учёта не удалить; часть из
них пришла из старых планов («План v2»); то, что размещено на плане,
остаётся там навсегда, или непонятно, где это править.

**Проверено по коду 0.22.0.** Сервер это умеет:

| Действие | Маршрут |
|---|---|
| Архивировать точку учёта | `PATCH /api/v2/points/<id>` с `archived` (`MeteringPointRepo.archive`, A39) |
| Архивировать узел | `PATCH /api/v2/topology/nodes/<id>` с `archived` (`topology_service.archive`) |
| Вывести линию из работы | `PATCH /api/v2/topology/edges/<id>` с `retire` |
| Убрать элемент с плана | `DELETE /api/v2/plans/<id>/items/<item_id>` |
| Удалить план (только представление, A27) | `DELETE /api/v2/plans/<id>` |

В интерфейсе «Плана v3» и «Структуры» ни одного из этих действий нет. В
«Структуре» архивируется только место и снимается членство точки в
группе.

**Нужно** (на языке интерфейса, всё через протокол ревизий, при 409 —
понятный текст, черновик не теряется):

1. **Точка учёта** — карточка в «Структуре» и в «Плане v3»: «Архивировать
   точку» с подтверждением и пояснением: «История сохраняется; из
   текущего состава, итогов и балансов точка уходит с этого момента».
   Архивные точки скрыты из списков; переключатель «Показать архивные».
2. **Узел** — карточка узла в «Плане v3»:
   - «Убрать с плана» — удаляется только значок на этом плане; узел
     остаётся в схеме и появляется в списке «Неразмещённые»;
   - «Архивировать узел». Если у узла есть действующие линии — сообщение,
     какие именно мешают, и предложение сначала вывести их из работы
     (или вывести вместе с узлом одной ревизией — решает агент, с
     обоснованием в отчёте).
3. **Линия** — карточка линии: «Вывести из работы» с подтверждением; с
   этого момента она не участвует в итогах и балансах, история
   сохраняется.
4. **План** — выбор плана в «Плане v3»: «Удалить план» с подтверждением.
   Удаляется только представление; узлы, линии, точки и история
   остаются (A27).
5. **Тесты.** API — «отказ + легитимный запрос» и перечитывание сущности.
   Браузерный сценарий: создать узел и точку → убрать узел с плана →
   архивировать точку → её нет в списках и в итоге «Обзора», запись есть
   в «Истории».

Полное удаление записей из БД в рабочей системе не делается (большое ТЗ
§9.2: архивирование — PATCH состояния, не DELETE истории).

## П2. Непонятно, чем «узел» отличается от «щита»

**Блокирует пилот.**

**Закрыто в партии 13-findings, PR #11** (выпуск 0.22.2; таблица сдачи — в описании PR).

**Сообщил Кир, 11.10.2026.**

**Проверено по коду 0.22.0.** Слово «узел» нигде не объяснено, а один и
тот же тип подписан по-разному в трёх выпадающих списках
`static/index.html`:

| Значение `kind` | ≈стр. 1831–1834 | ≈стр. 2426–2429 («План v3», «+ Узел») | ≈стр. 2603–2606 |
|---|---|---|---|
| `source` | Ввод (источник) | Ввод (источник) | Ввод |
| `panel` | Щит | Щит | Щит |
| `junction` | Узел разветвления | Промежуточный узел | **Узел** |
| `load` | Нагрузка | Потребитель | Нагрузка |

Кнопка в «Плане v3» называется «+ Узел», а по умолчанию создаёт «Щит».

**Нужно:**

1. Одни названия типов везде, на языке энергетика, из одного места в коде
   (общий словарь в `core.js`, а не три копии в разметке):
   - **Ввод** — откуда приходит питание (граница объекта);
   - **Щит** — распределяет питание, от него отходят линии;
   - **Ответвление** — точка разветвления без щита (бывший «узел
     разветвления / промежуточный узел»);
   - **Нагрузка** — конечный потребитель.
   Окончательные слова агент может уточнить по UX-копирайту, но одно
   слово — одно значение везде.
2. Слово «узел» в интерфейсе не использовать как название типа. Кнопку
   «+ Узел» переименовать по смыслу, например «+ Ввод / щит / нагрузка»
   или «+ Элемент схемы».
3. В форме создания и в карточке узла — тип крупно и одна строка
   пояснения. Отдельно сказать, что **счётчик ставится на линию**, а не на
   узел.
4. Подсказка на пустом «Плане v3»: «Схема — это вводы, щиты и нагрузки,
   соединённые линиями. Счётчик ставится на линию: тогда видно, сколько
   прошло по ней».
5. Те же слова — в «Структуре», «Обзоре», отчётах и в
   `docs/pilot-checklist.md` (раздел 3).
6. Эталон `tests/fixtures/app_keys_baseline.json` — по §2.7 задания;
   браузерный тест проверяет, что во всех трёх списках одинаковые
   подписи.

## П4. Точка учёта создаётся наполовину, прибор предлагается занятый

**Блокирует пилот.**

**Закрыто в партии 13-findings, PR #11** (выпуск 0.22.2; таблица сдачи — в описании PR).

**Проверено по коду 0.22.1.** «+ Точка учёта» в «Структуре»
(`structure.js::structSubmitPoint`, ≈стр. 682–730) делает два запроса:
`POST /api/v2/points`, затем `POST /api/v2/points/<id>/bindings`. Если
второй отказал — точка остаётся без прибора («создана, но привязка не
удалась»). Список приборов — `structKnownDevices` (`index.html`
≈стр. 1797–1801): все известные, включая занятые другой точкой. При этом
в коде уже есть и то и другое правильно: список свободных —
`plan-v3.js::planV3DevicesWithoutPoint()`, создание одной ревизией —
`POST /api/v2/topology/edges/<id>/attach-new-point` (точка + привязка +
«измеряет эту линию» одной транзакцией).

**Нужно:**

1. Нигде в наборе v2 не создавать точку и привязку двумя запросами.
   Форма «+ Точка учёта» в «Структуре» заменяется действием П5 (точка без
   линии в новом интерфейсе не заводится; если агент найдёт причину её
   оставить — тогда одна серверная операция и обоснование в отчёте).
2. Во всех списках выбора прибора — только свободные. Занятый, если
   показан, — серым: «занят точкой «…»».
3. Отказ сервера — человеческим текстом, без `scope`, `channel_profile`,
   `valid_from` и номеров записей; черновик формы не теряется.
4. Тест: занятый прибор в список не попадает; попытка привязать занятый
   через API — 409 и **ни одной новой записи** (точек, привязок,
   ревизий).

## П5. «Щит со счётчиком»: счётчик добавляется в узел схемы

**Блокирует пилот.** Решение Кира — R10.

**Закрыто в партии 13-findings, PR #11** (выпуск 0.22.2; таблица сдачи — в описании PR).

Кир мыслит так: создал узел, назвал, дал тип «Щит» — и добавил в него
живой счётчик. Сейчас для этого нужно: узел → линия → карточка линии →
«＋ новая точка из прибора». Модель расчёта не меняется (точка учёта
по-прежнему измеряет **линию**); меняется путь в интерфейсе.

**Нужно:**

1. В карточке узла («План v3» и «Структура» — одна и та же карточка)
   кнопка **«+ Счётчик»**: список свободных приборов (П4) → имя (по
   умолчанию — имя прибора) → вопрос **«Что измеряет этот счётчик?»**:
   - **Щит:** ● «Ввод щита — всё, что щит потребляет» (по умолчанию) ○
     «Отходящую линию → [нагрузка из списка | + новая нагрузка: имя]».
   - **Ввод:** отходящую линию (если их несколько — выбрать к чему).
   - **Нагрузка:** её входящую линию.
2. Если нужной линии ещё нет — она создаётся тем же действием:
   - ввод щита без входящей линии → «Откуда щит питается?» (список вводов
     и щитов схемы);
   - отходящая линия к новой нагрузке → нагрузка создаётся и ставится на
     план рядом со щитом.
3. Всё — **одной ревизией**: линия (если нужна), узел нагрузки (если
   нужен), точка, привязка, «измеряет линию». Сбой — ничего не создано.
   Новая серверная операция (например, `POST
   /api/v2/topology/nodes/<id>/meters`) поверх тех же сервисов, что
   `edges/connect` и `edges/<id>/attach-new-point`; формат и коды отказов —
   по `CODING_STANDARDS.md`.
4. Карточка узла показывает его счётчики: «wb-map3e_16 — ввод щита»,
   «wb-map12e_3 канал 2 — линия к «Станок»», с действием «Убрать счётчик»
   (П1: точка архивируется, история остаётся).
5. На плане значок узла показывает, что в нём есть счётчик (число или
   метка).
6. Тесты: API — каждый вариант (ввод щита с линией и без, отходящая к
   существующей и к новой нагрузке, ввод, нагрузка), отказ на занятом
   приборе без новых записей, перечитывание. Браузер: щит → «+ Счётчик» →
   баланс щита и «Обзор» видят точку.

## П6. «Структура» = та же схема, без отдельных «мест»

**Блокирует пилот.** Решение Кира — R11.

**Закрыто в партии 13-findings, PR #11** (выпуск 0.22.2; таблица сдачи — в описании PR).

**Проверено по коду 0.22.1.** Дерево слева в «Структуре» — места
(`structLocationRows()`, `index.html` ≈стр. 1238–1262): помещения,
отдельная сущность. Щиты и нагрузки из «Плана v3» туда не попадают,
поэтому «на карте одно, в Структуре другое». Разрезов отчётов по местам
нет (`reports_service.py`: `point`, `branch`, `group`); места видны ещё в
«Обзоре» — проверка «нет места» (`overview-v2.js`, `no_location`) и в
таблице точек «Структуры» (столбец «Чего не хватает»).

**Нужно:**

1. Дерево «Структуры» строится по опубликованной схеме: Ввод → Щит →
   (Щит …) → Нагрузка; у каждого узла — его счётчики (П5) и текущие
   мощность и энергия из того же снимка, что и «Обзор». Клик — та же
   карточка узла, что в «Плане v3».
2. Сверху «Не на схеме»: точки без линии (если такие остались) и
   «Приборы без точки учёта» — с переходом к «+ Счётчик».
3. Места в наборе v2 не показываются нигде: ни в дереве, ни в формах, ни
   в проверках («нет места» убрать из «Обзора» и из «Чего не хватает»).
   API мест и данные остаются (большое ТЗ §9.2: удаление — не DELETE
   истории); классический набор не трогать.
4. Поиск остаётся: имя, код, MQTT ID, серийник — по узлам и точкам.
5. Учётные группы («Структура» сейчас их тоже показывает) остаются, но
   отдельным разделом под схемой, а не деревом мест.
6. Тесты: браузер — дерево совпадает со схемой «Плана v3» (те же узлы,
   та же вложенность), мест нет; API, на которые опирается дерево, — с
   перечитыванием.
7. `docs/pilot-checklist.md` разделы 2–3 и `docs/status.md` — под новую
   модель.

## П8. Новые нагрузки ложатся на план в одну точку

1. Новый значок — в свободное место рядом с родителем: например, веером
   или в ряд под щитом с шагом, который не перекрывает подписи (учесть уже
   стоящие на плане значки отходящих линий этого щита и границы плана).
   Одна функция на оба места.
2. Браузерный тест: щит → три «+ Счётчик» с новыми нагрузками → у трёх
   значков разные координаты, подписи не пересекаются (по
   `getBoundingClientRect` подсказок).

## П9. Каждой фазе прибора — свой потребитель

**Блокирует пилот.** Решение Кира — R13 (18.10.2026).

**Закрыто в партии 13-findings-0.22.3** (выпуск 0.22.3; таблица сдачи — в описании PR).

Кир: «нужно вернуть возможность прописать каждой фазе своего
потребителя» — один WB-MAP3E, у которого L1, L2 и L3 питают разные
нагрузки.

**Проверено по коду 0.22.2 — расчёт этого никогда не умел.** Профили
привязки `phase_l1`…`phase_l3` есть (`binding_service.py`,
`VALID_CHANNEL_PROFILES`), и старая форма «+ Точка учёта» (до 0.22.2)
давала их выбрать. Но часовые итоги — один на прибор: `period_aggregates`
(миграция 001) без канала, `aggregator.py` считает только `Total AP
energy`, а `accounting_service.py` профиль привязки не смотрит (докстринг:
«предполагает один канал на прибор»). Точка на фазе L1 получила бы весь
трёхфазный расход прибора; три фазы одного прибора — тройной. API
`POST /api/v2/topology/nodes/<id>/meters` и сейчас принимает
`channel_profile=phase_l1` — то есть молча посчитал бы неверно.

**Нужно** (сначала проектная заметка в `docs/` — как этап 12.0 партии 12:
схема хранения, миграция, откат, нагрузка на RPC; потом код):

1. **Пофазные часовые итоги** по счётчикам `AP energy L1`/`L2`/`L3`
   (WB-MAP3E их публикует, см. `channels.py`): новая таблица или канал в
   ключе итогов — решает агент в заметке. Существующие итоги `Total AP
   energy` не меняются. Миграция схемы — с проверкой отката (обновление до
   0.22.3 → откат на 0.22.2: сервис поднимается, данные целы — тестом).
2. **Агрегатор** считает фазы для приборов с пофазными привязками (или для
   всех MAP3E — обосновать нагрузкой на `wb-mqtt-db`). Флаги A13/A14
   (`reset`, `sparse`) — и для фаз. Прошлые часы фаз — через
   `aggregates recompute` (CLI) и автоматически при создании пофазной
   привязки.
3. **Расчёт** (`accounting_service`, снимок «Обзора», баланс щита, отчёты,
   CSV): профиль привязки выбирает источник — `total_3p` → итоги прибора,
   `phase_lN` → итоги фазы; живая мощность — `P L1`…`P L3` вместо
   `Total P`. Сумма трёх фаз ≈ итог прибора (с допуском округления) — тест.
4. **Занятость по фазам.** Прибор с занятой L1 доступен для L2 и L3;
   `total_3p` конфликтует с любой фазой (правило уже есть —
   `profiles_overlap`). `occupied_devices` и списки выбора показывают
   свободные фазы: «wb-map3e_16 — свободны L2, L3».
5. **«+ Счётчик»:** «Как подключён прибор: ● все три фазы — одна линия ○
   по фазам — каждая фаза своя линия». По фазам — три строки L1/L2/L3, у
   каждой цель: существующая нагрузка, «+ новая нагрузка…» или «не
   используется». Всё одной ревизией (одна серверная операция на все
   фазы). Линии одной фазы — `phase_count = 1`. Если у прибора нет
   пофазных счётчиков в MQTT — «по фазам» недоступно, с пояснением. В
   карточке: «wb-map3e_16 · L1 — линия к «Освещение»».
6. **Тесты:** агрегатор по фазам на поддельном RPC; три фазы на три
   нагрузки — у каждой своя энергия, итог объекта без тройного счёта;
   баланс щита с пофазными нагрузками; занятость и конфликты (L1 дважды,
   `total_3p` + L2); браузер — «по фазам» от выбора прибора до баланса
   щита; миграция и откат.
7. `docs/pilot-checklist.md`, раздел 3 — шаг про счётчик «по фазам».

## П12. Эмулятор счётчиков в сервисе

**Закрыто в партии 13-findings-0.23.1, PR #22** (выпуск 0.23.1; таблица сдачи — в описании PR; проектная заметка — `docs/design-emulator.md`).

**Блокировало пилот** — решение Кира R17 (21.10.2026): отдельный выпуск
0.23.1 до партии 14. Настоящие приборы на контроллере для пилота не
годятся: у `wb-map3e_16` нет нагрузки, `wb-map3e_49` не отвечает по RS-485
(раздел 8 инструкции). Без нагрузки не проверить разделы 4–5 инструкции
(баланс, отчёт за неделю) и не сделать замер скорости (A40).

**Что есть.** `tests/pilot/rehearsal.py` (класс `FakeMeters`) уже публикует
поддельные WB-MAP3E по соглашениям Wiren Board (`/devices/<id>/meta`,
`/devices/<id>/controls/<канал>` с `meta`; `Total AP energy`,
`AP energy L1–L3`, `P L1–L3`, `Urms`, `Irms`, `Frequency`). История на
контроллере — настоящий `wb-mqtt-db`, он пишет всё, что приходит в MQTT
(если так настроен — см. п. 7).

**Нужно** (проектная заметка в `docs/` до кода — как 12.0):

1. **Модуль `wb_energy_meter/emulator.py`** — виртуальные WB-MAP3E в тот же
   брокер, что и сервис. `device_id` — `emu-map3e-N`, имя «Эмулятор N»,
   серийник `EMU-…`, драйвер в `meta` — свой (не `wb-modbus`). Значения раз
   в 5 с. `rehearsal.py` переходит на этот модуль (одна реализация).
2. **Счётчики не обнуляются при перезапуске**: последнее показание и время
   хранятся в базе (`kv`), после перезапуска рост продолжается с учётом
   прошедшего времени. Иначе каждый перезапуск сервиса выглядел бы как
   сброс счётчика (A13).
3. **Сценарии** (решение R17 — все четыре):
   - расход по суткам: день больше, ночь меньше, небольшой шум; у каждого
     прибора своя мощность;
   - разные фазы: мощность L1/L2/L3 задаётся отдельно — для «по фазам» (П9);
   - небаланс щита: прибор с ролью «ввод» показывает сумму выбранных
     приборов плюс заданный процент (потери / неучтённый потребитель);
   - сбои по кнопке у прибора: «Сброс счётчика», «Замена прибора» (новый
     серийник, счётчик с новой базы), «Пропадание связи на N минут» (не
     публиковать; каналы с `meta/error` = `r`, как у настоящего
     `wb-mqtt-serial`), «Редкие показания на N часов» (раз в 30–60 мин).
     Каждый сбой — в журнал эмулятора с временем: потом сравнить, как это
     показала программа (флаги `reset`, `sparse`, «не подтверждено» — A13,
     A14, A16).
4. **«Настройки» (набор v2), раздел «Эмулятор счётчиков»**: выключатель;
   список виртуальных приборов (добавить, удалить, имя, кВт по фазам,
   профиль «по суткам» / «ровный»); «ввод = сумма выбранных + %»; кнопки
   сбоев; журнал сбоев; состояние истории (п. 7). Серверный API — по
   `CODING_STANDARDS.md` (формат ошибок, коды, проверка входа); как хранить
   настройки (`kv` или таблица) — решает агент в заметке. По умолчанию
   эмулятор **выключен**.
5. **Пометка везде**: прибор и точка эмулятора — с меткой «эмулятор» в
   списках выбора прибора, карточках, «Структуре», «Обзоре», отчётах и CSV
   (колонка или пометка в имени — решает агент). Пока эмулятор включён — в
   «Обзоре» плашка «Включён эмулятор: N виртуальных приборов — цифры с ними
   не настоящие».
6. **Выключение**: публикация останавливается, retained-топики эмулятора
   стираются (пустой retained), чтобы приборы пропали из MQTT и из
   веб-интерфейса Wiren Board. Точки, привязанные к эмулятору, остаются (их
   история настоящая для программы); в разделе — кнопка «Архивировать
   точки эмулятора» с подтверждением.
7. **История**: через 10–15 минут после включения сервис сам спрашивает у
   `wb-mqtt-db` (RPC, как агрегатор) историю одного канала эмулятора. Нет —
   в разделе предупреждение: «wb-mqtt-db не пишет историю эмулятора —
   отчёты будут пустыми; проверьте настройки wb-mqtt-db (группы каналов)».
8. **Тесты**: модуль (профиль, фазы, «ввод = сумма + %», продолжение
   после перезапуска, каждый сбой); API (вход, отказы, перечитывание);
   браузер — включить → приборы с меткой в «+ Счётчик» → схема Ввод → Щит →
   нагрузки, одна «по фазам» → баланс щита = заданный % → сбой «сброс» →
   отчёт показывает флаг → выключить → топики стёрты. Репетиция пилота — на
   новом модуле.
9. `docs/pilot-checklist.md` — новый раздел «Проверка без нагрузки:
   эмулятор» (как включить, что ожидать, как выключить и убрать); правка
   инструкции и репетиции — в одном PR (§2.6, п. 5).
10. **Проверки на контроллере при сдаче** (R17, §12, шаг 7): кроме
   обновления и чтения агенту разрешено включить эмулятор и завести на нём
   свою тестовую схему — см. R17 и `claude/controller-access.md`.
