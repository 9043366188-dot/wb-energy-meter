## 1. Что уже готово (не переделывать)

Этапы A–C и партия 2 сделаны и покрыты тестами (27 файлов в `tests/`,
проходят на Python 3.9 + Flask 1.1.2, как на контроллере):

- доменная модель v2, миграция 005 (аддитивная, данные v1 целы);
- расчётный слой `accounting_service.py` — **сердце системы**, здесь
  считаются `measured_point`, `sum_points`, `check_sum_overlap`,
  `balance`, `comparison`;
- `/api/v2` — 33 маршрута, включая `overview/summary`, `reports/query`,

- глобальный протокол ревизий: каждая предметная запись требует

**Главное правило:** экран, отчёт и CSV берут числа из расчётного слоя

A43 требует одинакового результата везде.

## 2. Что входит в партию

Четыре задачи. Первые две — основные, они дают пользователю то, ради чего
строилась модель.

### Задача 1. Экран «Структура» и инспектор (§8.3)

Сейчас точку учёта негде посмотреть целиком: её место установки,
питающая линия и учётные группы разнесены по разным экранам, а истории
замен не видно вовсе.

Делать по §8.3. Ключевое:

- слева дерево и поиск, по центру дочерние элементы с показателями,
  справа инспектор выбранной сущности;
- **поиск по имени, коду точки, MQTT ID, серийному номеру и пути**; при
  выборе раскрыть предков и прокрутить к объекту;
- инспектор точки в порядке из §8.3: имя и код → состояние и свежесть →
  расход за период → напряжения и токи по фазам → «питается от / питает»
  → место установки → группы → действующий прибор → история замен;
- у группы вместо характеристик прибора — состав и качество суммы;
  у связи — концы, измерение, фазные токи, заданный предел;
- **непривязанные и неразмещённые точки не исчезают** — отдельная
  доступная подборка, а не молчаливое отсутствие;
- один и тот же инспектор открывается из плана, дерева, отчёта и
  проблемы.

Инспектор — только чтение плюс существующие действия через уже
имеющиеся ручки v2. Новых способов править данные в этой задаче не
заводить.

### Задача 2. Мастер переноса старых связей (§2, строка про §31.5)

В базе сосуществуют две модели планов: старая (`site_plans`,
`plan_zones`, `plan_links`) и новая (`site_plans_v`, `plan_items`,
`plan_edge_views`). Пока обе пустые, это дёшево. Как только пользователь
нарисует связи в одной — цена переезда вырастет.

Большое ТЗ прямо запрещает переносить старые связи автоматически:
«Только после подтверждения смысла каждой связи. Из рисунка между
группами нельзя достоверно вывести питающую линию».

Поэтому — **мастер**, а не автоматика:

- показать список связей старой модели с их подписями и концами;
- для каждой предложить: что это за электрическая связь, какие узлы
  сети соответствуют концам, какая точка учёта её измеряет;
- **пользователь подтверждает каждую связь явно**; неподтверждённые
  остаются как есть и не переносятся;
- результат — записи в `electrical_nodes`/`electrical_edges` через
  существующий сервис топологии, одной транзакцией с ревизией;
- повторный запуск мастера не создаёт дублей (сверяться с
  `migration_map`, он для этого и заведён).

Старую модель в этой партии **не удалять**. Решение о выводе её из
эксплуатации принимает пользователь, после того как увидит результат
переноса.

### Задача 3. Провижининг прибора при замене (§5.4)

Ручка `POST /api/v2/points/<id>/replace-meter` сейчас требует, чтобы
`meter_source` уже существовал: «Провижининг НОВОГО meter/meter_source из
адреса контроллера здесь не делается». Значит сценарий «сгорел счётчик,
поставили новый» из интерфейса не проходит целиком — а история замен
затевалась именно ради него.

Принимать в теле адрес нового прибора (контроллер + device_id, как они
приходят из MQTT), заводить `meter` и `meter_source` при необходимости и
открывать новый интервал привязки. Завершение старого интервала уже
делает сервер — не дублировать.

Обязательно: замена внутри часа и внутри суток считается корректно
(A17–A20 уже покрыты в `test_step15_binding_service.py` — не сломать их),
и расход за период, охватывающий замену, не теряется и не задваивается.

### Задача 4. Сводка незавершённой настройки (`validation`)

Маршрут `validation` в `api_v2.py` числится нереализованным. На ста
точках без него невозможно найти забытое.

Отдавать сводку: точки без привязки к прибору, точки без места, точки вне
групп, точки не на плане, узлы сети без связей, связи без измерения.
Использовать на экране «Обзор» в блоке «Требует внимания» и в
инспекторе — §8.2 требует сортировать проблемы по влиянию, а не по
алфавиту.

Замечание по существующему поведению: сейчас в «не входит ни в одну
ветвь» попадает сама точка ввода. Формально верно, но как «проблема» это
шум — ввод не обязан состоять в ветвях. Исключить его из этой сводки.

## 3. Чего в эту партию НЕ входит

- **Однолинейная схема вторым холстом** — отдельная крупная задача, и её
  разумнее делать после инспектора: схема открывает тот же инспектор.
- **Адаптивная вёрстка и смена `viewport` (§8.5)** — требует браузера.
  Сейчас `<meta name="viewport" content="width=1100">`, замена на
  `device-width` меняет вёрстку всех вкладок, включая классический набор,
  который остаётся рабочим интерфейсом объекта. Делать вместе с живым
  прогоном в браузере.
- **`change_log` (кто/что/когда) и историческая топология «как было на
  ревизии N»** — задокументированные ограничения 0.13.0, обе крупные.
  Кандидаты в следующую партию.
- **Удаление старой модели планов** — решение пользователя, не агента.
- Тарифы, начисления, Sankey, АВР/ДГУ, кольцевые сети — отложено большим
  ТЗ, §12.

## 4. Ограничения проекта

Каждый пункт уже стоил рабочего контроллера.

- **Только стандартная библиотека Python** плюс уже используемые flask,
  paho-mqtt, pyyaml. Никаких новых зависимостей, в том числе в тестах.
- **На контроллере Debian bullseye:** Python 3.9, Flask 1.1.2,
  Werkzeug 1.0.1. Перед тем как взять что-то из Flask/Werkzeug —
  проверить, есть ли оно в этих версиях. Для этого есть job `legacy-deps`.
- **Никаких CDN** — библиотеки лежат локально в `static/vendor/`.
- **У `<template x-if>` ровно один корневой элемент**, иначе Alpine молча
  не отрисует блок. Есть автопроверка в `tests/test_step6_webui.py`.
- Вкладка «План» — единственная на `x-show` из-за Leaflet. Остальные не
  переводить.
- Не менять формат существующих ответов API — только добавлять.
- Не трогать миграцию 005 и данные v1.
- Любая предметная запись проходит через протокол ревизий: без
  `expected_revision` — 409.
- **`DEFAULT_UI_SET` оставить `'classic'`.** Переключение по умолчанию —
  после того, как пользователь сам откроет новые экраны в браузере.
- Подробности по граблям — в `AGENTS.md`, прочитать до начала.

## 5. Проверка

Тесты гонять на **двух** наборах версий:

```bash
pip install "paho-mqtt>=1.6,<3" "pyyaml>=5.4" "flask>=1.1" --break-system-packages

python3 -m venv /tmp/venv_old
/tmp/venv_old/bin/pip install "flask==1.1.2" "werkzeug==1.0.1" \
    "jinja2<3" "itsdangerous<2" "markupsafe<2" "paho-mqtt>=1.6,<3" "pyyaml>=5.4"
```

Тесты — самостоятельные скрипты, запускать по одному
(`python3 tests/<файл>.py`), не pytest. `test_step3_daemon`,
`test_step3_e2e`, `test_step4_daemon` требуют mosquitto и в песочнице
падают — ожидаемо.

Новые тесты добавить в **оба** job'а `ci.yml`. Имя шага с `": "` внутри —
обязательно в кавычках, иначе YAML невалиден и workflow не запускается
целиком, молча.

Кроме тестов: `compileall`, `bash -n` по `scripts/*.sh`, баланс тегов
`index.html` скриптом (комментарии вырезать **до** скриптов и стилей —
слово `<script>` внутри комментария сбивает наивный разбор),
`node --check` по каждому инлайн-блоку JS, `yaml.safe_load` по `ci.yml`.

Из §13 большого ТЗ закрыть: A02 (три разных отношения у одной точки,
поиск по любому из них), A17–A20 (замены — не сломать существующие),
A21, A22 (историчность состава), A34 (переключение экранов не плодит
экземпляров и не теряет черновик), A35, A43 (ревизии), A45 (текст с HTML,
кавычками и формульным префиксом не исполняется нигде).

**Каждая проверка «доступ запрещён» или «ошибка» обязана иметь парную
проверку «легитимный запрос работает».** Тест, который проверяет только
отказ, уже один раз пропустил поломку целого маршрута: при сломанном
обработчике обходные пути тоже давали 404, и проверка была довольна.

## 6. Критерии приёмки

- [ ] Инспектор показывает три отношения точки (место, питание, группы)
      по отдельности; поиск находит точку по имени, коду, MQTT ID,
      серийнику и пути (A02).
- [ ] Непривязанные и неразмещённые точки доступны в отдельной подборке,
      а не исчезают.
- [ ] Мастер переносит старые связи **только с явным подтверждением**
      каждой; повторный запуск не создаёт дублей.
- [ ] Замена прибора проходит из интерфейса целиком, включая новый
      прибор; расход за период с заменой не теряется и не задваивается.
- [ ] Сводка незавершённой настройки не считает проблемой точку ввода.
- [ ] Все тесты проходят на обоих наборах версий, новые заведены в CI.
- [ ] Версия поднята в двух местах, `CHANGELOG.md` и `AGENTS.md`
      обновлены, незавершённые части названы незавершёнными.
- [ ] `DEFAULT_UI_SET` остался `'classic'`.
