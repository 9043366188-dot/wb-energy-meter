## [0.15.0] — 2026-09-19

Партия 5 по [заданию на партию 5](docs/TZ-batch5-make-v2-usable.md):
делает интерфейс v2 наполняемым с нуля. Прогон в браузере (сделан не
этой сессией, между партиями) показал, что до этой партии в v2 нельзя
было создать ни место, ни точку учёта, ни привязку к прибору, ни узел
или связь сети, ни опубликовать топологию — интерфейс мог только
переносить legacy-связи, редактировать план и запрашивать расчёты, хотя
все нужные ручки `/api/v2` уже существовали и были покрыты тестами (см.
§0 задания). Старый API (`/api/*`), формат существующих ответов
`/api/v2/*` и существующие данные не затронуты — только добавления;
кнопки «удалить все данные» в интерфейсе нет и не будет (см. раздел
README «Чистый старт»).

### Добавлено

- **`POST /api/v2/points/<id>/bindings`** (задача 1) — открытие ПЕРВОЙ
  (или дополнительной, `role="check"`) привязки точки к прибору.
  `replace-meter` для этого не годится: требует уже открытую основную
  привязку и закрывает её. Нужный метод сервисного слоя,
  `PointBindingRepo.open_binding`, уже существовал и использовался
  мастером переноса legacy, но не был доступен ни через один HTTP-
  маршрут. Тело — как у `replace-meter`: `meter_source_id` готового
  источника либо `new_meter{controller_key, device_id, display_name}`
  нового прибора; провижининг вынесен в общий
  `_resolve_or_provision_meter_source` (раньше был продублирован внутри
  `replace-meter`, теперь один источник истины для обоих маршрутов).
  `controller_key` необязателен — по умолчанию `DEFAULT_CONTROLLER_KEY`
  (тот же, что и у мастера переноса legacy; контроллер в системе один).
- **`installation_location_id` в `PATCH /api/v2/points/<id>`** (задача 2,
  «редактировать принадлежность» §8.3) — раньше место установки точки
  можно было задать только при создании (`POST /api/v2/points`), сменить
  позже было нечем (`update_fields` этого поля не знал). `null` —
  значащее значение («снять место установки»), не «не менять».
- **Экран «Структура»: заведение объектов из интерфейса** (задача 1,
  основная задача партии): новая панель «Завести в структуре» на вкладке
  «Структура» — формы создания места (имя/тип/родитель), точки учёта
  (код/имя/место + опционально сразу привязка к прибору из того же
  списка приборов, что и классические «Настройки» → «Добавить
  счётчик» — `registry/meters` + `meters/unregistered`), узла сети
  (код/имя/тип/место), черновика связи (от узла/к узлу/точка измерения/
  ток/кабель) и отдельное действие «Публикация топологии»
  (`topology/validate` перед `topology/publish`, список нарушений
  текстом при конфликте). Каждая форма — тонкая обёртка над уже
  существующими маршрутами `/api/v2` (плюс новым `bindings` выше) с
  протоколом ревизий; конфликт ревизии (409) показывается понятным
  текстом и НЕ приводит к автоматическому повтору запроса — не
  перезаписываем чужие изменения молча. В интерфейсе прямым текстом
  объяснено, что ввод объекта определяется автоматически (связь от
  узла типа «Ввод»/source с назначенной точкой измерения) — отдельного
  действия «назначить ввод» нет.
- **Действия карточки инспектора точки** (задача 2, §8.3): «Показать на
  плане» (ищет точку среди `plans/*/items` всех планов v2, при
  единственном совпадении сразу переходит и панорамирует карту к
  метке, при нескольких — список на выбор), «Открыть график»
  (переиспользует существующую детальную карточку классического
  интерфейса — `openDetail`/`openChannelChart`, вторая реализация
  графика не писалась), «Заменить прибор» (форма поверх уже
  существующего `replace-meter`, тот же список приборов, что и при
  создании точки, с предупреждением про закрытие старой привязки),
  «Редактировать принадлежность» (место — через новый PATCH выше,
  группы — через уже существующие `groups/<id>/members`).
- **Осмысленные пустые экраны** (задача 3, §8.5): «Структура» без мест/
  точек — подсказка нажать конкретную кнопку создания вместо голого
  «пусто»; «План v2» с планами, но без узлов сети — подсказка сначала
  создать сеть на «Структуре»; кнопка «Настроить границу объекта» на
  Обзоре (§8.2, партия 2) теперь ведёт прямо на форму создания узла на
  «Структуре» вместо Плана v2 (на Плане v2 узел создать было нельзя —
  сама эта партия и есть исправление); строки группы в режиме
  «сравнение» (электрическое пересечение, А04) на Обзоре различают
  ПОЧЕМУ у точки нет числа — «нет прибора» (не привязана), «нет связи»
  (устройство не отвечает), «архив» (точка архивирована), «нет данных»
  (остальное) — раньше везде было одно «нет данных» без разбора причины.
- **Пояснение модели плана v2** (задача 4): короткий блок прямо на
  вкладке «План v2» — в v2 нет заливки контуров зон, как в старом
  «Плане» (v1), только элементы (точки/узлы/места) и трассы вдоль
  опубликованных электрических связей; нужна ли заливка зон отдельно —
  открытый вопрос, записан в «Запланировано» выше, а не решён втихую.
- **Раздел README «Чистый старт»** (задача 5): пошаговая безопасная
  процедура (остановить сервис → бэкап БД с меткой времени → удалить
  рабочую БД → запустить сервис — миграции создают чистую схему →
  проверить `/api/selfcheck`/`/api/status`) с явным предупреждением, что
  удаление БД необратимо стирает всю историю энергии. Кнопки сброса в
  интерфейсе по-прежнему нет и не будет — задание партии 5 прямо это
  запрещает.

### Известные ограничения

- **Браузер для проверки интерфейса не использовался** (сессия без
  доступа к браузеру) — вся новая разметка и JS партии 5 (панель
  создания на «Структуре», действия карточки инспектора, пустые
  экраны, пояснение на Плане v2) проверены ТОЛЬКО статически (см.
  «Проверено» выше и AGENTS.md → «Что в работе»). Что кнопки реально
  нажимаются, формы реально заполняются и весь путь партии 5 работает
  в живом браузере — НЕ проверено. `DEFAULT_UI_SET` оставлен `'classic'`
  именно по этой причине.
- «Показать на плане» ищет точку перебором `plans/*/items` по ВСЕМ
  планам последовательными запросами — при большом числе планов (в ТЗ
  зафиксирован масштаб до 10 планов) это может быть заметно медленнее
  одного целевого запроса; отдельной ручки «на каких планах есть эта
  точка» не заводилось (не нашлось готовой, а заводить новую ради
  одной кнопки посчитано избыточным для этого объёма). Панорамирование
  карты к найденной метке использует внутреннюю `_planV2ItemLayers` —
  не проверено в живом Leaflet (см. пункт выше).
- «Показать на плане»/переход к инспектору для узлов и связей на самой
  панели создания не добавлялись — панель создания только создаёт
  новые объекты, открыть уже созданный узел/связь в инспекторе можно
  из дерева/списка «Структуры» как и раньше (не регрессия — так было
  устроено с партии 3).
- A19/A20 (частичный агрегат на границе, конкурентная замена/открытие)
  для НОВОГО пути открытия первой привязки используют тот же код
  `binding_service`/протокола ревизий, что и `replace-meter` (уже
  тестировался в партии 3) — отдельных целевых тестов конкурентности
  именно для `bindings` в этой партии не добавлено, риск оценён как
  низкий (общая логика), но это не то же самое, что проверено.
- `nodes_without_edges`/`points_without_meter` в `GET /api/v2/validation`
  (партия 3) не менялись и не переиспользовались напрямую в новых
  пустых экранах — «Структура»/«План v2»/«Обзор» решают, что показывать,
  по уже загруженным для себя данным (`structNodes`/`structPoints`/
  `ovSummary`), а не отдельным запросом к `/validation`, чтобы не грузить
  экран лишний раз ради текста подсказки.

Партия 3 по [заданию на партию 3](docs/TZ-batch3-structure-inspector-legacy.md)
и [ТЗ архитектуры учёта, электросети, планов и дашборда]

объекта, мастер переноса legacy-связей плана, провижининг нового прибора

только добавления; миграция `005` не тронута; новых мутирующих маршрутов

### Добавлено

- **Экран «Структура»/инспектор объекта** (§8.3, задача 1): вкладка v2
  «Структура» — дерево мест + поиск слева (`GET /api/v2/structure/points`,
  A02 — поиск по имени, коду, MQTT ID, серийному номеру прибора и пути
  размещения, регистронезависимо), дочерние точки с метриками снимка в
  центре, read-only инспектор справа. Один и тот же инспектор
  (`openInspector(kind,id)`) открывается идентично из вкладки «Структура»,
  Плана v2 (кнопка у выбранного элемента/связи), Отчётов v2 (клик по
  названию строки point/branch/group) и нового блока «Незавершённая
  конфигурация» на Обзоре. Порядок полей карточки точки — по ТЗ §8.3:
  имя/код → статус/свежесть → расход за период → фазные напряжения/токи →
  чем питается/что питает → место установки → группы → текущий прибор →
  история замен; у группы — состав и сумма/качество вместо атрибутов
  прибора; у узла сети и связи — свои варианты карточки. Непривязанные и
  неразмещённые точки не прячутся — отдельный бакет «Без места» в дереве и
  явный статус «не привязана». Инспектор не считает ничего сам — только
  уже существующие ручки v2 (snapshot, metrics/query,
  points/<id>/bindings, points/<id>/groups, topology/*,
  groups/<id>/effective-members).
- **Провижининг нового прибора при замене** (§5.4, задача 3):
  `POST /api/v2/points/<id>/replace-meter` принимает `{"new_meter":
  {"controller_key", "device_id", "display_name"}}` вместо готового
  `meter_source_id` — заводит `meter`+`meter_source` (либо переиспользует
  существующие с тем же адресом, устойчиво к повтору запроса) и открывает
  новую привязку одной транзакцией с ревизией. Старый вариант с
  `meter_source_id` продолжает работать на том же маршруте без изменений
  (A17-A20 регрессия проверена для обоих путей).
- **`GET /api/v2/validation`** (§8.2/§13, задача 4) — сводка незавершённой
  настройки: точки без прибора/места/группы/размещения на плане, узлы без
  связей, опубликованные связи без назначенного измерения; точка ввода не
  считается проблемой в «без группы» (переиспользует ту же логику, что и
  `overview/summary`). `issues` отсортирован по влиянию на сервере (нет
  прибора/измерения раньше отсутствия места/группы/плана), фронт порядок
  не переставляет. Фид для нового блока «Незавершённая конфигурация» на
  Обзоре — отдельно от существующего блока «Требует внимания» (тот смотрит
  на живую связь с устройством по снимку, этот — на завершённость
  конфигурации).
- **Мастер переноса legacy-связей плана** (ТЗ §2/§31.5, задача 2):
  `GET /api/v2/migration/legacy-links` + `POST .../confirm` — перенос
  `plan_links`/`plan_zones` старой модели плана в `electrical_edges`
  (топология v2) СТРОГО с явным подтверждением каждой связи (без
  эвристики «угадывания» узла по рисунку — большое ТЗ прямо это
  запрещает). Идемпотентно через `migration_map`: повторное подтверждение
  той же связи/зоны не плодит дубли, работает и внутри одной пачки.
  Создаёт только черновики рёбер — проверка леса и публикация делаются
  существующими `topology/validate`/`topology/publish`. Пачка
  подтверждений атомарна: ошибка в одной связи откатывает всю пачку.
  Старая модель (`plan_links`/`plan_zones`) не изменяется и не удаляется.

  1. **Ведомость расхода** — таблица по всем счётчикам за период,
     сгруппированная по зонам, итог по каждой зоне и общий итог.
  2. **Профиль нагрузки** — почасовой SVG-график выбранного счётчика,
     метрики (итого, пик, среднее, часов с данными), таблица по часам.
  3. **Сравнение периодов** — два периода рядом, Δ кВт·ч и Δ % с
     цветовой индикацией роста/снижения.
  4. **Доступность** — % времени на связи, суммарное время недоступности,
     число инцидентов; клик раскрывает список с датами от/до каждого.
  5. **Баланс** — ввод минус потребители = небаланс в кВт·ч и %. Три
     сводных карточки + детализация по каждой группе. Если вводных
     счётчиков нет — подсказка как их назначить.
  - Все отчёты выгружаются в **CSV** (UTF-8 BOM, открывается в Excel).

- **Аптайм счётчика** на карточке дашборда — если канал Uptime (s)
  включён в Device Manager WB.

- **Цветное время последнего обновления** на карточке: 🟢 < 2 мин,
  🟡 < 10 мин, 🔴 > 10 мин.

### Изменено

- Дашборд: карточки сгруппированы по зонам вместо плоского списка.
- `status.py`: два раздельных таймаута — `no_connection` (нет любых
  сообщений) и `no_measurement` (связь есть, но U/I = 0). Статус
  `no_measurement` теперь корректно отображается как «Нет нагрузки».
- `model.py`: добавлен `last_measurement_ts`, `MEASUREMENT_CHANNELS`,
  канал `Uptime` в `MAIN_CHANNELS`.
- `mqtt_client.py`: обновляет `last_measurement_ts` только для
  измерительных каналов (U/I/P/F) выше порога.
- `config.py`: дефолт `no_connection_timeout_s` поднят 300 → 600 с.
- `main.py`: `groups_repo` и `alert_repo` передаются в `ApiServer`
  и `StatusEngine`.
