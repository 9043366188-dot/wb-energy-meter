# Стандарты разработки

Единый источник постоянных правил разработки: архитектуры, данных,
совместимости, тестирования и выпуска. `AGENTS.md` маршрутизирует по задаче;
условные руководства содержат только подробности соответствующей подсистемы.
Не дублируйте правила в других документах.

## Стиль Python

- Минимальная версия в метаданных — Python 3.9; CI проверяет Python 3.9–3.12.
  Соблюдайте PEP 8; ориентир длины строки — около 88 символов, без
  механического форматирования.
- Docstring должен объяснять контекст и причину, а не пересказывать очевидное
  из кода. Допустимы русский и английский.
- Имена в коде и внутренние технические логи — по-английски. Пользовательские
  сообщения и логи — по-русски.

## Архитектура и владение данными

- Не дублируйте сырую телеметрию: её источник — `wb-mqtt-db`. Локальная БД
  хранит реестр и производные агрегаты, которые можно пересчитать.
- Читайте данные `wb-mqtt-db` через публичный MQTT-RPC контракт. Не обращайтесь
  напрямую к его SQLite и не записывайте туда.
- MQTT-колбэки должны быстро возвращаться. Переносите тяжёлую работу, например
  запросы к БД, в фоновые задачи.
- Если изменение API обновляет группу счётчика, синхронизируйте и in-memory
  `MeterRegistry`, чтобы `/api/status` видел новое значение до перезапуска.

## База данных

- Миграции только добавляются: не редактируйте применённые SQL-файлы, создавайте
  следующую миграцию `NNN_description.sql`.
- SQLite `COLLATE NOCASE` не сворачивает регистр кириллицы. Для
  регистронезависимой уникальности имён используйте Python `str.casefold()` и
  соответствующую нормализованную колонку.
- Не копируйте файл активной SQLite-базы обычным `cp`: подтверждённые данные
  могут оставаться в WAL. Остановите сервис и используйте SQLite Online Backup
  API.

## Совместимость с контроллером

- Целевая платформа — Wiren Board 8.x на Debian bullseye с Python 3.9 и
  системными пакетами, которые могут быть старше актуальных библиотек PyPI.
  Перед использованием новых API Flask, Werkzeug или paho-mqtt сверяйтесь с
  версиями контроллера и job `legacy-deps` в `.github/workflows/ci.yml`.
- CI устанавливает runtime-зависимости явно. При добавлении зависимости
  обновляйте установку в соответствующих CI job'ах и проверяйте её на
  поддерживаемом стеке.
- Для history RPC `WbDbClient.get_values` всегда передавайте `ver=1`: парсер
  ожидает короткие поля ответа `t`/`v`, а версия по умолчанию возвращает
  `timestamp`/`value`, из-за чего точки тихо теряются.
- Для публикации MQTT с QoS 1 запускайте сетевой цикл клиента перед ожиданием
  доставки. Не полагайтесь на `wait_for_publish(timeout=...)`: старый пакет на
  контроллере может не поддерживать аргумент `timeout`.

## API и проверки поведения

- Обработчик `PATCH` отвечает `400`, если тело не содержит ни одного поля,
  которое он умеет изменять. Проверки должны подтверждать изменение значения
  сущности, а не только HTTP-статус.
- Для отказа в доступе проверяйте обе стороны поведения: некорректный запрос
  отклоняется, а легитимный запрос к тому же ресурсу работает.
- Если данные существуют одновременно в SQLite и в памяти, обновляйте обе
  копии либо обеспечивайте их периодическую синхронизацию.

## Веб-интерфейс и статика

При изменении интерфейса, клиентских модулей или содержимого `static/` читайте

## Установщик и самообновление

- Установщик сначала проверяет доступность runtime-импортов. Ошибка зеркала
  `apt` сама по себе не должна мешать обновлению, если нужные пакеты уже есть;
  окончательное решение принимает проверка импортов.
- Основной запуск самообновления — отдельный transient-unit через
  `systemd-run`: так остановка сервиса не завершит обновляющий процесс. Если
  `systemd-run` отсутствует, код использует `setsid/nohup` как резервный путь;
  он не равноценен transient-unit. Запись статуса должна работать и во время
  замены или временного отсутствия кода пакета.
- `/etc/wb-mqtt-serial.conf` — чужой файл: запись разрешена только при
  `wb_serial.allow_edit: true` и меняет только `enabled` канала `Uptime` одного
  найденного устройства. Отказывайтесь от записи, если файл не является чистым
  JSON, формат неоднозначен или его SHA-256 изменился после чтения. Перед
  атомарной записью создавайте бэкап и сохраняйте права/владельца; после записи
  перечитывайте файл и проверяйте результат, а при сбое восстанавливайте бэкап.
  Перезапускайте `wb-mqtt-serial` только по явному действию пользователя.
- При изменениях `self-update.sh` сохраняйте защиту от самоперезаписи: тело
  `main` разбирается до запуска, а последняя команда должна оставаться
  `{ main "$@"; exit "$?"; }`. Иначе shell продолжит читать уже заменённый
  файл и обработчик ошибок может затереть успешный статус.

## Тестирование

- Не используйте pytest: тесты проекта — самостоятельные Python-скрипты.
- Юнит-тесты не должны зависеть от сети или работающего MQTT; для БД используйте
  временный файл. E2E-тесты, которым нужен MQTT, запускайте с локальным
  `mosquitto` и тестовым ответчиком вместо настоящего `wb-mqtt-db`.
- Основной запуск: `python tests/run_all.py`. Для выборки используйте
  `--only "test_step4*"`; `--skip-mosquitto` безусловно пропускает тесты,
  которым нужен локальный брокер. Раннер сам находит `tests/test_step*.py` и
  сообщает о пропущенных тестах.
- При добавлении или изменении теста сохраняйте проверяемый результат
  поведения: сверяйте состояние или значение, а не только отсутствие ошибки
  или код ответа.
- Перед выпуском запускайте проверки CI, включая legacy-зависимости и
  содержимое собранного пакета, когда изменение затрагивает соответствующую
  область.

## Версии и выпуски

- Используйте SemVer (`MAJOR.MINOR.PATCH`). При выпуске синхронизируйте версию
  в `wb_energy_meter/__init__.py` и `pyproject.toml`, добавьте раздел в
  `CHANGELOG.md`, создайте тег `vX.Y.Z`, затем откройте GitHub Release.
