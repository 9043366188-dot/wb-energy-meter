# AGENTS.md — wb-energy-meter

Контекст проекта для агентов (Codex читает `AGENTS.md`, Claude Code — `CLAUDE.md`,
который является ссылкой на этот файл). Держите оба в синхроне: правьте только `AGENTS.md`.

## Что это

`wb-energy-meter` — сервис учёта электроэнергии для контроллеров **Wiren Board 8.x**
со счётчиками **WB-MAP3E**. Читает данные из MQTT-инфраструктуры WirenBoard,
складывает в SQLite, считает расход и агрегаты, отдаёт веб-интерфейс и REST API.

- Язык: Python (`>=3.9`), пакет `wb_energy_meter`
- Текущая версия: **0.11.1** (`wb_energy_meter/__init__.py` + `pyproject.toml`)
- Репозиторий: https://github.com/9043366188-dot/wb-energy-meter
- Целевое железо: Wiren Board 8.x, WB-MAP3E
- Тестовый контроллер: `192.168.10.212`

```
  cli.py             CLI (console_script: wb-energy-meter-cli)
  api.py             Flask-приложение, все REST-эндпоинты
  mqtt_client.py     подписка на MQTT WirenBoard
  wb_db_client.py    доступ к БД WirenBoard

  aggregates_repo.py, aggregator.py   почасовые/периодные агрегаты

  background.py      фоновые задачи (в т.ч. периодическая ресинхронизация зон)
  config.py          чтение /etc/wb-energy-meter.conf

  migrations/*.sql   схема БД (применяются по порядку)

                      статус, запуск self-update.sh через systemd-run

  plan_geo.py         координаты плана: пиксели <-> [y,x] Leaflet CRS.Simple,
                      валидация геометрии зон/связей (v0.11.0)
  plan_repo.py        CRUD планов, зон на плане, связей; файлы картинок
                      на диске (v0.11.0)
  api.py::build_selfcheck_result()  самопроверка интерфейса: все файлы,
                      на которые ссылается index.html, реально на месте
                      (GET /api/selfcheck, v0.11.1)
  static/vendor/      Leaflet 1.9.4, Leaflet-Geoman Free 2.20.0, Alpine.js
                      3.13.0 — вендорено локально, см. VENDOR.md (v0.11.0)

scripts/             install.sh, install-from-github.sh, uninstall.sh,
                      self-update.sh, пример конфига
```

Веб-интерфейс — **один файл** `wb_energy_meter/static/index.html` на Alpine.js.
Сборки нет. С v0.11.0 все библиотеки (Alpine, Leaflet, Leaflet-Geoman) лежат
локально в `static/vendor/` — **не возвращайте ссылки на CDN**: на объекте
в изолированной сети интернета в браузере нет, и интерфейс просто не откроется.
Вкладки переключаются через `tab=='...'` (исключение — вкладка «План», см.
грабли про Leaflet ниже).

Тесты — не pytest, а самостоятельные скрипты; часть e2e-тестов требует локального
mosquitto на `127.0.0.1:1883` с `allow_anonymous true`.

CI (`.github/workflows/ci.yml`) гоняет матрицу Python 3.9–3.12 на ubuntu-latest.

## Правила и грабли

- **paho-mqtt 2.x**: при QoS=1 `wait_for_publish()` виснет навсегда без `loop_start()`.
  В тестовых публикаторах всегда вызывайте `pub.loop_start()` сразу после `pub.connect()`.
- **`wait_for_publish(timeout=...)` ломается на старом paho-mqtt с контроллера**
  (09.09.2026): параметр `timeout` появился только в paho-mqtt 1.5.1, а на
  Wiren Board пакет ставится из apt (`python3-paho-mqtt`) и может быть старее —
  падает `TypeError: wait_for_publish() got an unexpected keyword argument
  'timeout'`. Ловилось при открытии графика по параметру счётчика (веб-интерфейс
  → `WbDbClient._call()` в `wb_db_client.py`). `pyproject.toml` требует
  `paho-mqtt>=1.6`, но это не гарантирует версию реально установленного apt-пакета
  на объекте. Исправлено: вместо `info.wait_for_publish(timeout=...)` — ручной
  опрос `info.is_published()` в цикле со своим дедлайном (метод есть во всех
  версиях paho-mqtt).
- **`wb-mqtt-db get_values` без `ver:1` — история молча пустая** (09.09.2026):
  у RPC `db_logger/history/get_values` есть параметр `ver` (0 — полные имена
  полей ответа `timestamp`/`value`, 1 — короткие `t`/`v`; по умолчанию 0).
  `wb_db_client.get_values()` парсит именно короткие `t`/`v`, но `ver` в запросе
  не передавала — сервис отвечал в формате 0, все точки не находили `t`/`v` и
  тихо отбрасывались (`continue`), в ответе `points_count: 0` при реально
  непустой истории (`history-info` показывал `items > 0`). Выглядело как
  «нет данных за период», хотя параметр менялся постоянно. Чинится одной
  строкой — `params["ver"] = 1`. Не путать с предыдущим пунктом про
  `wait_for_publish`: это два независимых бага в одном и том же RPC-запросе,
  один маскировал другой (пока падал `wait_for_publish`, до парсинга ответа
  дело не доходило). Спека: https://github.com/wirenboard/wb-mqtt-db/blob/master/README.md
- **CI и зависимости**: рантайм-зависимости (в частности `flask`) должны быть явно
  перечислены в шаге `pip install` в `ci.yml`, наличия в `pyproject.toml` недостаточно.
- **На контроллере СТАРЫЕ библиотеки из apt, а не свежие из pip.** Wiren
  Board 8.x — это Debian bullseye: `python3-flask` 1.1.2, `python3-werkzeug`
  1.0.1, Python 3.9, `python3-paho-mqtt` может быть старее 1.5.1. Обычная
  матрица CI ставит **свежие** версии и к таким несовместимостям слепа.
  Это уже дважды роняло рабочий контроллер, оба раза 09.09.2026:
  `wait_for_publish(timeout=...)` (см. выше) и
  `from werkzeug.utils import safe_join` (см. ниже). Для защиты заведён
  отдельный job `legacy-deps` в `ci.yml` с пиннингом
  `flask==1.1.2`/`werkzeug==1.0.1` на Python 3.9. **Если он красный, а
  основная матрица зелёная — код работает у вас и не работает на объекте.**
  Прежде чем брать что-то из Flask/Werkzeug, проверьте, есть ли оно в этих
  версиях.
- **`werkzeug.safe_join` живёт в разных модулях в разных версиях**
  (09.09.2026, `api.py`, маршрут `/static/vendor/<path:filename>`): в
  Werkzeug 1.0.1 она в `werkzeug.security`, в `werkzeug.utils` появилась
  только во 2.0. `from werkzeug.utils import safe_join` на контроллере
  падал ImportError → маршрут отдавал 500 → `alpine.min.js` не грузился →
  **Alpine не стартовал вообще**. Симптом крайне обманчивый: вкладки на
  `<template x-if>` не рендерятся (инертные шаблоны), вкладка «План» на
  `x-show` наоборот видна всегда, `:data-theme` не проставляется — страница
  вообще без стилей. В логе сервиса при этом ни одной ошибки. Исправлено:
  свой разбор сегментов пути + проверка `realpath` + белый список
  расширений, без зависимости от версии Werkzeug.
  **Диагностический признак:** если интерфейс «залип» на одной вкладке и
  выглядит неоформленным — первым делом проверьте
  `curl -sI http://127.0.0.1:8080/static/vendor/alpine.min.js`.
- **Тест «обход каталога даёт 404» ничего не доказывает сам по себе.**
  Именно он пропустил баг выше: при сломанном обработчике обходные пути
  тоже давали 404, только по другой причине. К каждой проверке «доступ
  запрещён» обязательно нужна парная проверка «легитимный запрос
  работает» — см. `test_static_vendor_serves_every_referenced_file`,
  который требует, чтобы КАЖДАЯ ссылка `/static/...` из `index.html`
  отдавалась с кодом 200.
- **`/health` не видит белый экран — `/api/selfcheck` видит** (v0.11.1,
  прямое продолжение истории с `safe_join` выше). 09.09.2026 автооткат
  `self-update.sh` не сработал именно потому, что проверял только
  `systemctl is-active` и `GET /health` — оба честно отвечали «всё
  хорошо», хотя интерфейс был белым экраном: `/health` не знает о
  существовании браузера и Alpine.js вообще. Добавлен
  `GET /api/selfcheck` (`api.py::build_selfcheck_result()`): достаёт из
  `index.html` все ссылки `src=`/`href="/static/..."` и проверяет
  каждую напрямую на диске (не по HTTP к самому себе!) той же логикой
  разрешения пути, что и маршрут `/static/vendor/<file>`. HTTP-код
  **всегда 200** — это диагностика, а не сама ошибка; смотреть надо
  поле `ok`. `self-update.sh::verify_after_install()` теперь после
  `/health` дополнительно опрашивает `/api/selfcheck` (без `jq` — разбор
  через `python3 -c` с `json.load` из stdin) и откатывается через
  существующий `attempt_rollback`, если `ok: false`; **404 на этом
  эндпоинте не провал** — так отвечает откат на версию без него
  (например, v0.11.0), в этом случае просто полагаемся на `/health`, как
  раньше. Список несработавших файлов (`SELFCHECK_DETAILS`) попадает и в
  `update.log`, и в сообщение статуса — без этого пользователь опять
  остался бы с «обновление откатилось» без единой причины.
  `build_selfcheck_result()` вынесена на уровень модуля (не внутрь
  `create_app()`) специально ради тестируемости на временном каталоге
  с намеренно битыми файлами — см. `tests/test_step12_selfcheck.py`,
  реальные вендоренные файлы репозитория эти тесты не трогают.
- **Заглушка вместо белого экрана обязана работать без Alpine**
  (v0.11.1, `static/index.html`, `div#boot-error` сразу после
  `<body>`): раз она рассчитана именно на случай, когда Alpine не
  запустился, в ней нет и не может быть ни одной Alpine-директивы
  (`x-show`/`x-if`/`x-text`/`x-data`) и ни одной CSS-переменной темы
  (`--bg`/`--txt`/...) — переменные проставляет Alpine через
  `:data-theme` на `<html>`, при сломанном Alpine их не будет. Все
  цвета заданы инлайновым `style=` явно. Механизм: capture-phase
  `window.addEventListener('error', ..., true)` ловит ошибки загрузки
  `<script src>`/`<link href>` (у обычного bubbling-обработчика
  `event.target` для таких ошибок не виден) и показывает блок сразу со
  списком реальных путей; параллельно — `setTimeout(..., 1500)` на
  случай, когда скрипт загрузился, но упал внутри (там `error.target`
  указывает на `window`, не на элемент). Таймер снимается и блок
  удаляется из `init()` Alpine-компонента (`window.__wbemBootOk()`) —
  раз `init()` выполнился, Alpine жив. Задержка 1.5 с — чтобы блок не
  мигал при нормальной загрузке.
- **HTML `<template>`**: незакрытый `<template>` заставляет Chrome считать весь
  последующий HTML инертным фрагментом — скрипты не выполняются, Alpine не стартует,
  получается белый экран **без единой ошибки в консоли**. При правках `index.html`
  проверяйте баланс тегов (снять `<style>`/`<script>`, затем посчитать стек тегов).
  Автоматическая проверка — `tests/test_step6_webui.py::test_index_html_tag_balance`.
  **Важно:** наивный regex `<[^>]*>` для поиска тегов ломается на строках вида
  `:class="r.delta>0?'a':'b'"` — литеральные `<`/`>` внутри значений атрибутов
  нужно пропускать (учитывать открытые кавычки), иначе проверка даёт ложные
  срабатывания или пропускает реальные ошибки.
- **Leaflet и вкладки на `<template x-if>`** (v0.11.0, вкладка «План»):
  `x-if` уничтожает DOM при переключении вкладок, а Leaflet держит
  собственный DOM внутри контейнера карты и ссылку на него — при
  повторном входе получится либо пустой прямоугольник, либо исключение
  из недр Leaflet, либо утечка обработчиков. Вкладка «План» **сознательно
  на `x-show`, а не `x-if`** (остальные вкладки не трогать — не входило в
  задачу); карта создаётся один раз в `x-init` контейнера, ссылка на
  `L.Map` держится в замыкании модуля `index.html` (переменная `_planMap`
  вне `data()` компонента), а не в реактивных данных Alpine — иначе
  Proxy-обёртка Alpine ломает внутренние структуры Leaflet. После показа
  скрытой вкладки обязателен `map.invalidateSize()` (Leaflet посчитал
  размер контейнера в момент, когда он был `display:none`, — иначе карта
  отрисуется мусором), а контейнеру нужна явная CSS-высота
  (`#site-plan-map{height:calc(100vh - 220px);min-height:420px}`) —
  без неё блок схлопывается в 0 и карта не появляется вообще, без единой
  ошибки в консоли (тот же класс бага, что и с незакрытым `<template>`).
  Alpine не должен биндить `x-for`/`x-text`/`:class` на элементы **внутри**
  контейнера карты — слои, попапы и стили зон/связей меняются только
  императивно через API Leaflet (`layer.setStyle()`, `popup.setContent()`)
  из обычных методов Alpine-компонента; обновление живых данных (каждые
  5 с) правит стили и содержимое уже существующих попапов, не пересоздавая
  слои — иначе открытый попап закрывался бы на каждый тик.
- **Группа счётчика живёт в двух местах**: в SQLite (`meters.group_id`) и в
  in-memory `MeterRegistry` (`MeterState.group`). Второе заполняется один раз
  при старте демона (`main.py`) — без явной синхронизации любое изменение
  группы через API не долетает до `/api/status` до перезапуска. Синхронизация
  сделана на двух уровнях: push в конце обработчиков `api.py`
  (`_sync_registry_groups()`) и периодический опрос в `background.py`
  (`BackgroundTasks._sync_groups()`). При добавлении новых мест, где меняется
  привязка счётчика к зоне, не забывайте вызвать синхронизацию.
- **`COLLATE NOCASE` и кириллица**: SQLite сворачивает регистр в `COLLATE NOCASE`
  только для ASCII A-Z — «Цех1» и «ЦЕХ1» считаются разными строками. Для
  регистронезависимой уникальности с кириллицей нужна казефолд-нормализация на
  стороне Python (`str.casefold()`), а не SQL-коллация. См. `repo.py::_norm_name`,
  колонку `meter_groups.name_norm` (миграция 003) и `db.py::_py_casefold`
  (SQL-функция `py_casefold()` для миграций).
- **Установщик под Windows** (`Install-WbEnergyMeter.ps1` / `.cmd`):
  - запускать **от обычного пользователя**, не от администратора;
  - ключи генерировать без парольной фразы: `ssh-keygen -t ed25519 -N ""`;
  - OpenSSH под Windows молча не подписывает ключом, у которого в ACL есть
    унаследованные права или доступ шире текущего пользователя — снимать наследование
    через `icacls` и давать полный доступ только текущему пользователю;
  - PowerShell 5.1 не знает `Join-String`;
  - у старых сборок `plink` нет `-hostkey "*"` — сначала кэшировать ключ через
    `echo y | plink`.
- **`apt` в `install.sh` не должен быть фатальным** (09.09.2026): у зеркала
  `debian-mirror.wirenboard.com` протух `Release`-файл («Release file ... is
  expired»), `apt-get update` вернул 100, и из-за `set -euo pipefail`
  обновление рабочего контроллера сорвалось на первом же шаге — при том
  что зависимости давно стояли и apt был не нужен вовсе. Правильная
  логика: сначала проверить импортом (`python3 -c "import paho.mqtt, yaml,
  flask"`), лезть в apt **только** если пакетов реально нет, ошибки
  `apt-get update`/`install` не считать фатальными, а решение принимать по
  финальной проверке импортом — она же печатает человеку, что делать.
  Для протухших индексов помогает `-o Acquire::Check-Valid-Until=false`.
  Обходной путь на объекте: `SKIP_APT=1 bash scripts/install.sh`.
  Общий принцип: чужая инфраструктура (зеркала, сеть, прокси) обязана
  уметь ломаться, не мешая обновить наш код.
- **Самообновление и `systemd-run`/cgroup** (v0.9.0, `scripts/self-update.sh`,
  `wb_energy_meter/updater.py`): апдейтер **нельзя** запускать обычным
  `subprocess.Popen` из процесса сервиса. У `wb-energy-meter.service`
  `KillMode=mixed` и `MemoryMax=256M` — дочерний процесс попадает в ту же
  cgroup, и `systemctl stop` (который `install.sh` вызывает в начале
  установки) убивает systemd **всю** cgroup целиком, включая сам
  апдейтер, посреди обновления. Результат — полускопированное дерево в
  `/opt` и незапускающийся сервис. Правильно: `updater.start_update()`
  запускает `scripts/self-update.sh` через
  `systemd-run --unit=wb-energy-meter-update --collect ...` — это выносит
  апдейтер из cgroup сервиса, он переживает `systemctl stop`. Фолбэк
  (`setsid nohup`) — только если `systemd-run` недоступен, с
  предупреждением в лог.
- **Запись статуса обновления не должна зависеть от обновляемого кода**
  (`scripts/self-update.sh`, функция `_write_status_py`): `install.sh`
  делает `rm -rf $INSTALL_DIR/wb_energy_meter` и только потом копирует
  новый код. Если установка упадёт в этом промежутке, пакета на диске
  нет. Первая версия писала статус через
  `from wb_energy_meter.updater import write_status` — импорт падал,
  `step_status` молча не срабатывал (там `|| log_line`), статус навсегда
  оставался `installing`, и веб-интерфейс вечно показывал «идёт
  обновление» без единого способа это сбросить. Поэтому статус пишется
  **встроенным** кодом на голой стандартной библиотеке, без импорта
  проекта. Логика записи (слияние полей + `os.replace`) намеренно
  продублирована с `updater.write_status` — это тот случай, когда
  дублирование дешевле зависимости. Регрессия закрыта тестом
  `test_self_update_writes_status_without_installed_package`.
- **Самомодификация: одной `main()` мало, нужен `{ main "$@"; exit "$?"; }`**
  (09.09.2026, `scripts/self-update.sh`, последняя строка файла).
  Обёртка кода в `main()` защищает только **тело** функции: оно разобрано
  и лежит в памяти. Но после возврата из `main()` bash идёт читать файл
  **дальше**, с байтового смещения, запомненного до перезаписи. Файл к
  этому моменту другой длины (реально: 20087 → 25277 байт при обновлении
  0.11.0 → 0.11.1), смещение попадает в середину чужой строки, bash
  выполняет обрывок и получает «command not found» — **код 127**.
  Симптом: обновление полностью проходит, в логе «УСПЕХ: обновлено до
  X», и сразу следом «ОШИБКА на этапе 'done' (код 127)» — трап ERR
  затирает успешный статус аварийным, и пользователь видит в интерфейсе
  красный отчёт о неудаче после удачного обновления.
  Лечится составной командой `{ main "$@"; exit "$?"; }`: она
  разбирается целиком до выполнения, `exit` оказывается в памяти вместе
  с вызовом, и к файлу после этого никто не обращается.
  Вторая линия обороны: `on_error` выходит раньше, если `FINISHED=1` или
  `STAGE=done` — поздняя ошибка не имеет права затирать успех.
  Регрессии закрыты `test_self_update_survives_being_overwritten_while_running`
  и `test_on_error_does_not_overwrite_success`.
- **Самомодифицирующийся bash-скрипт**: `install.sh` теперь копирует
  `scripts/` целиком в `/opt/wb-energy-meter/scripts/`, а значит
  `self-update.sh` переписывает сам себя на диске, пока выполняется (шаг
  "installing" внутри самого себя). Классическая грабля: `cp` в
  install.sh открывает существующий файл с truncate, и если bash в этот
  момент дочитывает СВОЙ ЖЕ скрипт с диска дальше текущей позиции —
  получится "syntax error" на пустом месте. Мы уже наступали на похожее
  с незакрытым `<template>` в HTML — здесь аналог для bash. Митигация:
  всё тело `self-update.sh` обёрнуто в функцию `main()`, вызываемую
  последней строкой файла — bash обязан полностью разобрать (прочитать
  с диска) тело функции ДО начала её исполнения, поэтому к моменту
  запуска `main` файл уже читать не нужно. Не выносите код за пределы
  функций, определённых до финального `main "$@"`.
- **`set -e` + `trap ... ERR` + `set +e` внутри трапа**: в `on_error()` в
  `self-update.sh` мы специально вызываем `set +e` (чтобы шаги
  восстановления не падали друг на друга), но `set +e`/`set -e` —
  ГЛОБАЛЬНАЯ опция шелла, не локальная для функции. Без явного `exit`
  в конце `on_error()` shell после `set +e` решает, что `errexit`
  выключен, и **продолжает выполнять `main()` дальше**, как будто
  ошибки не было — обновление реально продолжало долбиться в
  `install.sh`/`verify_after_install` после уже случившегося отказа на
  предыдущем шаге. Нашли прогоном сценария "битый архив" в песочнице:
  скрипт не падал сразу, а зависал на 90-секундном опросе `/health`
  несуществующего сервиса. Фикс: `on_error()` обязан явно завершать
  процесс (`exit "$rc"`) в конце, не полагаясь на то, что `-e`
  подхватится сам после возврата из трапа.
- **CRLF в `.sh`-файлах ломает `bash -n` без единого намёка на причину**
  (нашли при сдаче v0.9.0): `scripts/install.sh` и
  `scripts/install-from-github.sh` были на диске с CRLF-окончаниями строк
  (рабочее дерево на Windows-примонтированном диске, `.gitattributes` с
  `text=auto` нормализует блобы в git, но не переводит уже вытянутые
  на диск файлы обратно). Любой `if ... then\r\n ... fi\r\n` в bash
  ломается: `\r` приклеивается к слову-ключевому слову (`then\r`,
  `fi\r`, `do\r`), bash его не распознаёт, и падает
  `syntax error: unexpected end of file` — причём номер строки в
  ошибке почти всегда не имеет отношения к реальной причине. Чинится
  `sed -i 's/\r$//' file.sh`. Проверяйте `file scripts/*.sh` перед
  сдачей — вывод должен быть без "with CRLF line terminators".
- **`/etc/wb-mqtt-serial.conf` — чужой файл** (v0.10.0,
  `wb_energy_meter/wb_serial_config.py`). В нём описаны ВСЕ устройства
  контроллера: реле, датчики, приводы, — он отвечает за весь ввод-вывод
  объекта, а не только за учёт электроэнергии. Правится **только** за
  флагом `wb_serial.allow_edit` (по умолчанию `false`), с бэкапом
  (последние 10), сверкой sha256 перед записью (тот же файл параллельно
  редактирует веб-интерфейс WB — гонка реальна) и **точечно**: меняется
  ровно `enabled` у канала `Uptime` у одного устройства, больше ничего.
  Запись атомарная (tmp + fsync + `os.replace`) с сохранением прав и
  владельца, после записи — обязательная перечитка с откатом из бэкапа.
  Файл, который не разбирается как чистый JSON (комментарии `//`,
  JSON5), **не правится никогда** — только отказ с просьбой включить
  канал вручную; «умных» починок и вычисток комментариев быть не должно.
  При малейшем сомнении (устройство не найдено, найдено дважды) — отказ,
  а не догадка. **RPC на запись конфигурации у драйвера нет** (есть
  только чтение портов/сканирование), `conf.d` — только для
  пользовательских шаблонов, куски конфигурации устройств туда класть
  нельзя. Перезапуск `wb-mqtt-serial` прерывает опрос всех устройств на
  несколько секунд и делается только по явной кнопке
  `POST /api/wb-config/restart-driver`; при неподнявшемся драйвере —
  автоматический откат конфига из бэкапа. Список неприменённых
  изменений живёт в таблице `kv`
  (`wb_serial_pending_restart`), чтобы пережить перезапуск нашего
  сервиса. Регрессии закрыты `tests/test_step10_wbserial.py`, в
  частности тестом «конфиг байт в байт не изменился при любом сценарии
  отказа».
- Версию бампать **в двух местах**: `wb_energy_meter/__init__.py` и `pyproject.toml`.
  Изменения фиксировать в `CHANGELOG.md`.

## Работа с git в этом репозитории

Читать **до** первой команды git. Здесь git ведёт себя не так, как вы
привыкли, и это регулярно съедает время.

### Почему всё зависает

Репозиторий лежит на диске Windows, а агент работает из Linux-песочницы
через монтирование. На этом монтировании `unlink()` не работает —
возвращает `Operation not permitted`. Git при этом функционирует, но
**не может удалить за собой служебные файлы**: после почти каждой
операции остаются `.git/index.lock`, `.git/HEAD.lock`,
`.git/objects/maintenance.lock`. Следующая команда git видит лок и
отказывается работать:

```
fatal: Unable to create '.../.git/index.lock': File exists.
Another git process seems to be running in this repository...
```

Никакого второго процесса нет. Это просто мусор, который git не смог
подчистить. То же самое видит GitHub Desktop — и тоже встаёт.

### Как делать правильно

**Локи не удалять, а перемещать.** `rm` здесь не работает вообще,
работает только `mv` в пределах того же диска. Складывать всё в
`.git/_trash/` и больше никуда:

```bash
cd /путь/к/wb-energy-meter
mkdir -p .git/_trash
for f in .git/index.lock .git/HEAD.lock .git/objects/maintenance.lock; do
  [ -e "$f" ] && mv "$f" ".git/_trash/$(basename "$f").$(date +%s%N)"
done
```

Запускать этот блок **перед** каждой git-операцией и **после** неё —
git создаёт локи заново прямо в процессе работы, так что одной уборки
в начале не хватает. Предупреждения вида
`warning: unable to unlink '.git/objects/.../tmp_obj_XXXX'` в выводе
git — ожидаемы, это тот же мусор; на результат они не влияют, трогать
эти файлы не нужно.

### Чего не делать

- **Не запускать `git gc`, `git prune`, `git repack`** — они массово
  удаляют объекты, здесь это гарантированно оставит кучу мусора и
  может порвать репозиторий.
- **Не трогать руками ничего внутри `.git/refs/`.** Один агент уже
  положил туда посторонний файл и сломал `git show-ref` и `git fsck`.
- **Не использовать `git push --force`** и вообще `--force` где-либо.
- **Не делать `git push`.** Пользователь пушит сам через GitHub
  Desktop. Задача агента — довести дерево до состояния, в котором
  Desktop может работать (см. ниже).

### Что должно остаться после вас

Пользователь открывает GitHub Desktop и жмёт Push. Чтобы это
сработало, на выходе обязано быть:

1. **Ни одного лока** — проверить:
   `find .git -maxdepth 2 -name '*.lock' -not -path '*/_trash/*'`
   должно вернуть пусто.
2. **Работа закоммичена.** Не оставляйте правки в staged-состоянии
   «чтобы пользователь сам закоммитил» — он ждёт готовый коммит и
   кнопку Push, а не разбор чужих изменений.
3. **`git status --porcelain` чист** (кроме файлов, которые
   пользователь сознательно держит неотслеженными).
4. Проверить, что реально уходит: `git log --oneline origin/main..main`.

Перед выводом об «отставании от origin» полезно свериться с сервером
напрямую — локальная ссылка `origin/main` может быть устаревшей:

```bash
curl -s https://api.github.com/repos/9043366188-dot/wb-energy-meter/commits/main \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['sha'])"
```

### Мусор

`.git/_trash` со временем разрастается. Из песочницы его не удалить —
попросите пользователя снести папку из проводника Windows. На работу
репозитория она не влияет.
